# Explicit action approval over AG-UI

`POST /api/operate/agui/approval` adapts one existing queued InferOps board transition. It does not run a model or grant connections. The authenticated API reopens `forwardedProps.approval.workspaceId` on every request; the existing build capability may inspect/decide its action journal, while use-only and foreign callers are refused without action metadata. Current capabilities have no visible-but-non-approver action surface.

The canonical 1.0 request supplies threadId, runId, messages and one approval selector `{workspaceId, actionId}`. Client messages/state are untrusted history and ignored; client tools and context are empty. The initial action must already be pending. Its existing journal record stores the authenticated person, thread/initial run, random interrupt id, ten-minute expiry and the facet's exact scope/request fingerprint/revision/idempotency key and bounded transition simulation. A sparse journal index reserves one action per person/thread. No separate approval store.

The response starts a run, sends authoritative STATE_SNAPSHOT and MESSAGES_SNAPSHOT, then RUN_FINISHED. Pending uses the namespaced reason `inferos.gatekeeper.approval.v1` (not a fabricated tool_call correlation), a single interrupt, ISO expiresAt and responseSchema `{approved:boolean, editedArgs?:{toStateId:string}}`. The simulation contains only issue/state references for this transition. Server action state/lastAttempt determine applied/rejected/failed/unknown; successful transport never implies application.

Resume contains exactly one resolved entry with the stored interruptId. The complete answer is validated before effects. Person/thread/action/fingerprint binding, deadline and current workspace capability are checked again. An unchanged approval calls approveAction; rejection calls rejectAction. Identical answers recover the stored result; conflicting answers fail. The existing action claim and provider idempotency serialize/recover applies; unknown stays unknown after a later refusal. Reload without a resume reads the current action record, including decisions made through another authorized surface.

An edit never approves: the existing facet validates the new target against the current issue/revision/workflow, stages a fresh transition with a new fingerprint/key, and records its replacement link durably. The kernel invalidates the old decision and journals the replacement, which gets a fresh interrupt before any application. Invalid edits leave the old action unchanged. Replacement recovery reuses the staged replacement, not another write. One action per run is explicit; there is no cross-action transaction promise.

Read-only endpoints and Gatekeeper session simulation/queue hiding remain unchanged. No implicit approvals, new roles, generic registry, UI or external Mastra. Local synthetic identity/provider and isolated real InferOps acceptance are separate from live sign-in and deployment proof.
