# Operate mode

## Overview

The operate session is implemented in the kernel: one per person, holding a page state that is the replay of an ordered event log, plus an owner-only workspace for its operate chat. Clients reach it through `AuthenticatedApi.getOperateSession()`. The session workspace is operate-only, enforced in its Overseer: its capability denies every authoring method, and its chats' agents get a tool set with no authoring tools plus `operatePage`, which changes the page as the agent.

## Data and Control Flow

The session lives in the user Durable Object, which already exists once per person and is owner-only. Every session method there runs synchronously against storage, so concurrent calls from several tabs and the operate agent are serialized and never interleave.

`dispatch(event, expectedSeq)` compares `expectedSeq` with the stored sequence number and rejects with `conflict` if another change landed first. It then applies the event with `applyOperateEvent`, rejecting with `invalidEvent` (an `OperateEventError`) when the event doesn't fit the current page. Only then does it append the log entry (`seq`, `event`, `actor`, `at`) and store the new snapshot together with that entry. Either both are written or neither is. Client dispatches are recorded with the actor `person`.

Before a person's `openConsole`, `openView` or `showScreen` (with a screen) reaches the user DO, `OperateSessionImpl` checks it against the console as stored, because the reducer is pure and only knows what `openConsole` copied in. It opens the console's workspace with the caller's own role and reads the console (the one being opened, or the page's open one) with `getConsole(id, source)`: its published revision, or its draft for a builder's preview, which the use role is refused. It then applies `consoleEventMismatch`: the event (for `openConsole`) or the open run must name the revision read, `openConsole` must name one of its views and its `fullChat`, `openView` one of its views, and `showScreen` a screen of the view the page shows. A missing or never-published console, an unreadable workspace (no access, deleted, views disabled), a draft the caller can't read or a mismatch rejects with `consoleChanged`, and nothing is appended. So once a new revision is published (or, while previewing, the draft is saved again), the open console's next navigation is refused and the person reopens it on the new revision; returning to the view (`showScreen` with null) is never checked. A concurrent change between the page read and the dispatch is caught by `expectedSeq`. The operate agent's `operatePage` cannot send these events, so its path skips the check.

`subscribe()` sends the current snapshot and subscribes to the stored snapshot with no await in between, so no event can fall in the gap. Every later update carries the log entry that produced it. Every connection a person holds subscribes to the same storage, which is what keeps their tabs and devices live on one session.

A session is also told, without an event, when the console its page has open moves on. After `publishConsole` or `deleteConsole` commits, the console's workspace (`OverseerImpl.announceConsoleRevision`, never awaited by the call; not in `ctx.waitUntil`, which has no effect in a Durable Object, so it runs while the workspace object stays alive with the calls outstanding) calls `noticeConsoleRevision(workspaceId, consoleId, revision)` on the user DO of its owner and of every current collaborator (`listCollaborators()`), in batches of 16, logging a failure (`console.revision.notice.failed`) and going on. A collaborator who has been removed, or anyone else, is not told, even with the console still open. The revision is the published one, or null for a deletion. A user DO whose page has that console open at an older revision, compared as numbers (either source: a publish raises the draft's revision too), or for a deletion at any revision, sends every live subscriber the unchanged snapshot with `OperateSessionUpdate.consoleRevision` set and no `record`; any other session ignores it. Nothing is appended or stored, so the page is still the replay of its log and the run still names the revision it opened, which the kernel goes on refusing. The notice is a hint that grants nothing: a client closes what it shows of the old revision and reloads its consoles. It is best effort and not replayed: a connection that was down misses it and learns of the change when its next navigation or host-board context check is refused. In `workshop-consoles.test.ts` it reaches an operator's open published console and a builder's draft preview within 2 s of the publish (15 to 18 ms measured locally), not a collaborator with nothing open or one removed while it was open, and a reopened session only for the next change, a deletion. `workshop-backend/__tests__/console-revision-notice.test.ts` covers the ordering: two publishes fan out independently, so an earlier publish's notice that lands after the session reopened at the later revision (or one naming the open revision itself, or another console) is dropped.

`getWorkspace()` claims a fresh Overseer id in the user DO (synchronously, so two first calls agree on one id) and registers it like `newGadget()` does, titled "Operate session". `listGadgets()` skips it. If the recorded workspace has been deleted, the next call claims a new one. The session opens it with `open(..., asOperateSession)`, which records `operateSession` in the workspace's own storage. The mark is never cleared, and every later open checks it, including the owner's `openGadget()` by id: a marked workspace is refused to anyone but its owner, before any share key is redeemed, and the owner gets `OperateOverseerInterface`.

`OperateOverseerInterface` wraps the owner's `OverseerClientInterface` and forwards only what the operate chat needs: metadata, presence, workpiece and console subscriptions; the chat methods (`newChat`, `sendChatMessage`, history, attachments, titles, `stopAgent`, `retryAgent`, `deleteChat`); the action log, `approveAction` / `rejectAction` and auto-approval rules; connection requests and `newGatekeeper` / `getGatekeeperById` / `getGatekeeperByResourceUrl`; and `listCanvases` / `getCanvas` / `listFlows` / `listConsoles` / `getConsole` / `getConsoleScreen`. Everything else rejects with "Unauthorized": gadgets (`createGadget`, `getGadget`), code (`submitCodeChange`, commit reads, merges and draft changes), canvas, flow and console edits, hooks, blueprints, AI-model and agent-spawner gatekeepers, sharing, and the workspace's title, kind, pin and deletion. Like `UseOverseerInterface` it `implements Overseer`, so a new Overseer method does not compile there until it is classified.

The agent loop reads the same mark (`AgentHooks.isOperateSession()`), never anything the client sends, so every chat in the workspace is an operate chat however its turn started. Its tools are the `OPERATE_AGENT_TOOLS` allowlist: `readFile`, `grep`, `webFetch`, `observeUserChanges`, `describeBinding`, `executeCode`, `listCanvases`, `listConnectableResources`, `requestConnection` and `operatePage`. `writeFile`, `editFile`, `createGadget`, `createWorktree`, `setGadgetBinding`, `editCanvas` and `listBlueprints` are not offered, so a call to one fails as an unknown tool. `executeCode` still reaches connected resources through their gatekeepers, so a domain write queues for approval exactly as in Build. A short operate note leads the project-specific half of the system prompt. Other workspaces' chats never get `operatePage`.

Some resource types are never used by an operate chat: a vendor marks them `SupportedResource.excludeFromOperateChat` (the InferMind Wiki, #61), which only narrows where a resource is used. The Overseer enforces it server-side, for the chat's agent only, by matching a connection's recorded vendor and resource URL against its vendor's types: `listConnectableResources` leaves the type out, `requestConnection` refuses it, `executeCodeMode` drops such connections from the bindings before building the env (so a Wiki the person connected in the session workspace and pasted into the chat is not in `env` at all), `describeBinding` refuses it, and `startGatekeeperSession` refuses an agent's session to one as a backstop for any stub that reached the agent another way. The person's own `openSession` on the connection, Build chats and the canvas Wiki widget are unaffected. A connection recorded with no vendor or URL (from before both were kept) matches no type. `integration-tests/__tests__/operate-chat-no-wiki.test.ts` covers the operate agent not being offered or able to request the Wiki, a pasted Wiki absent from its env, refused to `describeBinding` and unwritable, with no Wiki text reaching the model and no action queued, while the person's own session reads it and a Build chat reads a pasted one; the session-open backstop has no test of its own, since no route in the test reaches it once the env is filtered.

In an operate workspace, the agent's connection and `env.GIT` bindings are bound to the `executeCode` run they were minted for, as worktree bindings already are everywhere. `getEnvForAgent` stamps the run's `executionId` into each `gatekeeper` and `git` loopback target, `executeCodeMode` registers the run's `{executionId → chatId}` for exactly its duration, and `startGatekeeperSession` refuses an agent's session unless that execution is still running and belongs to the chat the stub was minted in. So a stub the agent keeps past its run, for example passed to `self.<method>()` and delivered back as a callback argument into a later run of the same chat or into another chat, fails with "no longer live" before any gatekeeper or git code runs, and an operate agent uses each binding by name in every run instead. An agent stub minted with no `executionId` (before this check existed) is refused too. Gadget callers, the person's own sessions and every other workspace are unchanged. This binding does not cover a stub used by another chat while its minting run is still live; that overlap is left to the planned taint work. `workshop-backend/__tests__/execution-bound-loopbacks.test.ts` covers the stamp, use inside the live run, refusal in a later run of the same chat, refusal under another chat's caller (both after the minting run and with a live run's id), the unstamped refusal, gadget callers, and unchanged Build workspaces. `integration-tests/__tests__/operate-execution-bound-loopbacks.test.ts` keeps `env.GIT` through `self.keep(...)` in a real operate chat and shows the delivered stub refused in the callback turn, while a Build chat running the same script still opens it.

`operatePage` reads the page or applies one event to it: `open`, `focus` or `close` a screen or workspace reference, `goToStep` or `exitFlow` in the running flow, `showHome`, or `openBoard` / `closeBoard` (not the issue events, which only the board surface sends). It returns the resulting page state as JSON. The Overseer forwards it to the owner's user DO (`dispatchOperateEvent(event, null, "agent")` or `getOperatePage()`), so the event goes through the same reducer and serialized log as a person's and is recorded with the actor `agent`. A null `expectedSeq` applies it to whatever page is current, since the agent acts on the latest page rather than one it watched.

A session can run a **flow**: `startFlow` copies an ordered list of one workspace's screen ids into the page state (`flow`), `goToStep` moves the index within it, and `exitFlow` clears it. While `flow` is set the page is meant to show only that step (the full-canvas state); the working set and focus are untouched, so they return on exit. Because the steps are copied in, the reducer validates a step from the event alone and a run is unaffected by later edits to the flow it started from.

Flows are authored per workspace and stored in its Overseer (`flows` collection), next to the canvases whose ids are a flow's steps. The flow methods need build access and both view flags, exactly like the canvas methods, and the use-role capability denies them. A flow is saved only over canvases that exist in that workspace, in the author's order; a step may repeat. Replacing or deleting compares the revision and rejects a stale one with the canvas conflict error. The store never touches a session: a client reads a flow and dispatches `startFlow` with its steps, so the kernel does not check that a run's steps match a stored flow, and a step whose canvas was deleted later is for the client to show as unavailable.

A session can have a **console** open. `openConsole` copies the console's workspace, id, title, `source` (`published`, or `draft` for a builder's preview), revision, `fullChat` setting and a starting view id into the page state (`console`), so later events are checked from the event alone, like a flow's steps. A run stored before consoles were published reads as the published one at no revision (`UserDurableObject` fills it in), so its next checked navigation is refused once. `openView` shows another view and `showScreen` opens a screen from it (`null` returns to the view), and `closeConsole` closes the console. `showHome` returns to the mosaic, clearing focus and any running flow as well as the console and setting `presentation` back to `canvas`, while keeping the working set, subject and approval state; the operate agent may send it. The page's `presentation` is `canvas` or `chat`. `openConsole` sets it to `chat` when the console's `fullChat` is `default` or `only`, and `setPresentation` is rejected when the console's setting is `off` (no full chat) or `only` (no canvas). The reducer does not check view or screen ids against the stored console; the session capability does, before dispatching (above). A view or screen that stops resolving after it was opened, because the console was edited later, is for the client to show as unavailable.

Consoles are authored per workspace and stored in its Overseer (`consoles` collection), beside the canvases their views reference, under the same rules as flows for writes: build access and both view flags, at most 16 per workspace, each view's screens must exist in that workspace, and replace and delete compare the revision. A console holds references, order and settings only, and opening one grants nothing.

A console follows **draft → preview → publish**. Its stored content is the draft: `createConsole` makes an unpublished draft (`published: null`), and `replaceConsole` changes only the draft and raises its revision, keeping `published`. `publishConsole(id, expectedRevision)` (build-only, the revision checked like a replace) raises the console's revision, like a replace, and copies the draft into `published` at that new revision (`revision`, `publishedAt`, `content`), so of two publishes at one revision the second throws the canvas conflict error, and every publish, even of unchanged content, is a new revision that open sessions move to and, in the same transaction, replaces the console's rows in the `consoleScreens` collection (keyed `<consoleId>/<screenId>`) with copies of the canvases its views reference as they are now. Later canvas edits change only the live canvas, which is the draft, so operators keep the screens as published until the next publish. `deleteConsole` removes the draft, the published revision and its screen copies. Storage version 5 publishes every console saved before this existed as it stood, with copies of its screens (`#migrateToPublishedConsoles`), so operators keep the consoles they had. `getConsole(id, source)` reads one console's draft or published revision (`publishedConsole`), and `getConsoleScreen(consoleId, screenId, source)` one screen of it: the published copy, or the live canvas for the draft; both are null where that revision doesn't show it. A builder previews a draft by opening it with `source: "draft"` in their own session: it reads through their own access like any console, and its actions still queue for approval.

Reading is wider than for flows: `listConsoles` is also allowed to the use role (`UseOverseerInterface`) and to the operate session capability, so an operator granted use on the workspace reaches their console without Build; create, replace, publish and delete stay build-only. Build access lists every draft, with its `published` revision; the use role lists only published consoles, as published, and its `getConsole` and `getConsoleScreen` are refused for `draft`. To find it, the operator needs the workspace in their `listGadgets()`: `Overseer.addCollaborator` records it in the new collaborator's user DO (`recordSharedGadgetOpen`, with their effective role) as soon as it is shared, not only on their first open. The record is presentation only and grants nothing (`open()` still authorizes), so a failure to write it is logged (`shared.gadget.add.record.failed`) and the share stands; `workshop-consoles.test.ts` checks the listing before the first open. The use role also reads, through `listCanvases` and `getCanvas`, exactly the screens its workspace's published consoles show, as published (where two consoles published different revisions of one screen, the later revision): layout and references only, so the console renders without Build. A screen no published console shows reads as missing (absent from the list, `null` from `getCanvas`), so it stops being readable as soon as a publish drops it, and canvas writes stay build-only. `workshop-consoles.test.ts` covers one winner among publishes at the same revision, a screen-only republish moving an open console, an unpublished draft hidden from the operator, publishing, draft edits to the console and a screen leaving the operator's revision unchanged, the builder's preview and the operator's refused one, conflicting publishes, the operator's open console moving on after a republish, the republish and deletion notices (above), and deletion; `published-consoles-migration.test.ts` covers the version 5 migration.

A screen's board references are resolved under the viewer's own authority. For a build-role viewer that is the console workspace's connection, verified against their own account at `open()`, as on any canvas. The use role is denied `getGatekeeperByResourceUrl` and `getGatekeeperById`, so an operator never reads through the console owner's connection. An operator resolves the same `inferops://` reference in their own operate session's workspace instead (`OperateSession.getWorkspace()`, whose capability allows `getGatekeeperByResourceUrl` and `newGatekeeper`): a connection exists there only if the operator created it with `newGatekeeper` from their own connected InferOps account, through `User.getGatekeeperClassFor`, where the gatekeeper resolves the reference's workspace among that person's InferOps workspaces and checks their own access to the project. So scope is bound to the operator's capability, never to the URI or the console. Reads are recorded as observations, and proposed writes queue for approval, in that session workspace. With no such connection the lookup is null; with no InferOps account, or one InferOps refuses the project, no connection can be made (the refusal reads like a missing project), and the operator gets nothing of the owner's. `integration-tests/__tests__/operate-use-role-boards.test.ts` covers an operator reading the console's screen and their own board with their own token, an operator with no account and one without the project, and an unchanged build collaborator.

A console may also carry `customization`: four independent booleans for personal shareable screens, custom widgets, application tools and custom skills. The parser requires every flag to be a boolean and keeps a definition with no field as it is; clients treat absence as all disabled (`DEFAULT_CONSOLE_CUSTOMIZATION`). They are opt-in policy settings, not capability grants, and are changed only through the build-only console writes with their revision check. Creating and sharing personal extensions is separate work, and the flags do not enable authoring in the operate-only session workspace.

A session can show an **approval** under review. `reviewApproval` names one pending action as `{workspaceId, actionId}` (the workspace's `ActionLogEntry.id`, a non-negative integer, since action ids count up per workspace) and sets `reviewing`, replacing any approval already under review. `approvalResolved` records `{workspaceId, actionId, outcome}` (`applied`, `rejected` or `failed`) as `lastApprovalOutcome` and clears `reviewing` only if it names the same approval. Both events change presentation only: they never approve, reject or apply anything. An action is resolved only through its workspace's `approveAction` / `rejectAction`, the gatekeeper's apply result is the truth `approvalResolved` reports, and the reducer does not check either event against the action log.

**Approval outcomes.** An action records what its apply actually established. `Gatekeeper.applyAction` may return `{failed: ActionApplyFailure}` instead of throwing, since RPC carries only an error's message. The result's `outcome` is `notApplied` (the provider effect is known absent) or `unknown` (it may exist), and `retryable` says whether applying again may succeed. `OverseerImpl.applyPendingAction` turns the answer into one of three facts:
- **Applied.** The action becomes `approved`.
- **Refused and not retryable** (`notApplied`, `retryable: false`). The action becomes `failed`, a terminal `ActionState` that can't be approved again, with `lastAttempt {outcome, message, code?, at}`.
- **Anything else, including a thrown error, which asserts nothing.** The action stays `pending`, with `lastAttempt` recording the reason, whether the effect may exist, and `retryable` (a thrown error is recorded `false`: it asserts nothing).

An action that has a `lastAttempt` is sent again only when that attempt is explicitly `retryable: true`, whatever its outcome (for example an adapter that can replay its write, such as InferOps' board writes under their idempotency key, or a refusal reconnecting can fix). Otherwise (`false`, a thrown error, a recovered interrupted apply, or a flag left out by an older gatekeeper or an attempt recorded before it was kept) `#applyPendingAction` refuses another approval, manual or by the auto-approval drain, before reaching the gatekeeper and without recording anything, so the action can only be rejected; a `notApplied` attempt without `true` already ended `failed`. An untouched pending action is approvable. The Workshop applies the same rule (`canApproveAgain` in `actionAttempt.ts`): Approve is disabled and no Always approve rule is offered in Activity, the chat card and the Operate approvals panel, and `attemptNotice` tells the person to check the provider and deny it. Activity's review card and the chat card's details show the last attempt's notice. A rejection keeps an unknown attempt's uncertainty: history shows it as "Denied, may have applied" (Activity, chat), and the notice and the Operate outcome, also when restored, say local approval is closed and the provider decides whether it took effect. Operate re-reads the decided action whenever its reported outcome changes, so a later decision elsewhere (a rejection after this tab's failed attempts) shows the current entry, and a newer reported outcome replaces this tab's own notice.

Further details:
- An unsuccessful apply never sets `appliedAt`. `actionChangeTime` (and so the `byLastChanged` resume index) uses `lastAttempt.at` for it, so reconnecting subscribers see the attempt.
- `failed` is not `pending`, so the pending and history indexes and `matchesActionHistoryFilter` treat it like any resolved action, and the auto-approval drain skips it.
- A rejection keeps an earlier `lastAttempt`, so an action whose outcome was unknown never reads as safely undone.
- Once an attempt's outcome is unknown, it stays unknown until a success, the authoritative receipt, settles it. A later attempt's refusal is recorded against it with a note and never ends the action as `failed`.
- `applyStartedAt` is written durably before dispatch and cleared with the outcome. At startup `#recoverInterruptedApplies` turns any pending action still carrying it into a new unknown attempt with `retryable: false`, always replacing the earlier one (even an explicitly retryable one), since a restart may have cut off an apply the provider received. It stamps `lastAttempt.at` with the recovery time (the original start is kept as `startedAt`), so a subscriber resuming from a watermark another action set after the start is still sent it.
- One decision runs per action at a time. `withActionClaim` holds an in-memory claim from the pending check to the outcome for an apply (manual approval and the auto-approval drain alike) or a rejection (`rejectAction`, which keeps the claim through its gatekeeper call, a re-read of the record and the stored rejection). Concurrent approvals reach the gatekeeper once, and a rejection cannot interleave with an apply.
- A `failed` awaited action counts as decided. Its agent turn resumes with a note naming what was refused and why, and nothing is reported as applied.
- gatekeeper-kit's `applyActionOutcome` turns `ActionApplyError` into a not-applied refusal and `ActionOutcomeUnknownError` into an unknown, non-retryable outcome. A journal record replayed after a restart rethrows its stored classification. The test gatekeeper, the tickets connector and the connection template (`scripts/connection-template`) use it.
- The InferOps gatekeeper returns its own outcomes: a board write refused on its first attempt, or anything that failed before sending, is not applied; every other failure, and any coding or Wiki write that may have reached InferOps, is unknown. See [InferOps gatekeeper](inferops-gatekeeper.md) (apply outcomes).
- `workshop-agent-actions.test.ts` covers:
  - a refused apply that ends failed with its reason, applies nothing, refuses a second approval and resumes its turn;
  - an unknown outcome that stays pending with its warning through a restart and a rejection;
  - another send only after an attempt with an explicit `retryable: true`, for both outcomes with the flag true, false and left out (an untouched pending action is approvable): a kit `ActionOutcomeUnknownError`, a generic thrown error and a recovered interrupted apply are refused before the gatekeeper; the auto drain, signalled complete by an earlier action it applied, does not send a later unretryable one; and an attempt the drain itself made is not sent by the next drain (checked over a window, as no earlier action can signal it);
  - an unknown outcome the adapter can replay (`retryable: true`) recovering through another approval, and a retried dispatch cut off by a restart recovered as non-retryable with no third send, reaching a subscriber resuming from a newer watermark;
  - two concurrent approvals that apply once;
  - a refusal after an unknown outcome that keeps the action pending and possibly applied;
  - an apply interrupted by a restart that comes back with an unknown outcome;
  - a rejection refused while an apply is under way, and an approval refused while a rejection is;
  - an interrupted apply's recovered outcome reaching a subscriber that resumes from a newer watermark.


A stored snapshot may predate a page-state field. The user DO fills missing fields from `INITIAL_OPERATE_PAGE` whenever it reads the snapshot, so such a session reads as if it always had the field (a session stored before approvals reads `reviewing` and `lastApprovalOutcome` as null).

A session can show a **board** (#61): `openBoard` names `{workspaceId, boardRef}`, the board's canonical reference and the workspace whose connection reads it, and `closeBoard` stops showing it. Opening a console, another view or screen, closing the console or going home closes the board too, so a board never outlives the context it was opened in. The board carries an optional `issueId`: `openIssue` shows one issue over it (a board must be shown) and `closeIssue` returns to the same board; `openBoard` starts with none. Board, issue and Back are therefore session events, restored on reload and reconnect from the log, and a tab acting on an old sequence number is refused with `conflict`. The reducer checks only lengths. Before a person's `openBoard` reaches the user DO, `OperateSessionImpl` opens the named workspace with the caller's own access and requires `getGatekeeperByResourceUrl(boardRef)` to find a connection there; otherwise it rejects with `boardUnavailable` and appends nothing. A use-role operator is denied that lookup on a console workspace, so their boards name their own session workspace, where a connection exists only if they made it from their own account. The operate agent's `openBoard` (`operatePage` with a `boardRef`) is rewritten by the Overseer to name the session workspace itself and refused, as an agent-readable tool error, unless one of that workspace's connections reports exactly that reference; the agent is told to ask the person to connect it rather than open another board. So a stale, unconnected or removed target is refused explicitly and never replaced by a default; a board whose project was since deleted or whose access was revoked opens as a reference and fails on its first read, which the board surface shows as such.

The operate prompt tells the agent to discover boards with the InferOps board session's `findBoards(query)` through `executeCode`, to show the candidates and ask when more than one fits, to say plainly when none fits and open nothing, and to open only the candidate the person chose by its exact `boardRef`. `findBoards` itself is the gatekeeper's (see [InferOps gatekeeper](inferops-gatekeeper.md)). `integration-tests/__tests__/operate-board-discovery.test.ts` covers paraphrased and empty searches over the person's own projects, opening a connected board, refusing a found but unconnected one and then opening it once connected, refusing a console owner's connection to a use-role operator and to a stranger, and a revoked or signed-out person's search failing; `operate-chat.test.ts` covers the agent's refused `openBoard`. `operate-chat-boards.test.ts` drives the operate chat with a scripted model and a board the person pasted: an ambiguous request returns both plausible boards with reasons and opens neither, a request nothing matches returns no candidates and opens nothing, and a board found in the person's other InferOps workspace is refused when opened unconnected, drops out of the search once their membership there is revoked, and stays refused (the page log stays empty throughout). What a real model says to the person is not tested. `operate-board-recovery.test.ts` covers #63's recovery cases below the UI: a connection dropped while a board, an issue and a pending edit are open comes back to the same page at the same sequence number with the one pending action, overlaid and unwritten (the same edit again is a no-op, another edit is refused `CONFLICT`, and approving twice writes once); two tabs proposing the same new issue queue one create and write one issue; and an issue deleted in InferOps while open leaves the board, refuses its reads, its edits and its pending edit's apply without writing, while the page keeps naming it until the person closes it.

### Subjects, handovers and the per-subject audit

A session's **subject** (#64) is the board it shows. `OperatePageState.subject` is derived: `applyOperateEvent` sets it to `board?.boardRef ?? null` after every event, and the user DO re-derives it when it reads a stored snapshot, so it can't disagree with the board. `openBoard` is the design's `openSubject` for the first subject type, and it is already validated against a connection the sender can reach (above). Switching subject is another `openBoard`, which replaces the board and starts with no issue, so nothing of the previous subject stays on the page; the board surface keys its subject-bound state by the reference. The older free-string `setSubject` event is kept in the `OperateEvent` union so logs recorded before still read, but the reducer refuses it and the agent's `operatePage` no longer offers it.

Each log entry records the subject it concerned (`OperateEventRecord.subject`, from `operateEventSubject`): a handover's board, else the board shown after the event, else the one shown before it, so the event that closed or switched away from a board counts toward it. Entries stored before this field have none.

A **handover** (`OperateSession.handOver(recipientId, note)`) shares the session's subject (its board reference and open issue, never the sender's workspace id) and a note of up to 2,000 characters into another person's session. `OperateSessionImpl` reads the board from the sender's own page, re-checks that the sender still reaches it (`boardUnavailable`), and looks the recipient up as `addCollaborator` does (`idFromName` and `whoamiIfExists`), refusing an unknown id or the sender with `recipientUnavailable`. It appends `handoverReceived` to the recipient's log first, then `handoverSent` to the sender's, both with the actor `person` and the same handover id; the two Durable Objects can't be written atomically, so if the second append fails the call rejects and the recipient keeps the handover. A person's `dispatch` of either event is refused with `invalidEvent`, so a log can't claim a handover that never happened. `handoverReceived` adds the handover to `handovers` (at most 20, oldest dropped) and `dismissHandover` removes it; `handoverSent` changes nothing on the page. A handover grants nothing: the recipient opens the board with their own `openBoard`, validated against their own connections, so a recipient without access is refused exactly as if they had found the reference themselves. Handover notes appear in the page JSON the operate agent reads.

The **per-subject audit** (`OperateSession.listSubjectAudit({workspaceId, boardRef}, cursor?)`) is read from the existing logs, with no copy kept. It first opens the named workspace with the caller's own access and requires a connection to exactly that reference, the same check as `openBoard`, so a person who can't reach the subject is refused with `boardUnavailable`, and a use-role operator can't read a console workspace's log through it. One page returns this session's events whose `subject` is the reference (scanning up to 200 entries, via the user DO's `listOperateSubjectEvents`) and the workspace's action log entries whose `resourceUrl` equals the reference (one `listActions` page of 50), both newest first, plus a cursor (`beforeSeq`, `beforeActionId`, null once a log is exhausted). A page can be empty while the cursor continues. The events are the reader's own; the action log is the workspace's, so in a shared console workspace it holds every collaborator's reads and writes there, and in a session workspace only its owner's.

**Presence on a subject** (`OperateSession.subscribeToSubjectPresence(subscriber)`) shows who else has the same board open. Each person's session lives in their own user DO and workspace, and a use-role operator's board resolves through their own session workspace, so no existing object (in particular no workspace's Overseer presence) is shared by two operators on one board. The smallest shared place is one `SubjectPresenceDurableObject` per subject reference (`getByName(boardRef)`, migration `v4`). It keeps only an in-memory roster, like the Overseer's workspace presence, and speaks the same `PresenceSubscriber` protocol (now generic over its participant), with `OperateSubjectParticipant {key, user, issueId}` in place of a role, so each person also shows the issue they have open over the board. Several subscriptions by one person (tabs, devices) collapse into one participant showing the issue of their latest one, who leaves when the last ends; an `add` for a present key replaces it.

`OperateSessionImpl` reads the board from the caller's own page (`invalidEvent` when none is shown), runs the same reach check as `openBoard` (`boardUnavailable` otherwise), and joins the caller (`whoami()`) with the page's issue. So only people whose own access reaches the subject can see or appear on its roster; the DO itself has no access check and is reachable only from the kernel. The caller is present until the returned stub is disposed or the connection breaks (`onRpcBroken`); a client re-subscribes when its board or issue changes. Access is checked when subscribing, not continuously, so a person whose connection is removed stays on a roster until they next subscribe. The roster is lost when the DO is evicted or restarted, which also breaks every subscriber's stub, as with workspace presence.

Retention and compaction: the audit has no storage of its own, so it is retained exactly as long as the two logs are. Today both are kept in full: the operate event log has no pruning and the action log is never pruned. If the event log is ever compacted, the rule is that entries carrying a `subject` (and every handover) are kept, and only subject-less page navigation may be folded into the stored snapshot, so the audit of a subject never shrinks under compaction. Action log entries are the gatekeepers' record and are not compacted by Operate.

References in the page state (`screen`, `workspace`, a board, a handover, and a flow's workspace and steps) identify targets only. The session never opens them and grants no access.

### Pinned installs and upgrades

Publishing stamps the source workspace's kind on the blueprint (`BlueprintMetadata.kind`, in `createBlueprint` and in `updateBlueprint` when it republishes code) and stores it with that version's R2 content (`<blueprintId>/<version>`, custom metadata `kind`). An uploaded archive keeps a known kind and drops any other. Content stored without a kind (older versions, bundled blueprints) reads as `app`; an unknown stored kind is refused.

Each version may also declare a **data contract**, a non-negative integer the publisher passes with the publish (`createBlueprint(..., {dataContract})`, or `updateBlueprint({updateCode: true, dataContract})`; a contract with no new version is refused). It is stored like the kind, as custom metadata `dataContract` on the version's content, and as `BlueprintMetadata.dataContract` for the current version. A version published without one, and every version from before contracts, has none, which counts as unknown. An uploaded archive keeps a valid contract and drops anything else.

Each version's binding list is stored beside its content too, as its own R2 object `<blueprintId>/<version>.bindings` (JSON). It isn't custom metadata like `kind` because R2 caps custom metadata at 2 KiB, which binding titles and descriptions can exceed. `propagateBlueprint` writes it for the current version on every publish or update, before the content, so `updateBlueprint({updateBindings})`, which changes the current version's bindings without a new version, is kept too. Deleting a blueprint deletes both objects per version. A version without a stored list (published before lists were stored, or uploaded or bundled content, whose only list is the blueprint's KV metadata) falls back to the blueprint's current bindings.

There are two ways to install a version, sharing `blueprint-install.ts`. Both read the version with `readBlueprintVersionToInstall`, which refuses, before creating anything, a version that doesn't exist, whose kind differs from `options.kind`, or whose binding list has no binding an assignment names, and both record a `BlueprintInstall` of `{blueprintId, version, kind, dataContract}` taken from the version's content. Both create the assigned bindings with `createBlueprintBindings`, through the installer's own capability, so connections come from the installer's accounts (through `User.getGatekeeperClassFor`) and models from the installer's models. An install may still leave bindings unassigned (the standard output formats install with none). Republishing writes a new version and touches no install. Installing by id works for any signed-in person, published or not; publication records (see [feature capabilities](feature-capabilities.md#publication-records)) govern only reach beyond that: the unauthenticated `PublicApi.getBlueprint`/`downloadBlueprint` and the featured listing. The tests read blueprint metadata through `AuthenticatedApi.getBlueprintInfo` for that reason.

- `AuthenticatedApi.newGadgetFromBlueprint(blueprintId, bindings, options)` makes a new workspace of the installer's own. `initializeFromBlueprint` gives it that version's kind (also in the owner's list) and records the install in the workspace's storage (`installedFrom`), which `getMetadata()` and `subscribeToMetadata()` report for both build and use roles.
- `Overseer.installBlueprint(blueprintId, bindings, options)` installs into an existing workspace, an **operate space**, as a new gadget, and returns its id. It is called on the space's capability, so it needs build access there: the owner and `build` collaborators may install, whoever owns the space, and `UseOverseerInterface` and `OperateOverseerInterface` deny it. The installer reads the blueprint by its id, which is the read capability, as in `fetchBlueprint`. The version's files become the gadget's first commit, the gadget is titled after the blueprint with a binding name derived from its title, and the install is recorded on the gadget's record (`GadgetRecord.installedFrom`), reported as `GadgetSummary.installedFrom` on workpiece subscriptions. The space's own kind is unchanged. The gadget is placed on the space's screens and reached through its consoles by the existing canvas and console composition; nothing new assigns it. Creating a connection as a `build` collaborator severs every `build` session of the space under the existing verification-scope rule (`addGatekeeper`, `scheduleAccessRestart`), so the installer's client reconnects and verifies the new connection with an account of their own, like any build collaborator's.

  An install request may carry a key (`SpaceInstallOptions.requestKey`, 1 to 128 characters). A repeat with the same key creates nothing and returns the first request's gadget: while the first runs, from `OverseerImpl.runningInstalls` (registered before its first await, so a concurrent double submission joins it), and afterwards from the key stamped on the gadget's record (`GadgetRecord.installRequest`), so a retry after a lost connection or a restart finds it. The key is bound to the blueprint and version option it was first used with; reusing it for another is refused. If an instance restarts in the middle of an install, the retry returns the gadget with the bindings made so far. Without a key, every request is its own install.

**Publication review (client).** Build's "Publish to Operate" button (shown with composable views, like InferOps Canvas) opens `/workspace/$id/publish`. It reviews the blueprint first published from the workspace (`listBlueprints`, read back through the signed-in `getBlueprintInfo`, so an unpublished blueprint is reviewable): version, kind, data contract and connections. "Publish version N" calls `updateBlueprint({updateCode: true, dataContract})` with the contract the person entered (prefilled with the current one; empty publishes an unknown contract), and warns when the workspace's kind changed since. A space is chosen among the person's workspaces they build in (`listGadgets`, use-role entries left out) and kept in the URL. The space is opened with `useWorkspaceOpen`, so a build collaborator verifies its connections as on any open, and its installs of the blueprint are read from its workpiece subscription (`GadgetSummary.installedFrom`), so after a reconnect the page shows what the kernel holds. The space shows a "Test space" badge when `testOnly`, and a button marks it a test or a normal space (`setTestOnly`; the kernel's refusal to unmark one holding mocks is shown). Each install shows its version and contract, and offers "Upgrade to version N" only when `upgradeBlock` finds nothing in the way; otherwise it says why (current, wrong kind, needs migration, unknown contract). A version with no connections installs from the page (`installBlueprint` pinned to the version and kind under review); one with connections links to the blueprint page with `?space=`, which reuses its connection choosers and then installs into the space. That page opens the space with the account-verification prompt (`hooks/useObserverPrompt.ts` and `ObserverConfigModal`), so a build collaborator verifies the space's connections with accounts of their own exactly as when opening it in Build; cancelling installs nothing and says why. Each Install, on the review and on the blueprint page, sends a request key (`SpaceInstallOptions.requestKey`) generated once per intent (this version into this space): a retry after a failure or a lost connection reuses it, so the kernel returns an install it already made, and the key is dropped once the install succeeds. The blueprint page reads the blueprint signed in (`getBlueprintInfo`), as the review does. One action runs at a time, so a second click submits nothing; a lost connection to the space marks it stale and disables its actions until it reconnects. A refusal is shown in an alert that takes focus, with the kernel's message and what it means; nothing is rolled back or claimed. With nothing published, the page offers only Back to Build. A use-role viewer of the source gets no authoring controls. A test-only space shows `components/TestSpaceBadge` wherever it appears: on the review, in the Build header, in the use-role view (`GadgetUseView`) and over its screens in the Operate session (`SessionScreen`, with a note that it may use mock data). `OperatePublishReview.test.tsx` and `operatePublish.test.ts` cover these states, `BlueprintLandingPage.test.tsx` the install into a space and its verification prompt, `GadgetUseView.test.tsx` and `SessionScreen.test.tsx` the badge.

**Mock dependencies.** Before `installBlueprint` creates anything it resolves every assignment as the caller (`#mockDependencies`), which also refuses an account or model the caller no longer has. A connection is a mock dependency when the account's own `getGatekeeperClassFor` reports the URL as `mock` (the InferOps gatekeeper does for `demo.local`; `User.getGatekeeperClassFor` passes it through), and a model when its registration is marked `mock` (`ApiKeyModelConfig.mock`, which `pnpm dev:setup --mock-model` sets). Names are never consulted. Unless the space is **test-only**, any such assignment refuses the install with an error naming each binding. `Overseer.setTestOnly(testOnly)` sets or clears the mark (build role; stored as `testOnly` in the workspace's storage and reported as `GadgetMetadata.testOnly` to build and use roles); the mark grants nothing. In a test-only space the install records the bindings in `BlueprintInstall.mockDependencies`.

The check also holds after install. Each connection and model binding records whether its creator's account or model reported it as mock (`GatekeeperRecord.mock`, set by `newGatekeeper`, `newAiModelGatekeeper` and `newAgentSpawnerGatekeeper` through `addGatekeeper`), and `bindWorkpiece`, which every binding goes through (the person's `GadgetClient.bind`, a chat's proposed binding, the agent's `setGadgetBinding`), refuses to bind a mock record into a gadget installed by `installBlueprint` in a workspace that is not test-only, naming the binding. Clearing the test-only mark is refused while any installed gadget has recorded mock dependencies or binds a mock record.

`Overseer.upgradeInstall(version, gadgetId?)` is the only thing that moves an install: gadget `gadgetId`'s, or with no id the workspace's own, on its default gadget. It needs build access: `UseOverseerInterface` and `OperateOverseerInterface` deny it. It reads that version of the recorded blueprint and refuses a missing version and, through `assertUpgradeCompatible`, one whose kind differs from the install's or whose data contract is not equal to the installed one: a different contract is refused as needing migration, and an undeclared contract on either side as unknown. So an install of a version with no contract (including every install made before contracts) cannot be upgraded. It also refuses a version that needs a binding the gadget doesn't have on mainline (its `spawnerOnly` bindings aside; the error names each missing binding), and writes the version's files as a new commit on the gadget's head. It then re-checks that neither the head nor the pin moved during the awaits, fast-forwards the head, re-pins the install, and restarts the gadget. Bindings, storage, chats, grants and credentials are untouched, and nothing is read from the source workspace. A downgrade is the same call with an older version of the same contract. There is no migration or data rollback.

A bound resource fails closed for anyone the install is shared with, through the observer check every non-owner open runs (`authorizeCollaborator` / `ensureObserver`; see `docs/observers.md`): a `use` viewer must name an account of their own for each gatekeeper bound into the gadget, and the gatekeeper's `addObserver` must admit it. A viewer with no account, no prompt channel, or an account the gatekeeper refuses gets an error that names the binding, the account and the gatekeeper's reason, and no workspace capability, so they never reach the gadget or the installer's connection; a refused first-time viewer stays registered with no gatekeeper. The check runs again on every open, so revoked access is refused on the next one. An operate session holds references only, so the same person's session can show the install's screen in its working set while rendering it still goes through `openGadget` and is refused. `operate-published.test.ts` covers each case against the test gatekeeper.

### Console widget registry

A console's content may carry `widgets`, its widget registry (`ConsoleWidgetEntry` in `operate-console.ts`, at most 16): each entry names a gadget of the console's workspace, the blueprint and version it was installed from, a label, and `state: "resettable"`, the builder's declaration that the widget may start with empty local state on each publication (the only value). `parseOperateConsoleContent` trims the label and drops any client-supplied `frozen`. The store (`checkConsoleWidgets` in `console-store.ts`) checks the registry when a console is saved and again when it is published: each entry must pass `consoleWidgetRefusal` (a permanent gadget of the workspace, not itself frozen, whose `installedFrom` matches the entry with `kind: "widget"`, that declares no data contract and that has no binding edges at all, pending or not, read from the gadget itself because bindings can be added after install), and every widget install (or frozen install) placed as an `inferos.gadget` on a screen the console shows must be registered; other gadgets, such as installed apps, are placed as before.

Publishing (`publishConsoleRecord`) gives each entry a *frozen install*: through `OverseerImpl.frozenInstalls()`, a new gadget record at the registered gadget's current commit (the workspace's one object store already holds it), with the same `installedFrom`, no bindings, and `frozenFor {consoleId, revision, sourceGadgetId}`. The published content lists the frozen installs, each entry recording `frozen {sourceGadgetId, commitId}`, and the published screen copies point their `gadget:<id>` references at them. Since a gadget runs one code version on one facet, the frozen install's UI bundle and server both run that commit, whatever later happens to the registered install. All of this, and the removal of the console's earlier frozen installs (record and facet), runs in the publish transaction after every check has passed, so a refused publication creates nothing and leaves the previous one live; deleting a console removes its frozen installs too. `assertNotFrozen` refuses every change to a frozen install: a client's code submission (`submitCodeChange`) and the agent's file-writing tools (through the `AgentHooks.assertNotFrozen` hook), chat merges, `bind` / `unbind` / `renameBinding`, `setTitle`, `setBlueprintAnnotation`, `createBlueprint`, `remove` and `upgradeInstall`; and a builder cannot run it from a chat (`getUiBundle` / `connectToGadget` with a `chatId`), so it only ever runs its frozen commit. Its runtime state (facet storage) still changes as operators use it, and starts empty for each publication. Merging a code change restarts the workspace's gadgets so they load the new heads (`bumpVersion`), but by default not its frozen installs, whose commit no merge changes: an operator's open widget, and every capability it holds, keeps running across a Build edit of the source. Restarts that name a gadget, and the authority checks on every call, still apply to them.

The use role cannot open a widget installed into the workspace, registered or frozen, through `getGadget`. It opens one with `getConsoleWidget(consoleId, revision, gadgetId)` on the console's workspace, opened with the operator's own role (as the Operate page opens a console's screens). That is allowed only for a frozen install that the console's published revision `revision` offers (`offeredWidget`) while the caller's own operate session has that console open at that published revision (its `OperateConsoleRun`, read from their user DO). The returned `UseGadgetClientInterface` repeats both checks before every call (title, UI bundle, connect, export), and so does the server capability `connectToGadget` returns: `getGadgetFacet` takes the check as a guard that runs before every call through the facet proxy and wraps any capability a call returns (`guardedResult`), including ones held in returned arrays and plain objects and returned functions (an `apply` trap), the same way. So a capability from an older publication, from a console since unpublished or deleted, or from a console the person has since left for another is refused. Build access gets the ordinary gadget capability after the registry check. The operate session's own workspace capability denies `getConsoleWidget`, like `getGadget`: it holds the person's operate chat, never a console's widgets. Apps shared for use open with `getGadget` as before; a widget installed as a whole workspace (`newGadgetFromBlueprint`, whose provenance is the workspace's `installedFrom`) is refused for its default gadget like any widget install. `createBlueprint` and `updateBlueprint` (with `updateCode`) run `assertPublishableKind` on the published commit for every kind. It classifies the commit's files (`classifyGadgetFiles`, reading a widget's `view.json` and `tools.json` as strict UTF-8 through `readCommitBlob`) and refuses what `blueprintPublishRefusals` keeps. A widget is refused on every violation, so a widget version has its UI and server, its server and a valid `tools.json` (a callable widget, see [Callable widget tools](#callable-widget-tools)), or is view-only: a valid `view.json` (see [Bound views](#bound-views)) and no `.js` file or `tools.json`. An app or workflow is refused only for shipping a `view.json` or `tools.json`, with a message telling the author to rename the file. Its other codes, such as an app with no `client.js` or a workflow with one, still publish as before. `operate-widget-registry.test.ts` covers registration and placement refusals, the frozen install's runtime and its refusals, edits and new versions reaching operators only on republish, another console's and a stale revision's refusal, a kept capability, server capability and server capabilities returned directly, in an object, in an array and as a function refused while the person's session shows another console and after a republish, proposals and chat runs refused on a frozen install, a losing concurrent publish and a refused one leaving the live publication and its frozen install, a whole-workspace widget install refused to the use role, kept capabilities that keep running across a merge into the source while the source itself restarts, the old capability failing after a republish, removal on republish and deletion, data contracts and non-installs refused, both publication paths' kind check, an app with no `client.js` and a workflow with one still publishing but refused once they ship a `tools.json` or `view.json` (and publishing again once it is renamed), a widget with an invalid `view.json`, or one beside code, refused while a valid one alone publishes, and its `tools.json` refused when invalid and published (with or without `client.js`) when valid; `workspace-kind.test.ts` covers every row of the classification matrix, and `bundled-blueprints.test.ts` that every bundled blueprint still passes the publish check; `operate-console.test.ts` covers parsing and `consoleWidgetRefusal`.

### Callable widget tools

A widget may declare tools in a `tools.json` beside its `server.js` (`WIDGET_TOOLS_FILE`); its kind stays `widget`, and the file is pinned with the code by the commit. `widget-tools.ts` holds the schema and the checks, all pure and without `eval`:

- `parseWidgetTools(text)` returns the declarations or throws a named reason. The file is at most 16 KiB of UTF-8 and a JSON array of 1 to 8 tools, each exactly `{name, description, method, effect, input, output}`. Names and methods match `^[a-z][A-Za-z0-9]{0,47}$`, names are unique, and a method is never reserved (`RESERVED_TOOL_METHODS`: `constructor`, `fetch`, `alarm`, the handler names, `then`, `dup`, `toJSON`, `Object.prototype`'s methods, `ctx`, `env` and `__invoke`, plus any name starting with `_` or `webSocket`, through `isReservedToolMethod`). The description is one line of 1 to 200 characters of plain text, with no control, format or separator characters. `effect` is `"read"` only.
- An input takes no input (`{type: "object", properties: {}}`) or is one flat object with `additionalProperties: false` and at most 8 properties, each a string `enum` of at most 64 builder-written values of at most 64 characters, a `boolean`, or an `integer` whose `minimum`..`maximum` holds at most 1,024 values. Free strings, `number`s, unranged integers, nested objects, arrays and every other keyword (`$ref`, `pattern`, `oneOf`, `anyOf`, `description`, ...) are refused. There is no exception tier.
- An output schema nests objects and arrays at most 3 deep; every object is closed, every array has `maxItems` of at most 64, every string a `maxLength` of at most 256, and every `integer` or `number` a `minimum` and `maximum`. `null` and `boolean` are allowed.
- `plainJsonProblem(value, maxBytes)` refuses anything but finite plain JSON: functions (so capabilities), class instances, cycles, `NaN` and `Infinity`, sparse arrays, accessors, symbol keys, and nesting deeper than 8. It counts the UTF-8 bytes `JSON.stringify` would write without building the string, and stops as soon as they pass `maxBytes`.
- `widgetToolValueProblem(schema, value, maxBytes)` checks a value against a schema, after `plainJsonProblem` at the input cap of 512 bytes unless an output cap (16 KiB) is passed.
- `parseToolEnvelope(bytes, output)` reads a runner's result: at most 16 KiB of strict UTF-8 JSON, exactly `{t: "ok", v}` with `v` matching the output schema, or `{t: "err", m, len}` with `m` at most 1,024 characters and `len` at least its length. Every control or format character in `m` other than a line feed, and every lone surrogate, comes back as a space (one for one); a leading byte-order mark is refused.

No problem message quotes a value that crossed a call. The classifier parses `tools.json` with `parseWidgetTools`, so a widget with `server.js` and a valid `tools.json` publishes as a blueprint version, with `client.js` (callable, combined) or without (callable, tools-only), and `tool-main.js` or `tool-guard.js` at its top level is refused (`invalidTools`). Nothing else reads `tools.json` yet. No kernel method lists or calls a tool, the operate agent has no tool for either, and a console registers and freezes a callable widget like any other: its server runs only as a placed widget's does, through `getConsoleWidget` and its per-call checks, and a tools-only widget has no UI bundle (`getGadgetUiBundle` returns `null`). Discovery, invocation, the isolated runner and a `CONSOLE_TOOLS` flag do not exist.

### Host boards

A host board (MVP-26 slice 2; the trusted renderer, picker and editors are in [InferOps canvas](inferops-canvas.md#host-rendered-board)) is a console entry that trusted host code renders from a bounded board snapshot, which each operator reads through a connection they selected themselves, in their own operate session workspace. It is off unless `INFEROPS_HOST_BOARDS` is `"true"` (and `INFEROPS_ENABLED` is not off), checked at registration and publication, selection, acquisition and every read (`hostBoardsEnabled`). `ServerConfig.hostBoards` reports the switch, read only.

- **Entries.** `OperateConsoleContent.hostBoards` (`HostBoardEntry` in `operate-console.ts`) beside the unchanged `widgets`: `{kind: "host-board", id, label, requirement: {name, resource: "inferops-board", target}}`. `parseOperateConsoleContent` canonicalises the target (`canonicalHostBoardTarget`: lowercase `<tenant>.<workspace>` slugs, a key matching `^[A-Z][A-Z0-9]{0,9}$`), checks unique ids and requirement names and counts entries against `MAX_CONSOLE_WIDGETS` together with `widgets`. The store (`WorkspaceConsoleStore`) keeps a console's saved entries when a replacement omits `hostBoards` (ConsoleBuilder and ConsoleSettings omit it until the boards are edited); an explicit list, `[]` included, replaces them. While the switch is off it refuses a new entry (one without an id) and publishing any entry not already published, but a console holding saved entries can still be edited and republished, since they grant nothing while it is off. It mints an id (`crypto.randomUUID()`) for an entry without one, and refuses an entry naming an id the console's draft or published content does not hold with exactly that requirement. Publication copies the entries into the published content; they create no install, so a host-only publication freezes nothing, and only `widgets` entries reach `checkConsoleWidgets`, frozen installs, `getConsoleWidget` or `GadgetUI`.
- **Context.** Every host-board call names a `ConsoleRef` `{consoleId, source, revision}`. `OperateSessionImpl.#hostBoardRun` (server.ts) re-reads it each time: the caller's own console run must show that console from that source at exactly that revision (its workspace is the run's), the console is read through the caller's own role in that workspace (so a draft needs build access every time), its revision must still be that one and it must offer the entry. The guard each call hands the operate workspace returns `{target, sessionSeq}` (the session's event sequence, which rises on every event, so A→B→A or leaving and reopening never matches) or null.
- **Selection.** `OperateSession.selectHostBoardConnection(console, entryId, accountId, requestKey)` reaches the caller's operate session workspace Durable Object directly (`OverseerDurableObject.selectHostBoard`, Worker-only, owner-checked and only for a workspace marked `operateSession`) and runs `HostBoardDesk.select`. A request key already stored is checked against the caller and the exact payload (console workspace, console, source, revision, entry, account) first: a mismatch is refused, a settled request returns its outcome, a pending one is joined (or resumed after a restart). A new key reserves the target's next intent epoch and stores the request (`pending`), with the initiating context the session read (`intent`: the target and session sequence), in one synchronous step on arrival, before anything is awaited or created, so intents are ordered as they arrive. The connection is minted through the user DO's `resolveHostBoardClass`, which wraps the `getGatekeeperClassFor` chokepoint and returns the account's provenance only if its incarnation did not change across the resolution; `addGatekeeper` stamps `GatekeeperRecord.hostBoardMint {by, requestKey, accountId, incarnation}` at creation, which is how a retry finds its candidate instead of minting again. After the facet's `connectionIdentity()`, the account's provenance and the guard are read again, one transaction commits it only if the request is still pending and holds the latest epoch, the guard still finds the initiating target at the initiating session sequence (so a console left and reopened in between fails it), the connection's URL is the target and the account's incarnation is the minted one: the selection `{gatekeeperId, mintedFor (with the adapter's string account id), selectionEpoch}` and the request `committed`. A superseded or failed attempt is recorded as such (a tombstone a retry cannot reopen), and the replaced selection's request becomes `superseded`. A candidate is removed only when its stamp names this owner and that request and no committed selection names it, and never one a gadget binds or a hook uses (never a blind `removeGatekeeper`).
- **Provenance.** Each connected account (user.ts) carries an `incarnation`, new whenever the record starts pointing at a different account stub (a connect, a same-id replacement in `linkConnectedAccountFromLogin` or `putConnectedAccount`), and an `epoch`, from a per-user counter, raised by every authoritative mutation (those, an expiry, a restore after reconnect); `putAccount` is the one writer and `accountProvenance` the reader. `markCredentialsRestored` refreshes the description after its `describe()` only onto the record as it restored it (same incarnation and epoch), as a description-only update, so an expiry, replacement or disconnect landing meanwhile stands. Records from before read as incarnation `initial`, epoch 0. A disconnect deletes the record, so its provenance is null.
- **Read.** `OperateSession.getConsoleHostBoard(console, entryId)` checks the switch and the context and returns `ConsoleHostBoard`, which holds no target, account or connection. `readRequirement(name)` refuses any name but the entry's, takes `readAt` before any await and calls `OverseerDurableObject.readHostBoard`, which runs `HostBoardDesk.read` under one 10-second deadline from `readAt`: the guard, the owner's selection for the guard's target (none: `not-connected`), the connection's URL and stamp against `mintedFor`, the account's provenance (gone or a new incarnation: `not-connected`), `connectionIdentity()` against the minted adapter account, `readHostBoardSnapshot()`, whose answering attempt must have the same account and connection generation as that first sample (only the identity may differ, for a token refreshed within the generation), then a fresh `connectionIdentity()` compared with the answer's own fence, the account's provenance again (incarnation and epoch), and the guard again (same session sequence and target). Any change is `stale`; a connection removed under the read (a newer selection's cleanup) is `stale` too. The snapshot is projected again by the kernel (`projectHostBoardSnapshot`: only the allowlisted fields, every bound and enum rechecked, else `unavailable`). The read also captures the target's intent epoch and change sequence before its first await. The one final compare-and-set (`#commit`, no await from start to end) checks the call's token and the deadline, then that version (a newer intent reserved meanwhile makes any answer `stale`), then the selection's gatekeeper and epoch, then the pin: the first successful read pins the provider's `scope` on the selection, and a later scope that differs (a reused slug or key) is `not-connected` until the operator selects again. Only then does it write the pin and the audit, and return `{status: "ok", board, readAt, publicationRevision}`. When the deadline passes first the call is `unavailable` and the continuation can no longer return, pin or audit anything; a late rejection is observed without logging its cause. The session runs reaching the operate workspace and the desk's read under the same absolute deadline (`readByDeadline`), so a stall before the desk starts is `unavailable` at 10 seconds from `readAt` too; an answer committed just before the deadline whose response arrives after it is a lost response, answered `unavailable`. Diagnostics the adapter writes on its own are outside this no-late-effects claim. The compare-and-set validates the latest remotely checked state (user DO, console workspace, gatekeeper); it is not a lock across them, so a revocation those commit after the final remote check can let that one snapshot through, bounded by the client's expiry, which the UI change must enforce.
- **Audit.** A kernel-owned sink, not `ApprovalQueue`: `hostBoardReads` in the operator's own operate session workspace (at most 1,000 kept), each `{kind: "host-board-read", consoleId, entryId, requirementName, status, at}` and nothing else, never in the action log, activity or the console workspace. `ok`, and `not-connected` or `unavailable` only once the guard has held again; never a timed-out, stale or superseded read. A read before the workspace holds any host-board state (it has never been opened as the session) is `not-connected` with no record. `OperateSession.listHostBoardReads()` returns the latest 200, newest first.
- **Selection subscriptions.** `ConsoleHostBoard.subscribeSelection(subscriber)` covers that handle's one validated entry; its target is resolved server-side. `OverseerDurableObject.subscribeHostBoardSelection` installs the subscriber and takes its first state in one synchronous step (`HostBoardDesk.subscribe`) and returns that snapshot. The session side is one delivery lane (`HostBoardSelectionRelay`): nothing before the snapshot, then only the newest full state (a slow consumer holds at most one pending), never an older or repeated `changeSeq`, the context re-checked before each delivery, and exactly one terminal `unknown`. The operate workspace dropping its reference to the session's callback, which it does when it resets, is observed as that callback's disposal (the same signal `#openGadgetInternal` uses) and ends the subscription with `unknown`; a subscription whose setup failed ends silently. Each target's selection record has its own `changeSeq`, raised when an intent is reserved, committed or settled and when the selected connection is removed (`connectionRemoved`, called from `removeGatekeeper`); updates are full states `{state: "none" | "pending" | "selected", changeSeq, selectionEpoch}` with no account or board data, delivered after the event that made them (`setTimeout`), so a rolled-back commit is never reported. Once the context no longer holds, a delivery fails, or the client disposes it, the subscription ends the same way. A reconnect is a fresh subscription and snapshot; there is no replay log.
- **Tests.** `workshop-backend/__tests__/host-boards.test.ts` (synthetic ports, a fake clock, storage with rollback): idempotent and joined retries, a restart after and before the mint, latest-intent commits and loser cleanup, same-id replacement, the switch, exact audit fields, slug reuse, a refresh retry, paused reads released after each change, A→B→A, stalled guard, identity and snapshot at 10 s with no late effect, subscription bootstrap, pending to committed, rollback, deletion and recreation, a missed change, and the Durable Object entry points refusing another owner and the switch off. Its race-fence cases cover a generation change after the first sample, an older selection's held guard against a newer completed intent, a console left and reopened during a selection, a read released while a newer intent is reserved, the delivery relay (delayed bootstrap and guards, a slow consumer, concurrent invalidation, failed setup) and a real Durable Object reset observed as the native RPC disposal of the subscriber stub (this proves the reset signal the session relies on, not the browser subscription end to end; no integration test resets a Durable Object), and `readByDeadline` with a stall before the desk starts. `host-board-account.test.ts` covers provenance and a restore racing an expiry, a replacement and a disconnect through the real `markCredentialsRestored`. `console-host-boards.test.ts` covers both current editor payloads keeping saved entries, explicit removal, and editing and republishing after the switch goes off. `integration-tests/__tests__/operate-host-boards.test.ts` drives the real Workshop and gatekeeper against the fake InferOps: two operators with distinct synthetic boards and only their own bearers, a target only the publisher can still read, not-connected cases, forgeries, paused reads after a reconnect, selection change, console move and republish, a stalled fetch and a stalled body at 10 s, slug reuse, preview with the builder's own selection and a draft edit, and a subscription through selection, removal and a republish. `operate-host-boards-off.test.ts` covers the switch off at registration, selection and acquisition.

### Isolated tool lane

`tool-lane.ts` runs one method of a widget's frozen code for one caller and deletes everything the call created. It is kernel-internal (step C3 of the callable-widget contract): no client method, agent tool or Overseer RPC reaches it, and the Overseer only constructs the lane (`OverseerImpl.toolLane`) and wires its sweeps. Discovery, invocation, authorization and output-schema validation are not implemented.

- **Slots.** `ToolLane.reserve(callerUserId)` is synchronous: it sweeps, then refuses with `busy` when 4 calls are live in the workspace, `caller-busy` when the caller already has one, `cleanup-behind` when `pendingToolFacets` holds 64 rows, and `name-collision` when the minted name is pending or one of the latest 256 tombstones (it is never re-minted). Otherwise it writes `{name, callerUserId, startedAt, state: "pending", attempts: 0}` before any facet exists and returns a `ToolLaneSlot`. The slot is held until `release()` has aborted and deleted the facet; `runIsolatedTool` releases it in every outcome.
- **Load.** `LOADER.load` with the commit's `.js` files plus the kernel's `tool-main.js` and `tool-guard.js` (`mainModule: "tool-main.js"`), `env: {}`, `globalOutbound: null`, no tails, `compatibilityFlags: ["disallow_importable_env"]` and `limits: {cpuMs: 100, subRequests: 0}`. The facet is `tool-<crypto.randomUUID()>` with the loaded `ToolRunner` class. Every module path must be a plain relative `.js` path (no empty, `.` or `..` segment, no other extension), or the call is refused (`invalid-module`); a commit containing either kernel module name is refused (`reserved-module`, the same names as `RESERVED_TOOL_MODULES` in `widget-tools.ts`), as is one with no `server.js`. All are refused before anything loads.
- **Module graph.** `tool-main.js` imports `./tool-guard.js` first and the authored `./server.js` second, then hands the authored namespace to the guard's one-shot `attach` (a second attach throws, so an authored module that attaches first fails the load). The guard imports only `cloudflare:workers`, captures the intrinsics it uses (`JSON.parse`, `JSON.stringify`, `TextEncoder` and its `encode`, `ReadableStream`, `Object.getOwnPropertyNames`, `Object.getOwnPropertyDescriptor`, `Object.freeze`, `Reflect.apply`, `String.prototype.slice`; not `Array.isArray`, which the contract lists but the guard never calls) and freezes `ToolRunner`, its prototype and `attach` during its own evaluation. `ToolRunner.__invoke(method, inputJson)` constructs the authored `Gadget` and calls `method` only if it is an own data-function property of `Gadget.prototype` other than `constructor`. Setters for `ctx` or `env` installed by authored top-level code on `Object.prototype` or `DurableObject.prototype` do run on the runner instance as it is constructed, but an own `__invoke` they define there is not dispatched: workerd calls only prototype methods over RPC and refuses the call, which fails as `threw`.
- **Envelope.** The runner returns a byte stream of `{t: "ok", v}` (an `undefined` value becomes `null`) or `{t: "err", m, len}`, with `m` cut to 1,024 characters in the isolate. `readToolEnvelope` refuses a non-stream (`not-a-stream`), reads with a BYOB reader into a 16 KiB + 1 buffer and cancels on overflow (`too-large`), and accepts only UTF-8 JSON with exactly those keys (`bad-envelope`). A throw over RPC is `threw`, and its text is not read. `ok` results return the authored value unvalidated: the guard protects bounding only, since authored code can still patch intrinsics it does not own, so the caller must check the value against the tool's declared output.
- **Deadline.** `runIsolatedTool` refuses a call whose `deadlineAt` has already passed before loading anything (`deadline`), then races `deadlineAt` and aborts the facet when it passes. The race answers `deadline` even if that abort throws. It ends asynchronous waits only.
- **Cleanup.** A call ends with `facets.abort` then `facets.delete`; the row then moves to `toolFacetTombstones` (FIFO by `seq`, the latest 256, indexed by name). A delete that throws keeps the row pending with `attempts` raised; the slot is still freed. If the abort itself throws, the slot is freed too, while the facet may keep running until a sweep deletes it. `ToolLane.sweep()` deletes rows not live in this instance, oldest first, at most 16 per sweep, and runs at Overseer construction (every row is abandoned in a new instance), before each reservation and at the start of `runAlarmTasks`. `#updateAlarm` adds `ToolLane.nextSweepTime()`: while any row remains (live ones included, so a crash mid-call still wakes the object), 30 s from when it was first computed since the last sweep, doubling for each failed attempt after the first, up to 5 min. Every sweep clears that held time, so a call that is live across an alarm does not re-arm it at the time that just fired. A row leaves the table only after a successful delete.
- **Not bounded locally.** Local workerd does not interrupt CPU-bound code: a spinning tool delays the deadline until it ends and blocks the workspace, sibling facets, other objects in the process and the test runner; an infinite loop wedges them. `cpuMs`, `subRequests` and memory are not enforced locally, and nothing bounds what the runtime allocates before the 16 KiB cap applies. These are remote checks.
- **Tests.** `workshop-backend/__tests__/tool-lane.test.ts` runs the lane in a real `OverseerDurableObject` with synthetic fixtures: envelopes and the 1 KiB error cap, method and module refusals, a huge first chunk, non-stream returns, malformed envelopes, a top-level and a constructor-time `__invoke` override (with the spike's three-layout control), an instance-own `__invoke` set from `ctx`/`env` setters, non-plain module paths, an already-expired deadline and a throwing abort at the deadline, an early `attach`, blocked `fetch` and `connect`, concurrent callers (with a shared-facet control), stale descendant stubs, name minting and collisions (with a name-reuse control), the 256-tombstone window, slots, the async-wait deadline, abandonment and crash sweeps, failed-delete retries, the 16-delete bound, the 64-row refusal, the backoff, forced and real alarms, and an alarm with a call live across it. CPU-bound and wedge cases are documented in the file and not run.

### Bound views

A bound view (MVP-26) is a widget's `view.json`: a declarative spec, with no code, of what trusted host code renders from each operator's own host-board reads. So far only its pure, static validator exists, `parseBoundViewSpec(text)` in `workshop-shared/src/bound-view.ts`, the frozen v1 grammar (tightening it needs `version: 2`, so a published v1 spec is never reclassified). It returns `{ok: true, spec}` or `{ok: false, problems}`, each problem a `BoundViewProblemCode` and a spec path such as `$.root.of.where[0].equals`, never a quoted value, at most 32. It never throws, and it runs in order:

- **Raw text.** At most 8 KiB of UTF-8 (`specBytes`) and no leading BOM. Strict UTF-8 decoding is the caller's: blueprint publish reads `view.json` through `readCommitBlob(commitId, path, "text")`.
- **Tokenizer**, before `JSON.parse`. It checks JSON syntax, refuses a key repeated in one object and the keys `__proto__`, `constructor` and `prototype`, all compared after unescaping (so `"\u0061"` duplicates `"a"`), and holds every number lexeme to `0|[1-9][0-9]*`, at most 10,000, refusing `10.0`, `1e1`, `-0` and `00`. JSON nesting is bounded at 24.
- **`JSON.parse`**, whose reviver gives every object a null prototype.
- **Closed schema.** Unknown and missing keys, types and enums; the nodes `stack`, `columns`, `text`, `field` (a `ProjectRef`), `count`, `list` and `table` (queries) and `empty`. List items and table columns are leaves: a query or container inside a list item is `nestedCollection`. Fields come from `BOUND_VIEW_FIELDS`, the closed field tables of `HostBoardViewSnapshot`: `issues` (`identifier`, `title`, `priority`, `targetDate`, `blocked`, and the derived `column` and `group`), `columns` (`label`, `group`, the derived `count`), and `project.identifier`/`project.name`, which only a `ProjectRef` names. A field is looked up with `Object.hasOwn`, so `toString` is no field. `groupBy` takes only `column`, `group`, `priority`, `blocked` or `targetDate` for issues and `group` for columns. A `where` literal must have its field's type (`null` only for `targetDate`, an enum one of its members, a date `yyyy-mm-dd`). A badge-map key must be the canonical string of a value of the mapped field: a member, `"true"`/`"false"`, a canonical decimal at most 10,000, a date or `"null"` for `targetDate`, or the exact string (at most 100 code units, never `"null"`, since no string field is nullable) for a string field. A table column's `as: "date"` needs a date field, `"flag"` a boolean, and `map` needs `as: "badge"`. Requirement names (1 to 4, the host-board name pattern) are unique, and every query and `ProjectRef` names one exactly. `Text` is 1 to 200 code units and a string literal at most 100; both refuse a lone surrogate and the bidi controls U+061C, U+200E, U+200F, U+202A–U+202E and U+2066–U+2069.
- **Static limits** (`BOUND_VIEW_LIMITS`): depth 8, 64 nodes, 12 children per stack and 2 to 4 per `columns`, 16 queries, 4 `where` clauses and 2 sort keys per query, 1 to 8 table columns, 1 to 4 item leaves, 8 badge entries, `limit` 1 to 200 (50 when absent), Σ `limit` over lists and tables at most 500 rows and Σ `limit` × width at most 2,000 cells.

The classifier's default `view.json` parser is `parseBoundViewSpec`, which throws its problems as one line (`formatBoundViewProblems`). So a widget whose files are a valid `view.json` and no `.js` file or `tools.json` is classified `viewOnly`, and its blueprint version publishes. Nothing else uses a bound view yet: there is no `bound-view` console entry kind, no delivery and no renderer, and nothing reads `view.json` outside the classifier. A view-only version can be installed, and its install registered and placed in a console's `widgets` like any widget install (`consoleWidgetRefusal` checks provenance, not files), but it has no code: `getUiBundle` returns `null`, a connect fails for want of a `server.js` as a UI-only app's does, it offers no export, and `view.json` reaches no frame. `bound-view.test.ts` covers every static limit at its bound and one past, a maximum legal spec at every bound at once, raw-text size in bytes and the BOM, invalid JSON, plain, nested, escaped and collapsing duplicate keys, plain and escaped forbidden keys, refused and accepted number lexemes, closed-schema keys, own-property lookups, literal and badge-key typing per field, columns' `as` and `map`, requirement names, nested collections, bidi controls (plain and escaped) and lone surrogates, problem accumulation and capping, and a seeded fuzz over random token strings and byte- and structure-mutated valid specs (total, never accepting invalid JSON); `workspace-kind.test.ts` runs every matrix row under the real `view.json` and `tools.json` parsers.

### Authorization generation

`authzGeneration` is a persisted Overseer singleton that rises by one at every change to an authorization input (step C5a of the callable-widget contract, §4.1). `OverseerImpl.authzGeneration()` reads it synchronously, so a caller can record it, await, and compare it again in the same block as its final checks. Nothing reads it yet: C5b's console tool call will refuse to release a result when it moved during the call.

- **Helper.** `bumpAuthzGeneration(storage)` in `sharing.ts` is the only writer, apart from `deleteSelf`'s carry-over. Each call sits in the same synchronous block as the write it covers, after the write and after the enclosing function's last await, so no reader can see the change without the new generation. A bump at entry would let a call pass its final check between the bump and the grant.
- **Sharing.** `addCollaborator` (grant or role change), `removeCollaborator`, each kept user `#reRootKeptUsers` re-roots, `redeemShareKey` (beside each `collaborators.put`, after the profile fetch), `createShareLink` and `newShareLinkKey` (beside the `shareKeys.put`, after the key mint), and `revokeShareLink` (after the link write and the alias delete) each bump once per write. `updateShareLink` edits only a note and does not bump. A refused call, a preview and a redemption that grants nothing leave it unchanged.
- **Overseer.** `authorizeObservation` bumps when it newly sets `containsRestrictedData` or `ownerInvitesOnly`. A repeated flag leaves it alone. Observer records bump when removed (`#enforceExcludeObservers`, `tearDownLostObservers`) and when `ensureObserver` admits one or changes its id or account choices. A returning observer's identical rewrite leaves it alone. The owner write bumps in the first `open()` and in `receiveExternalMessage`. The operate-session mark bumps when first set, because it shuts out every other caller; the contract's table omits this input. `scheduleAccessRestart` bumps before its first await, in the same block as the removal, revocation or scope widening that triggered it, and its `storage.sync()` flushes the bump.
- **Deletion.** `deleteSelf` reads the generation before `storage.deleteAll()`, then writes it back and bumps it, so the generation never decreases. As a result, a deleted workspace keeps this one key. The restart it schedules bumps once more.
- **Tests.** `authz-generation.test.ts` drives every input through its real code path in a real `OverseerDurableObject` and asserts the exact rise. It also checks that the generation is unchanged by repeated flags and identical observer rewrites, that a revoke followed by a regrant raises it twice, and that it never decreases and survives `abortAllDurableObjects()`. `sharing.test.ts` checks placement: nothing rises while `redeemShareKey` awaits the profile, and a refusal during the profile fetch or the key mint leaves the generation unchanged. `authz-generation-guard.test.ts` scans `src/` for writes to the authorization inputs. It pins the reviewed sites, and it fails on any site without a following bump in the same method or with an await in between. It also fails on any other direct write to the generation, and on a `scheduleAccessRestart` that does not bump first.

## Configuration

None. Limits are constants in `operate-session.ts`: references and screen ids up to 128 characters, a subject (board reference) up to 512, a handover note up to 2,000 and at most 20 waiting handovers, at most 24 references in the working set (opening one more drops the oldest), and 1 to 32 steps in a flow run with a title up to 120 characters. The page holds at most one approval under review and one last outcome. One `listEvents()` page returns at most 200 entries, and one `listSubjectAudit()` page scans at most 200 events and 50 actions.

## Divergences from Design

Against [the design](../design/operate-mode.md):

- A console is stored in, and references screens of, one workspace; there is no operate space yet. It has no state machine (`consoleEvent`, `navigateBack`), no app assignments (widgets are registered as above), no role assignment, and no derived inventory. Operators with only the use role read a workspace's consoles and the screens they show, but not its flows, and they never reach its connections; their boards resolve only through a connection in their own session workspace (above). The operate agent's `operatePage` offers `showHome` but not the other console events.
- Full chat is a page presentation only: the conversation does not yet render widgets inline.
- A flow is a single ordered list of one workspace's screens. Views that lay out several screens at once, steps from other workspaces, and steps that must be completed before moving on are not implemented.
- Views and subject types other than the InferOps board are not implemented, and there is no separate `openSubject` event: `openBoard` opens the subject. A view does not declare a subject type, and the subject is not passed to screens and widgets as an input. The page state covers the working set, focus, subject, chat panel, app presentation, a running flow, the approval under review, the last reported approval outcome, the shown board and waiting handovers.
- The per-subject audit is per reader, not one cross-person trail: it covers the reader's own session events and the action log of the workspace they name. Another person's opens, and reads and writes made through another person's own session workspace, are not in it; a handover is in both people's.
- The session page dispatches `reviewApproval` and `approvalResolved` (see the approvals on the [operate session page](inferops-canvas.md#operate-session-page)) and reports only the outcome it read back from the workspace's action log, but the kernel does not check a reported outcome against the log. The page covers the session workspace and the focused screen's workspace only. Workflow runs started by a schedule, their approval waits and a generic workflow-run view are not shown in the session (post-release).
- The URL mirror is not implemented. Presence is per subject (the shown board); there is no presence on screens or views of a console. The agent can open, focus and close references, step or exit a running flow and open or close a board, but cannot start a flow or hand over, and it learns the page only by calling `operatePage` rather than from its prompt.
- A session workspace claimed before the `operateSession` mark existed is marked on its next `getWorkspace()`. Until then an `openGadget()` by id returns the full owner capability.
- The event log is kept in full. Compaction is defined (above) but not implemented.
- Role consoles are partial: there is a console definition and the `openConsole` / `openView` / `showScreen` / `closeConsole` / `showHome` events and a shown board and issue (`openBoard` / `closeBoard` / `openIssue` / `closeIssue`), but no general console state machine (`consoleEvent`, `navigateBack`).
- The kernel does not re-read the provider when a board is opened: it checks that a connection the sender can reach holds exactly that reference, and the board's first read is what reveals a deleted project or revoked access. A Wiki connection's binding name and title, when the person pastes one into an operate chat, stay in the conversation; only its use is refused (above).
- Build is not gated by role. Any signed-in user can author, and the Build | Operate toggle depends only on the `operate-mode` flag and composable views.
- Kind controls stop at install. The kernel enforces the explicit `setKind()` (denied to `use`), the builder contract and starter files, the workflow `client.js` refusal in the agent's file tools (skipped in worktrees), the kind recorded with each published version, and the kind checks at install and upgrade. The file classifier runs when any version is published, but an app or workflow is refused only for a `view.json` or `tools.json`. Placing an `inferos.gadget` on a canvas does not require a widget-kind gadget; a console's save and publication require a placed widget install to be registered.
- An operate space is an ordinary workspace: there is no separate container type, and a space's owner and `build` collaborators can still edit an installed gadget's code and call `setKind` on the space. An upgrade replaces the installed gadget's files with the version's, so local edits made on an install are superseded (they stay in its commit history). Installs are not assigned to consoles from the review; a builder registers one in the console's draft.
- Mock dependencies are checked for gadgets installed into a space, at install and whenever a binding is added; an upgrade adds no binding, so it is not checked again. `newGadgetFromBlueprint` (a personal, whole-workspace install) is not checked, and a connection or model binding created before `GatekeeperRecord.mock` was recorded counts as real. A model or resource is recognized as mock only when its registration (`ApiKeyModelConfig.mock`) or the account's own `getGatekeeperClassFor` says so, rather than from the resource type or model provider the design names, since neither of those distinguishes the InferOps demo host or the scripted model.
- "Cannot read the source blueprint" is the existing bearer-id rule: an install of a blueprint id that does not resolve (unknown or deleted) is refused before anything is created.
- An install whose bindings fail part way (after the pre-checks) keeps the gadget with the bindings made so far, as `newGadgetFromBlueprint` keeps its workspace; nothing is rolled back.
- A version published before binding lists were stored, or an uploaded or bundled one, is checked against the blueprint's current bindings at install and upgrade, since it has no list of its own.
- Host boards have no canvas widget kind yet: an entry is addressed by its id, and placing one on a screen is the UI change's. The registry editors send `hostBoards` only once a builder edits them, so an unedited save keeps the saved entries (still counted against the combined limit). The selection is keyed by target in the operator's workspace, so two consoles offering the same target share it. Only a connection removal clears a selection; there is no explicit unselect. Same-id replacement is proved at the unit level (`putAccount`); the integration suite reconnects the same account instead.
- The widget registry is MVP-26's first slice ([#183](https://github.com/factory-level/inferos/issues/183)): self-contained visual widgets only. A registered widget may have no bindings, so bound operational widgets cannot be offered; tool-running widgets without a UI, and the Operate agent's discovery and invocation of registered widgets, are not implemented; only the isolated lane those calls would run in exists, with no caller. Because a registered widget declares no data contract, `upgradeInstall` refuses it (see above): a new version reaches a console as a new install registered in the draft. A frozen install's state is shared by every operator of that published revision and starts empty on each publication. There is no registry editor in the Workshop UI yet.
- There is no derived console inventory and no admin or observability view of which apps and widgets each console uses.
- Console publication is decided by the workspace's `build` collaborator role, not a publisher permission issued through an InferOS gatekeeper, and a published console is shared with the workspace's collaborators only; there is no other sharing audience. There is no rollback to an earlier published revision (only the current one is kept) and no retirement short of deletion. An open console adopts a new published revision only by being reopened (its sessions are told at once, see `consoleRevision`, and its next navigation is refused); a running flow is not affected. A console's revision changes only when the console itself is replaced or published, so a screen edited since the last publish does not show as an unpublished change in the console's revisions (comparing `getConsoleScreen` for `draft` and `published` shows it, as the builder's launcher does); publishing an unchanged console again republishes its screens at a new revision.
- Preview has no separate data or side-effect contract: a draft opened as a preview reads through the builder's own access, and its actions queue for approval like any other.
- Build still offers the bundled `inferops.kanban` blueprint as a creatable output, and it does not yet offer Widgets or Agent workflows as outputs.

## Open Questions

- When the event log should start compacting (by size or age), given that subject entries are kept.
- Whether a cross-person subject trail is wanted, which would need a per-subject log rather than reads over each person's logs.

## Wave 5 design boundary

The [publication review](../design/operate-publication.md) design was accepted by the owner on 2026-10-05. Its kernel slice is implemented as described above: a space is a workspace that build collaborators install into, upgrades need equal declared data contracts, and mock dependencies are refused outside test-only spaces. The client's review page and actions are described above. The [approval/provider policy](../design/operate-policy.md) is a proposed review artifact, not new runtime behavior. A unified company-role/IAM administration surface and restricted-data provider allowlisting remain unimplemented. Company-specific roles are not equivalent to Build/Use or deployment ADMINS. Each person still owns one separate Operate session.
