# InferOps canvas and transactional widgets

## Overview

Current-state baseline inspected at InferOS `1045d2e1ceac7be29e1a6f056c936fb31aa00851`. Proposed work is recorded in the [design](../design/inferops-canvas.md), not asserted as implemented here.

## Data and Control Flow

InferOS hosts sandboxed Gadgets and human participant presence; these are not an implemented InferOps canvas or agent activity feed. InferOps has a versioned widget definition, visual/text registries, inferops:// target references and one project/board widget. Its text resolver coalesces repeated URIs, then resolves distinct URIs independently. ProjectKanban currently depends on InferOps authFetch and its own UI environment. The board DTO contains a full board and decimal-string revisions, not a cursor-page protocol. Personal canvas pins are scoped by tenant/workspace/principal and store x/y positions; they are not the guarded shared composition contract proposed here.

## Configuration

Current board widget freshness is 60 seconds. The InferOps board hook pauses polling when the document is hidden and merges revisions while protecting pending changes. Existing personal pins have their own RLS boundary. InferOS frontend changes must follow frontend-conventions and reuse Kumo/@gadgets/ui.

## Divergences from Design

A guarded composition schema and pure edit engine now exist; workspace-authorized definition storage now exists; the kernel resolves a board reference to the workspace's existing connection and the frontend's shared board data adapter loads it (see [Board data adapter](#board-data-adapter)); a Kumo Kanban renders it as a canvas card and a full view, with transitions through the approval path (see [Kanban board](#kanban-board)). The design's chat presentation is the canvas pane beside the workspace chat on the InferOps Canvas page: there is no board rendering inside chat messages. Board activity is derived on the client from the workspace action log rather than from emitted activity events (see [Board activity](#board-activity)): it carries no canvas, widget or run identity beyond the log's `requestedBy` label, has no *proposing* or *applying* phase for actions it did not propose itself (the log records a move once it is queued), and links an action to an issue card only through the `Issue` field the gatekeeper renders for the approver. Issue create and edit go through the same approval path as moves; whether a create or edit was applied or rejected is inferred from successive board reads (the gatekeeper also stops overlaying a change made stale by an outside change, which then reads as applied, as a stale move does), a created issue is matched to its provisional card by title, and the edit form cannot show or clear the current description, which the board DTO does not carry. Kanban performance is instrumented, has an adapter-side baseline and a local browser run against the mock gatekeeper (see [Kanban performance](#kanban-performance)); board cards defer their reads until they come into view, but no budget is agreed, nothing is measured against a live InferOps, and a large board still renders every card (no windowing or paging). The adapter's freshness is event-driven (moves and decided actions); the design's visibility-aware polling and freshness policy are not implemented. Importing the existing React component alone would not resolve authentication, styling, iframe or sharing boundaries.

Console board and issue continuity (#63) covers one board and one issue in the session; it has no multi-board history beyond the browser's, and a duplicate mutation is prevented only within one form (the in-flight guard) and, for an issue that already has a change awaiting approval, by the gatekeeper's `CONFLICT`: two tabs proposing the same new issue still queue two creates. Narrow and wide layouts reuse the existing console and full-view layout and are not separately browser-tested here; live real-provider browser evidence for #59 is not recorded by this change.

Durable views are released as a bounded slice (#34, MVP scope in #1): the one private Kanban/Operate view keeps its definition through reload and Worker restart, refuses stale expected revisions and inherits the workspace's build-access boundary (see the evidence under [Resolving a board reference](#resolving-a-board-reference)). The durable-view requirements in the [consumer configuration design](../design/consumer-configuration.md) for generalized export/import/rebind, independent view-sharing controls, deployment-update recovery, schema migrations and cross-customer upgrade matrices are post-release and not implemented; today a view is shared only by sharing its workspace, and import always creates a new definition.

## Open Questions

- The Wiki widget shows a page reference (`knowledge/document/<slug>`) of another workspace's Wiki only as its text, and InferOps widget kinds other than `project/board` and `project/issue-card` (for example `project/board-summary`, `project/my-issues`) as an unsupported reference. Whether InferOS should render those, and how a page reference resolves across Wikis, is open ([#87](https://github.com/factory-level/inferos/issues/87)).
- `modeForPath` counts the workspace's own canvas (`/workspace/$id/inferops-canvas`) as Operate for the shell's Build | Operate toggle, yet it is the one surface that offers coding dispatch (its viewers hold the workspace's build role, and it is not the Operate session). Whether the coding control should move to a Build-only surface once role consoles land ([#106](https://github.com/factory-level/inferos/pull/106)) is open.
- Choose ownership and persistence for shared canvas configuration; current InferOps pins are personal and cannot simply be widened.
- Decide whether the canonical InferOps widget client package can be safely adapted to Kumo and capability RPC or needs a thin host-specific renderer.
- Set measured payload, latency and memory budgets from representative device/network fixtures. Proposed starting budgets, not decisions, from the [baseline](#kanban-performance) (the local browser run compares against them, but they await owner agreement): a board payload to the browser of at most 256 KB (about 800 cards at the synthetic card size) before paging is required; at most one `readBoard()` per target per demand, whatever the number of cards (held by tests today); adapter-side work per landed read (decode, land, render prep) under 4 ms for 500 cards on a desktop-class CPU, so under 16 ms with a 4x CPU throttle; and, once a browser run exists, p95 board load under 1.5 s and p95 move-to-pending feedback under 100 ms on a mid-range laptop over a fast 4G profile. Long-task and memory budgets wait for that browser run.
- The board DTO has no paging: `readBoard()` returns every column and card of the project, and every refresh re-reads it whole. A proposal for InferOps (an upstream contract change, so a cross-repo decision under `BoardResponseSchema`): (1) a column page, `GET` board with `?limit=<n>&cursor=<opaque>` per state returning `columns[].{state, issues, nextCursor, total}`, so a card shows the first page of each column and its count; (2) a delta read, `?since=<board revision>` returning the changed and removed issue ids since an opaque board-level revision (a new `boardRevision` on the response, monotonic per project), falling back to a full read when the revision is too old. The gatekeeper would expose both as optional `readBoard({ limit, cursor, since })` arguments with the same capability scope, and the adapter would keep per-target pages and apply deltas under its existing `wanted`/`applied` clocks. Whether InferOps can provide a board-level revision cheaply is open.
- The browser run shows rendering, not reading, dominates a large board: 4 cards of a 500-issue board put about 1,700 issue cards and 21,000 elements in the DOM, with long tasks of 1 to 3.8 s at 4x CPU. Whether to window the card list (render only the visible cards of each column) or wait for upstream column paging is open.
- `useHasBeenOnScreen` observes against the viewport with a 200px margin, but cards live inside the canvas pane's scroll container, which clips the margin away, so a card reads only once it actually scrolls into the pane. Observing against the pane (an explicit `root`) would let a card read just before it is seen.

## Implemented guarded definition and edit engine

`@gadgets/workshop-shared/canvas` exports v1 definition, content, section, widget and operation types, `parseCanvasDefinition`, `applyCanvasOperations` and a revision-conflict error. The parser reconstructs detached objects, accepts only known fields and rejects unknown definition/widget versions. Three widgets are registered. `inferops.project-board` v1 has a canonical target reference, software/content workflow filter and explicit completed-card visibility; presentation filters do not authorize data. `inferos.gadget` v1 has a `gadget:<workpieceId>` reference to a gadget in the workspace that owns the definition and no parameters. That reference is resolved only through the owning workspace's already-authorized session, grants nothing, and is meaningless in another workspace. `inferops.wiki` v1 names one InferMind workspace's Wiki, `inferops://<tenant>.<workspace>/knowledge/wiki` (`CANVAS_WIKI_REF`), with one parameter, `page`: the slug of the page opened first (`CANVAS_WIKI_PAGE`, URL-unreserved characters) or null for the first page. Like a board reference it is resolved through a separately granted connection and is presentation only (see [InferMind Wiki widget](#infermind-wiki-widget)). No transaction DTO, credentials, ownership or sharing grants are embedded in portable content.

View, section and widget IDs occupy one unique namespace per definition. Titles are bounded plain text. Sections have one to three desktop columns; sizes are normal (one column), wide (up to two), or full (all available columns). The renderer must collapse layouts responsively. Structural limits are 12 sections, 48 total widgets and 32 operations per batch; these bound validation work and are not measured performance budgets.

Edits add/remove/move/configure sections or widgets, rename the view, or restore validated prior content. Move indices refer to the destination after removal. Every intermediate composition validates, and a failure returns no partially modified caller state. A successful batch advances one canonical decimal-string revision using BigInt; stale expected revisions return a conflict with the current revision. Restore keeps the view identity and advances revision; it never invokes or reverses InferOps transactions. An unchanged-content edit still consumes a revision.

This engine performs no storage, authorization or feature enforcement. Its result is suitable for preview. Before persisting, a server caller must check installation flags and workspace edit authority, resolve resource capabilities independently, and compare/write inside one storage transaction. A test of this pure engine is not evidence that concurrent durable writes are safe.

Bootstrap writes `views/operations.json` with the configured target reference. `views:check` runs the pinned validator, bounds file count/size, rejects links/executable files, duplicate view IDs and any widget other than a project board (gadget references are workspace-local, so a portable starter cannot carry one), and reports runtime readiness false. It does not load the InferOps fixture, connect a provider or publish a view. Supporting pins expose a builder Canvas page when composable views are enabled; importing the starter creates a new definition.

## Workspace-scoped definition storage

The existing Overseer durable object's typed storage now has a `canvases` collection. `WorkspaceCanvasStore` uses that collection and the object's synchronous transaction mechanism; it does not introduce a separate database or domain-data cache. Owner/build sessions expose list, get, create, edit and delete methods on the existing Overseer capability. The use-only surface denies create, edit and delete, covered by the exhaustive use-role suite; list and get return only the screens a console of the workspace shows (see [operate mode](operate-mode.md)), so a view no console shows lists as absent and reads as `null`. Unrelated users still fail the native workspace-open authorization, and IDs are resolved only inside the current workspace's collection.

Every storage operation requires deployment bindings `COMPOSABLE_VIEWS` and `DURABLE_VIEWS` to equal the string `true`. These are structural installation switches, separate from admin soft settings and rollout flags. Disabling either denies reads and mutations without deleting stored records. The consumer launcher maps the corresponding config flags to these bindings. Public server configuration exposes effective flags; the frontend hides the editor's Canvas button and the Canvas page explains that composition is disabled.

Creation accepts content only, mints a new UUID and starts at revision zero. It enforces 64 active definitions per workspace. Imports/recreation never reuse the deleted view's identity, avoiding stale-edit confusion. Edit and delete compare expected revisions in the same synchronous transaction as the write. Invalid edit batches leave persisted content unchanged. Delete removes only the definition; underlying InferOps data is untouched. Unknown stored schema versions fail validation rather than being silently rewritten.

Definitions inherit the native workspace build-access boundary; they do not yet have independent sharing controls. The existing sharing manager's session/revocation behavior remains authoritative. Reading a definition is not reading a referenced board: no target is resolved and no resource grant is created by this API. The renderer/data adapter separately obtains an authorized capability before loading any referenced data (see [Resolving a board reference](#resolving-a-board-reference)). Existing InferOps personal pins remain untouched.

## Resolving a board reference

A board card's `targetRef` is resolved to a capability through `Overseer.getGatekeeperByResourceUrl(resourceUrl)`, which returns the workspace's existing connection (a `GatekeeperClient`) for that resource or null. It is a lookup over the workspace's gatekeeper records, matched on the canonical URL the gatekeeper reported in its own `describe()` (`GatekeeperRecord.resourceUrl`), never on what the creator typed; the oldest match wins, and vendorless connections (models, spawners) have no URL and never match. The returned client's `openSession()` goes through `openGatekeeperSession`, the same chokepoint as a gadget binding or the agent, so reads are recorded as observations and transitions are submitted as actions attributed to the calling user.

The lookup mints nothing. A connection exists only because `newGatekeeper(accountId, resourceUrl)` created it from the creator's own connected account through `User.getGatekeeperClassFor`, where the InferOps gatekeeper resolves the reference's `<workspace>` slug among the creator's own InferOps workspaces, checks the account can open the project there, and the admin's disabled gatekeeper/resource lists are enforced. Board references use InferOps' own grammar, `inferops://<tenant>.<workspace>/project/board/<KEY>` (lowercase slugs; `inferops://demo.local/project/board/DEMO` is the demo data), never a deployment host ([ADR 0005](../adr/0005-inferops-uri-authority.md)); `canonicalBoardRef` lowercases the authority for cache keys and the lookup, while the gatekeeper accepts only the lowercase form when a connection is created. A collaborator holding a build session was verified against every such connection with their own account at `open()` (`addObserver`, strategy B for InferOps), and a connection added later restarts live sessions so they re-verify. So a canvas reference identifies a target but authorizes nothing: an unconnected reference yields null, which is the cue to offer the normal connection flow, and the method is denied to use-role collaborators like `getGatekeeperById`. A use-role operator resolves a console's board in their own operate session's workspace instead, through a connection made from their own InferOps account (see [operate mode](operate-mode.md#data-and-control-flow)); they never read through the workspace owner's connection. `packages/workshop-backend/__tests__/gatekeeper-lookup.test.ts` covers the oldest-match, canonical-URL, vendorless, blocked-pending-restart and use-role cases.

Real Workers/RPC tests cover concurrent revision conflicts, rollback, scope isolation, build/use roles, quota and recreation identity. A harness configuration update reloads Workers with durable views disabled, proves access is denied, then reenables them and reads the original definition. This demonstrates Worker-reload retention, not a cloud rollout, OS crash recovery, schema migration or completed consumer view experience.

The release slice of #34 (one private Kanban/Operate view with a live reference) has its own end-to-end test in `packages/integration-tests/__tests__/workshop-canvas.test.ts`. A view whose board card targets `inferops://demo.local/project/board/DEMO` is created and edited; an edit or delete at the replaced revision is rejected with the `Canvas changed` conflict and the stored definition is unchanged; two connections of the same owner editing the same revision produce exactly one winner and one conflict. Another account cannot open the workspace, and its own workspace neither lists nor reads the view and reports `not found` on edit. A collaborator added with the `use` role opens the workspace, lists and reads no view while no console shows it, and gets `Unauthorized` on edit and delete. The owner's Operate session opens the view, then the Workshop Worker is restarted through a harness configuration update (a pre-restart connection is shown to drop). Afterwards the definition, its revision and its board reference read back unchanged, the Operate session's working set and focus still hold the view and resolve to it, the use-role denial and the stale-revision conflict still apply, and an edit at the current revision advances it. Like the reload test above, this is local Worker-restart evidence, not a cloud deployment or OS crash recovery claim, and it reads no board data.

## Canvas page and builder composition UI

`/workspace/$id/inferops-canvas` is a fullscreen page (the root already treats every `/workspace/` path as chrome-free). It opens the workspace through the same `useWorkspaceOpen` flow as the editor, so share keys, observer confirmation and open failures behave identically, and use-only collaborators are redirected to the editor route, which shows them only the deployed gadget UI. The workspace's chat runs in a resizable left column (`ChatInterface`, with the remembered width shared with the editor) and the canvas fills the rest; on narrow screens a Chat/Canvas toggle shows one at a time. Chat selection lives in the `chat` search parameter. Opening a gadget from chat navigates to the editor with that gadget selected. The editor's InferOps Canvas button navigates to this page. The selected view lives in the `view` search parameter, so a screen can be linked to directly.

Outside edit mode the active view renders read-only. Sections are size containers, so column counts follow the canvas pane's width rather than the viewport: two- and three-column sections collapse to one column below 48rem, and three-column sections show two columns until 64rem. Gadget widgets resolve their reference against the live workpiece list and open a `GadgetClient` through the workspace's `Overseer` (`getGadget`), disposing it when the widget goes away. They then render through the existing sandboxed `GadgetUI` host, keyed by the gadget's head commit so an accepted change reloads it. A widget does not load its bundle until it has been within 200px of the screen. Missing gadgets and drafts that are still pending in a conversation are never opened; each shows an explanatory state instead. Board widgets render the Kanban board the board data adapter holds for them, or its loading, not connected or error state (see [Kanban board](#kanban-board)). A board card's **Open** button opens its full view: the `widget` search parameter names the widget, the pane shows only that board with a **Back** button, and the widget is cleared from the URL when the view changes or no longer holds it. In edit mode a board card shows only its reference.

Edit mode uses Kumo controls and the shared guarded operation engine. Sections can be renamed. Each section adds a board by reference or an accepted gadget from a picker. A separate move form selects a widget and destination section, appends it there, and returns focus to the source selector. This avoids removing the focused control along with a moved card. Existing upward ordering and undo can refine or reverse the move. It supports temporary in-memory views or saved definitions through the existing Overseer capability. Temporary views are labelled unsaved and last only while the page stays open. Saved changes compare revisions; rejected writes retain the displayed snapshot and offer an explicit reload. Undo restores prior content with a new revision and retains up to 20 session-local snapshots per view. Import validates bounded JSON and sends only content, so stored identities and workspace authority are never imported.

Async responses from an earlier workspace are ignored. A slow file read cannot initiate a create against a workspace that has since been left. Layout controls do not load or mutate domain records or gadget code. Gadget console logs in chat, individual sharing and performance benchmarks remain follow-up work.

Export revalidates the active definition and uses the existing browser file-download helper. The JSON contains only the strict portable schema, including required resource references. It contains no ownership, grants, credentials or transactional rows. The filename uses the validated view ID rather than the display title. Import preserves section/widget identities within the new composition but creates a fresh view ID and revision zero; it never carries authority from the source workspace. Exporting a temporary view is allowed, and does not implicitly save it to the server. Exported views that contain gadget widgets are rejected by the consumer starter validator, because gadget references are workspace-local.

## Composition catalog

`CanvasCatalog` (in `@gadgets/workshop-shared/canvas`) is what an installation offers for composition: the widget kinds people and agents may add, blueprints offered as widgets (instantiated as gadgets, placed as `inferos.gadget`), and screen templates new canvases may start from. Templates hold layout and `inferops.project-board` and `inferops.wiki` references only, since gadget IDs are workspace-local; `parseCanvasCatalog` reuses the definition parser, so IDs, limits and widget rules match saved canvases exactly.

The deployer sets it through the `CANVAS_CATALOG` JSON binding. `readCanvasCatalog` (`canvas-catalog.ts`) treats an unset binding as every registered kind with no blueprints or templates, and a malformed one as an empty catalog, logged at `error`: a catalog only ever narrows composition, so failing closed loses nothing it could grant. `getServerConfig` publishes it as `canvasFeatures.catalog`.

`applyCanvasOperations` takes an optional `allowedKinds`. Every widget an add, configure, add-section or restore brings in must be of an allowed kind; widgets already on the canvas are left alone, so narrowing the catalog never strands a composition. `WorkspaceCanvasStore` passes the catalog's kinds to every edit and checks created content the same way, so the builder UI and the agent are held to one rule.

The catalog grants nothing. It does not resolve a board reference or bind a gadget to a resource, and enabling a kind is not permission to read the data it shows.

## Agent canvas tools

When durable views are enabled the chat agent has two tools, `listCanvases` and `editCanvas`, which reach the workspace's canvases through the `AgentHooks.getCanvasAccess` hook. That hook returns the same `WorkspaceCanvasStore` paths the builder UI uses, so the agent's edits obey the same revision checks, limits and catalog. With durable views off the tools are not offered at all, and spawned sub-agents never get them.

The `editCanvas` description lists every widget kind with its reference grammar and params, including `inferops.wiki` and that a page's embedded references show live only where the workspace holds their own connection. `listCanvases` returns each canvas's layout and revision plus the catalog (kinds, blueprint widgets, template titles). `editCanvas` creates a canvas (optionally from a template) or applies a batch of the engine's own operations against an expected revision; a stale revision returns the current one so the agent re-lists before retrying. Edits apply when the call runs rather than riding the chat's proposed changes: a canvas holds references and layout, not code or domain data, and the builder UI applies the same edits immediately. Replay returns the recorded output and never re-applies an edit.

A blueprint widget such as the InferOps Kanban board is placed in three steps the tool description spells out: `createGadget` from the blueprint, wire the binding its notes describe (requesting the connection first), then add it with `editCanvas` as an `inferos.gadget` widget. A gadget created in the chat renders on the canvas once the user accepts the chat's changes.

## Canvas configuration CLI

`scripts/consumer/canvas.ts` configures composition before any custom code is written, in this repository (`pnpm canvas <command>`) or in a consumer wrapper (`pnpm canvas <command>`, through the wrapper runtime). It reads and writes `inferos.canvas.json` at that root: enabled widget kinds, blueprint widgets, screen templates, and which `custom-gatekeepers/` packages run. `list` shows what the checkout builds beside what is enabled; `enable`/`disable`, `add-screen`/`remove-screen` and `gatekeeper enable|disable|all` edit the file, re-validating before every write so the CLI never writes a configuration the Workshop would reject. Names the checkout does not build are errors rather than being dropped, and a blueprint widget requires the gadget kind it is placed as. `customGatekeepers: "all"` (the default, also used with no file) selects every custom gatekeeper whose `connection.json`, if it has one, says `reference` or `production`: a `scaffold` or `conformant` package (`gatekeeper-tickets`) appears in `list` under `available.unreleasedGatekeepers` and runs only when named with `gatekeeper enable`, which also expands `"all"` to that released set before adding it.

`pnpm dev-server` (and `run-local`) reads the same file — from `--consumer-root`, or this checkout's root — and passes the resolved catalog as `CANVAS_CATALOG` and binds only the selected custom gatekeepers. In-repo there is no `inferos.config.json` to carry feature flags, so the presence of `inferos.canvas.json` turns composable and durable views on; a wrapper's own flags always take precedence.

## First-class InferOps Canvas page

When composable views are enabled the sidebar shows **InferOps Canvas**, linking to `/inferops-canvas`. That page lists saved screens across the user's most recently active build workspaces (at most 24): screens are stored per workspace, so it opens each workspace once with a pipelined `openGadget(id).listCanvases()` and disposes the stub right away. A workspace that needs observer setup before it can be opened is listed without its screens. The page also creates a screen in a chosen workspace, blank or from a catalog template, and opens it.

On a workspace's page the pane offers only the catalog's widget kinds. Catalog blueprint widgets appear as buttons that start a new chat (with the user's last-chosen model) asking the agent to build and place that widget, since doing so means creating a gadget and wiring a connection. Saved views are re-read every five seconds while the page is visible and no operation is in flight, and again as soon as a hidden page is shown, so the agent's edits show up without a reload. A board reference card shows the board through the board data adapter when the workspace has a connection for it, and says it is not connected otherwise; in edit mode it shows only the reference.

## Board data adapter

`features/canvas/boardData.ts` is the adapter every board-shaped card shares; `useBoardData.ts` serves it to React. One `BoardData` instance serves one scope, the user's capability on one workspace (its `Overseer` stub): the hook holds one per stub with a reference count and disposes it, sessions included, when the scope's last card unmounts, so a reopened session or another workspace starts empty and nothing read in one scope is shown in another. Within a scope, entries are keyed by the canonical widget request: kind, version, the canonical target (`inferops://` host lowercased, as the gatekeeper describes it) and the normalized params. Params are presentation only (`visibleColumns` filters the whole board by workflow and completed visibility at render), so every card of one board shares its reads whatever their params.

A target is resolved through `Overseer.getGatekeeperByResourceUrl` and the returned client's `openSession()`, pipelined and disposed; the session is cached per target and forgotten after any failed read so the next read resolves the connection again. A null lookup is the `unbound` state (the reference is not covered by any connection in this workspace); the card says so and offers nothing, since connecting is the normal connection flow. The adapter never mints a connection and never selects one from the URI. The session types are imported type-only from the gatekeeper's own `src/types.d.ts` (a workspace dev dependency), not copied.

Reads are independent `readBoard()` calls; there is no batching. A card that subscribes while another card of the same target shows it `ready` (the last read landed and nothing newer was asked for) takes that board and its pending moves and changes without a read, so a card deferred while offscreen costs nothing when it scrolls in; while that card is `stale` the newcomer joins the pending read, and after a failed or no read it reads. In-flight reads are coalesced per target, at most four run at once per scope, a queued read nobody subscribes to any more is dropped before it starts, and an in-flight result for a card that left is discarded. Two clocks per target order results: a demand for fresher data (a refresh, a submitted move, a decided action) stamps `wanted`, and a read started earlier cannot satisfy it; `applied` records the read on screen, and an older read never lands over it. A refresh keeps the last good board visible as `stale`; a failed refresh keeps it with the error, while a revoked connection (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, or the connection removed) drops it. A `DISABLED` failure (the deployment has InferOps turned off, `INFEROPS_ENABLED`; see [InferOps gatekeeper](inferops-gatekeeper.md#integration-switch)) is its own `disabled` state: the board is dropped, the connection is not treated as revoked, and the next successful read after InferOps is turned back on shows the board again.

`move(request, issueId, toStateId, expectedRevision)` proposes a transition through `openIssue(id).transition(...)`, the gatekeeper's approval path, with the decimal-string revision the card read. The move is listed as pending on every card of the board, `proposing` until the call returns and `awaiting` once it is queued; a second move of the same issue is refused locally as `CONFLICT`, as the gatekeeper would. The board is re-read whether the call succeeded or failed. A pending move stays while the authoritative board still shows it undecided, that is, the gatekeeper's simulation of the issue in the target state at the unchanged revision; it is dropped once the revision differs or the issue is back in its state. The adapter only says the board stopped showing it pending; how it ended is the action log's to say (see [Kanban board](#kanban-board)). The adapter never edits the board itself.

`create(request, issue)` proposes a new issue through the session's `createIssue` (the board UI always passes the column's `stateId`), and `update(request, issueId, changes, expectedRevision)` an edit through `openIssue(id).update(...)` with the revision the card read; both go through the same submit path as `move()` (session lookup, `NOT_CONNECTED` when no connection covers the board any more, the gatekeeper's code and message on refusal, a re-read either way) and return the same `ProposalResult`. Each is listed in the state's `changes` as a `PendingChange`, `proposing` until the call returns and `awaiting` once it is queued. Unlike a move, an awaiting create or edit is held only until the next read lands: only reads started after it was queued can land, and the gatekeeper's reads overlay it themselves (`Issue.pending` `create`, a provisional card with id `pending-<action id>`; `update`, the new title and priority at the unchanged revision), so from then on the board, not the adapter, says it is pending and how it was decided. `move()` and `update()` refuse locally, without calling the gatekeeper, an issue the board marks pending or that has a local pending move or edit (`CONFLICT`, as the gatekeeper would) and a provisional card (`PENDING_CREATE`, since `openIssue` does not accept its id). `CanvasView` listens to the workspace's action log through the existing `useActionEntries` store and invalidates a board when an action on its connection leaves `pending`, so an approval or rejection by anyone re-reads it.

`CanvasBoardWidget` renders a live board in one of two presentations (below); `CanvasBoardSummary` shows only the reference, for edit mode. Nothing polls on visibility. `boardData.test.ts` covers duplicate cards sharing one read, unbound and retried references, canonical keys, partial failure and revocation, InferOps turned off and back on, stale responses in both orders, concurrency and cancellation, scope isolation and disposal, pending moves through decision, refused moves, creates and edits through queueing and the overlaying read, local refusal of changes to pending and provisional issues, stale edits and presentation filtering, and (with the development read metrics) duplicate cards counted as one read, no read for a card that left, a superseded stale response, one re-read per invalidated target, coalesced invalidations under saturation, a late card served from the card showing the board (pending move included) without a read, and a late card joining a pending re-read or reading after a failure; `CanvasView.test.tsx` covers the live card, session release, action-log invalidation, offscreen board cards reading nothing until they come into view (duplicates still sharing one read) and a card that scrolled away staying subscribed. `useDecidedActionInvalidation` (in `useBoardData.ts`) is the action-log listener, called by every presentation that shows boards of a scope; the underlying `useActionEntries` store is reference-counted, so the view and the full view share one subscription.

## Kanban board

`CanvasBoardWidget` is one board reference shown live. Its props are a discriminated union on `presentation`: `card` (in a view's grid cell, with an optional `onOpen` for the full view) or `full` (the widget on its own, in `CanvasBoardFullView`). A card subscribes to its board, and looks up its coding-dispatch reference, only once it first comes near the screen (`useHasBeenOnScreen`, the same latch gadget cards use); until its board is loaded it holds an embedded board's height (32rem), so cards further down are not all near the screen as short loaders. The full view always reads. Both read through `useBoardData` with the widget's request, so the card and the full view of one reference are one adapter entry and one read, and a move proposed in either is pending in both. The frame shows the project name and key, the reference, a **Refreshing** or **Refresh failed** badge while the adapter holds a stale board, a count of moves pending approval, a refresh button, and the body for the adapter's state: a loader while loading, a *not connected* note for an unbound reference (the cue to connect through the normal flow, never a connect action), a `role="status"` note that InferOps is turned off for this deployment (and that the connection is kept) for the `disabled` state, an alert with **Try again** for an error, the last board with the refresh error for a failed refresh, and an empty note when the card's params leave no columns. `visibleColumns` applies the card's workflow and completed-visibility params to the whole board at render.

`KanbanBoard` renders the given columns, each a labelled section with a heading, a count and a list of `KanbanCard`s sorted by priority then identifier (`kanbanBoard.ts` holds the pure rules). A card shows the identifier, a priority badge, the title, the assignee id (truncated, full id as its title) when set, the target date with an overdue mark for open issues, and the blocked reason. Layout is a prop: `embedded` gives fixed-width columns that scroll sideways within the card's cell, capped in height with per-column scrolling, and `full` gives columns that share the pane's width and height. Kumo tokens and components only; no custom colors.

Moves go through the adapter's `move()` only, with the issue id, the target state and the revision the card read. Three inputs reach it: a card's **Move to** menu (`DropdownMenu`) listing the issue's targets, the keyboard (the card is focusable; left and right arrows choose a target, shown on the card, Enter proposes it, Escape cancels), and pointer drag and drop onto a column, which the board accepts only for an allowed target (same workflow, not the issue's own state, taken from the whole board so a target the card's params hide is still offered; the issue then leaves the card's columns). A card with a pending move offers none of the three until it is decided, matching the gatekeeper's one-move-at-a-time rule.

A card stays where the authoritative board places it and shows its pending move as a badge: *Proposing move to* while the transition call is in flight, *Awaiting approval* once queued; the re-read after the call shows the gatekeeper's simulation, which places the issue in its target column at its unchanged revision. When the board stops showing a move pending, its outcome is taken from the action log, never from the board (see the decisions paragraph below): a rejected move is marked *rejected* until the issue changes again, an applied one is marked for six seconds. Every outcome, including a refused proposal (a `STALE_REVISION` tells the user the board was re-read), is announced through a visually hidden `role="status"` live region, and the keyboard instructions are a hidden paragraph every card describes itself by. The board remembers which card has focus and restores it after the card re-mounts in another column; focus that left the board is left alone.

Each column header has a **New issue** button (`aria-label` *New issue in Todo*) and each card that can be edited an **Edit** button (*Edit ENG-12*); both open `KanbanIssueDialog`, a Kumo `Dialog` holding a form with a required title, a description and a priority (`Select`). Selects in these dialogs use Kumo's default portal, which Base UI nests inside the open dialog's own portal, the only subtree the modal dialog leaves visible to assistive tech; `styles.css` raises their positioner (`z-index: 1100`) above the dialog layers. The dialog's own trigger is the control, so Kumo returns focus to it when the dialog closes, and the form is mounted only while open, so every opening starts from the board's current values. A new issue is proposed in the column's state; columns are whatever states the board returns, and no workflow is assumed. The edit form starts from the card's title and priority and sends only the fields that changed (`changedFields`): the title when its trimmed value differs, the priority when it differs, and the description only when one was entered, because the board DTO does not carry the current description (the field says that leaving it empty keeps it). Submitting with nothing changed is disabled. While the proposal is sent the form is disabled and says *Proposing…*; a refusal keeps it open with the reason in an alert, the gatekeeper's message (a workflow-policy `FORBIDDEN`, `CONFLICT`, `INVALID_STATE`, `DISABLED` and so on) except `STALE_REVISION`, which reads *This issue changed; refresh and try again.* (the board is re-read either way, and reopening the form starts from the new values); a queued proposal closes it and is announced as waiting for approval.

A card shows one pending badge, most specific first: its own move (*Proposing move to* / *Awaiting approval*), its own edit while the call is in flight (*Proposing edit…*), a provisional card (*New issue, waiting for approval*, with a dashed border and *(not created yet)* in its accessible name), an awaiting action from the log (*Awaiting approval (Agent): …*), then the gatekeeper's markers (*Edit waiting for approval*, *Move waiting for approval*), which also cover changes requested elsewhere that the log does not tie to the card. Anything pending withholds the edit button, the move menu, keyboard moves and dragging (a drag that starts anyway is cancelled), so a provisional card can no longer be dragged into a move that fails `NOT_FOUND`. Provisional cards sort after the column's existing issues. **Decisions come from the action log.** `advanceDecisions` (`kanbanBoard.ts`) tracks what the board shows waiting for approval (`trackedChanges`: this board's own awaiting move or the gatekeeper's `transition` marker, an `update` marker, a provisional card; at most one per issue). When the board stops showing one, it is decided only once its action's record in the log is decided, and the outcome is that record's: `approved` is applied, `rejected` is rejected. `KanbanBoard` receives the board's decided actions as `decided` (`BoardActivity.decided`) and matches them on the issue identifier (the action's inline `Issue` field) or, for a new issue, on its title (the inline `Title` of an action that names no issue). The board's revision is never read as an outcome: an outside edit in InferOps moves it too, and the gatekeeper stops overlaying a change made stale while its action stays pending, as does an approval whose apply failed. A drop with no decision yet waits for one, a decision that lands before the drop is held for it, decisions the log held when the board mounted are history, and decisions for changes the board never showed pending are ignored. Edits are marked *Edit applied* (six seconds) or *Edit rejected* on the card. All outcomes are announced in the polite region, whoever proposed them.

`kanbanBoard.test.ts` covers `advanceDecisions` (a dropped edit at a new revision decided only by the log's rejection, early decisions, history and untracked issues, creates by title). `KanbanBoard.test.tsx` covers rendering, the three move paths, pending and decided display, announcements (including a denied edit announced as rejected though an outside edit moved the revision), focus retention, the two layouts, creating in a column's state, edits sending only changed fields, stale-revision and refusal messages, provisional and pending-edit cards withholding their controls, and announced create and edit decisions; `CanvasBoardWidget.test.tsx` covers the adapter states (including the turned-off note and recovery), the ids and revision a keyboard move sends, the card and full view sharing one read, a create and an edit end to end through the session, waiting for approval and applied after a decided action re-reads the board, a create through approval (#59) shown as a provisional card while its action is pending and announced from the action log as created, or as rejected for a denied one, an issue deleted in InferOps while its form is open (#63) closing the form with "no longer on this board" and the way back, and a pending edit across a reconnect (#63: a new `Overseer` stub whose log replays the pending action) still shown as awaiting approval with no outcome announced and nothing re-sent, then announced as rejected once the log says so; `CanvasWorkspacePane.test.tsx` covers opening and closing the full view. Chat shows no board of its own: on the InferOps Canvas page the chat sits beside the canvas pane, and a move's approval is decided in the chat's action list. Large boards are not paged and nothing polls on visibility; see [Kanban performance](#kanban-performance) for what is measured.

## Kanban performance

Tracking issue [#28](https://github.com/factory-level/inferos/issues/28). Instrumentation, an adapter-side baseline and a local browser run against the mock gatekeeper exist; nothing has been measured against a live InferOps, and no budget is agreed (proposals are under [Open Questions](#open-questions), compared below).

**Read metrics.** `features/canvas/boardMetrics.ts` is an optional recorder `BoardData` takes as `metrics`. Per `readBoard()` it records the duration from read start (including the session lookup of a first read) to the result, the UTF-8 byte length of the result as JSON, and the outcome: `applied`, `unbound`, `superseded` (lost to a newer read, or no card left to show it) or `failed`. It also counts reads started and *shared demands* (a card served by an existing entry, or a demand joined to a queued or in-flight read). Snapshots give the counts, nearest-rank p50/p95 latency and last/max payload over the last 200 reads. Nothing about a board is kept: no target, content or identity. `useBoardData` creates one per scope only when `import.meta.env.DEV`, and exposes them as `window.__inferosBoardMetrics()` in development builds; production adapters have none and pay nothing. Sizing a payload serializes it, so metrics roughly double the adapter's per-read cost on large boards (below).

**What the tests prove** (`boardData.test.ts`, `CanvasView.test.tsx`): duplicate cards of one target, whatever their params, share one read; a queued read for a card that left is never started, and an invalidation does not re-read a target with no cards; an older response never lands over a newer one; an invalidation re-reads each target exactly once whatever its number of cards, reusing the cached session; repeated invalidations while reads are saturated (four per scope) coalesce into one queued read; a board card reads nothing until it first comes near the screen, and a card arriving after another card of the board loaded takes that board without a read.

**Offscreen cards.** A board card subscribes only once `useHasBeenOnScreen` reports it near the screen, and then stays subscribed, also after it scrolls away; it is not unsubscribed when far away. Re-subscribing on each scroll back would cost a whole-board read every time (there is no paging or delta read), and a card that drops back to loading would unmount its Kanban, losing the decision tracking (`advanceDecisions`) and announcements of proposals still pending; a subscribed offscreen card costs nothing until its board is invalidated, and that re-read is shared with every other card of the target. Pending proposals are held per target in the adapter, so they reach a card whenever it subscribes. The full view always reads. Cards render nothing of the board until then; rendering, not reading, is the larger cost of a large board (below). The adapter does not poll, so there is no stale polling to clobber an edit; refreshes are event-driven and ordered by the `wanted`/`applied` clocks.

## Action attribution

Every workspace action log entry (`ActionLogEntry`, from `listActions` and `subscribeToActions`) carries an optional `requestedBy`: `agent`, `person`, `gadget` or `hook`, mapped in `actionRecordToLog` from the kind of the stored record's `caller` (`user` becomes `person`). It is the groundwork for agent activity and approval displays. It is a display label only: no decision reads it, and the caller's chat id, gadget id and identity stay on the server. Records persisted before callers were tracked have no `caller`, so their entries omit the field. `workshop-agent-actions.test.ts` checks that an agent's writes report `agent`, and `workshop-action-history.test.ts` that writes and reads through the owner's own connection session report `person`. The canvas board activity line (see [Board activity](#board-activity)) and the operate session's approvals show it, the latter as *Requested by the agent*, *a person*, *a gadget* or *a hook* (see [Operate session page](#operate-session-page)).

## Board activity

`boardActivity.ts` folds action log entries into one board's activity. Only entries whose `resourceUrl` is the board, after the same `canonicalBoardRef` the adapter keys on, count; entries for other resources, with no resource, or for hooks are ignored, and a later record with the same id replaces an earlier one. An observation is a *read*, a pending action is *awaiting approval*, and an approved or rejected action is *applied* or *rejected*. Awaiting actions are active until decided; the others are recent, dated by `actionChangeTime`, and fade two minutes later (`RECENT_ACTIVITY_MS`), at most five kept (`RECENT_ACTIVITY_LIMIT`). Each item carries the `requestedBy` label (`Agent`, `Person`, `Gadget`, `Automation`, or none for older records; a person is not necessarily the viewer) and only the one-line title the gatekeeper rendered for humans, never the description, fields or payload. An awaiting action's issue is the whole (untruncated) inline `Issue` field of its description, which the InferOps gatekeeper's `transition` and `update` write, and an action naming no issue carries the whole inline `Title` as `creates` (the gatekeeper's `createIssue`); both are used for matching only. Besides the capped `recent` list, `decided` holds every applied or rejected action the log holds for the board, oldest first and unfaded, for the board's decision announcements.

`useBoardActivity(overseer, targetRef, connected)` reads the scope's log through the shared, reference-counted action store: `useActionEntries` for live entries (replayed on mount) and `useActions` for actions already pending when the session opened, which the store pages rather than streams. Entries are held with the `Overseer` stub they arrived on and ignored for any other, so a card moved to another workspace or a reopened session never shows the previous scope's log. A timer re-renders when a recent item turns a minute old or fades.

`CanvasBoardWidget` passes `connected` as whether the adapter holds a board: once the connection is revoked or the board cannot be read (`error`, `unbound`, or loading), nothing shows as awaiting, so a pending action never looks active on a board that can no longer show its outcome. `BoardActivityLine`, below the header, shows a Kumo status badge, the label, the title and the age: the card shows the newest awaiting action (else the newest recent item) with a *+N more* count, the full view lists them all. A visually hidden, always-mounted polite live region announces the newest awaiting action only, so repeated reads stay silent. `KanbanBoard` takes the awaiting actions by issue identifier and marks the matching card *Awaiting approval (Agent): Move ENG-12 to Done*, offering no move on it, as the gatekeeper refuses a second; a move the board proposed itself keeps its own *Proposing* / *Awaiting approval* badge.

`boardActivity.test.ts` covers ordering, active to decided, fading and the cap, the disconnected fold, resource filtering, attribution labels, title-only output and issue linking; `useBoardActivity.test.tsx` covers scope isolation between two `Overseer` stubs, pending pages, the disconnected state and timed fading; `CanvasBoardWidget.test.tsx` covers the header line, the announcement, the card badge and clearing on a revoked connection.

## Coding control surface

A board's issues can be handed to the local coding runner from the Kanban ([#72](https://github.com/factory-level/inferos/issues/72)), through the project's **coding-dispatch** connection (`inferops://<tenant>.<workspace>/project/dispatch/<KEY>`, a separate grant from the board's; see [local coding workflows](local-coding-workflows.md)). Nothing about the board authorizes it.

- **Who offers it.** `codingDispatch` is an opt-in prop on `CanvasWorkspacePane`, `CanvasView`, `CanvasBoardFullView` and `CanvasBoardWidget`. Only `InferOpsCanvasPage` (the workspace's own canvas, which sends use-only collaborators away) passes it. The Operate session's `SessionScreen` and a flow's `FlowScreen` never do, so on those surfaces the dispatch reference is never looked up and no control is rendered: code is not edited from Operate.
- **Resolving it.** With the prop, `CanvasBoardWidget` derives the project's dispatch reference from the board reference (`dispatchRefOf` in `codingRuns.ts`) and `useCodingDispatch` reads it through `CodingDispatchData` (`codingDispatch.ts`), which resolves it exactly as the board adapter resolves a board: `Overseer.getGatekeeperByResourceUrl`, then `openSession()`. No connection means state `unavailable`, and the board then gets no `coding` prop: no button, no badge, nothing disabled. A connection removed later goes back to `unavailable`. `DISABLED` (the deployment's `CODING_WORKBENCH_ENABLED` off) is its own state, and so is a read error.
- **Reads and following.** One read lists the repositories and the runs; later automatic re-reads list only runs, since each read is an observation in the action log. While a run is queued or running, or a dispatch or cancel of one awaits approval, the runs are re-read after 10, 20 and 40 seconds and then every 60 seconds, for at most 60 re-reads (`FOLLOW_DELAYS_MS`, `FOLLOW_LIMIT`). Re-reads stop once nothing is in flight, after a failed read, or at the limit, which the dialog says (*Stopped checking for updates automatically*). A refresh restarts them, from the dialog's **Refresh runs**, the board's **Refresh board**, or any action on the dispatch reference leaving `pending` in the action log (`useActionEntries`). Requests made during a read coalesce into one more read. The instance is disposed, with its session, when the card unmounts.
- **Card.** `KanbanBoard` passes each card its issue's newest run (`latestRunOf`; the gatekeeper lists dispatches awaiting approval first). The card shows it as a Kumo badge (`CodingRunBadge`): *Dispatch awaiting approval*, *Coding queued*, *Coding running*, *Coding succeeded*, *Coding blocked* (a failed run with `reasonCode` `AUTH_BLOCKED` or `QUOTA_BLOCKED`), *Tests failed* (`TESTS_FAILED`), *Coding failed*, *Coding cancelled* or *Coding outcome unknown*, plus *Cancel awaiting approval* while one is pending. A software issue that exists (not a provisional create) gets a **Coding task** button (*Coding task for ENG-12*); a pending move or edit does not withhold it. When a run the board saw active finishes, the board announces it in its polite status region (`finishedRuns`, `describeRun`).
- **Dialog.** The button opens `KanbanIssueDialog` in `code` mode, which renders `KanbanCodingForm`. It shows the latest run (`CodingRunDetails`): repository and base ref, what a queued, unknown or blocked run means, the run's error, and once finished the patch path with files and `+`/`−` lines, the test pass and fail counts with the artifacts directory, each test command with its exit code, timeout, duration and its `stdout`, `stderr` and `record` paths, the test summary when there is no per-command detail, and the runner's own summary, labelled as not evidence. An active run can be cancelled (**Propose cancel**). With no active run and no dispatch awaiting approval, a **Repository** `Select` offers only repositories that are `allowed && enabled`; the others are listed with why (*disabled in InferOps*, *not on this deployment's coding allowlist*), and with none selectable the form is replaced by an explanation. Only software issues can be dispatched.
- **Honest states.** **Propose dispatch** sends `dispatch(issueKey, {repoId}, revision)` with the revision the card read. The dialog's polite status says *Proposing…* while the call is in flight, then *awaiting approval* (from the provisional run, the action log, or the queued call until either arrives), then *approved: InferOps queued the run* or *was rejected; nothing was queued* from the decided dispatch action in the log (`BoardActivityItem.tag` `inferops.code-dispatch`, only actions newer than the proposal). The run's own state, re-read from InferOps, says what happened after. A refusal is an alert and never shows as queued: `FORBIDDEN` (the repository is not allowlisted), `RUN_ACTIVE`, `STALE_REVISION` and `DISABLED` each get their own text (`codingErrorText`). An apply failure (for example a missing `issue:delegate`) leaves the action pending, so the dialog keeps saying it awaits approval, and the approval itself says why. The dialog stays open after a proposal, since it also follows the run.
- **Activity.** The board's activity line also shows the dispatch reference's actions (`combineActivity` with `actionsOnly`, which leaves out its reads, re-read automatically as they are), so a dispatch or cancel awaiting approval is announced like a move. Only the board's own awaiting actions lock a card's move and edit controls.

`codingRuns.test.ts` covers the run phases (blocked, tests failed, awaiting approval), following and cancelling rules, the newest run per issue, finished runs, the repository picker rules, the dispatch reference and a refused cancel; `codingDispatch.test.ts` covers no connection, the follow limit and refresh, coalescing, stopping after a failed read and disposal; `CanvasBoardCoding.test.tsx` covers no control without a connection or without the prop (the dispatch reference never looked up), dispatch through proposing, awaiting approval and applied, the `FORBIDDEN`, `RUN_ACTIVE`, stale-revision and `DISABLED` messages, the turned-off state, every run state on the card and in the dialog, a succeeded run's patch, tests and artifacts, a run that failed its tests, cancel through approval with its announcement, following on a backoff until the run finishes, content issues and the repository choice; `OperateCoding.test.tsx` renders a session screen and a flow step over a workspace that holds both connections and finds the board with no coding control and no lookup of the dispatch reference; `boardActivity.test.ts` covers the action kind tag and the combined line.

## Workspace kind

Each workspace stores an explicit kind, `WorkspaceKind` in `workshop-shared/src/api.ts`: `app`, `widget` or `workflow`. It records how the workspace is meant to run and where Operate mode (the InferOps Canvas) presents it. An app opens full-screen with a chat/app toggle. A widget is a tile on canvas screens. A workflow has no UI and runs on timed (scheduler) or event (hook) triggers.

The kind is deterministic. The Overseer's `kind` singleton changes only through `Overseer.setKind()`, which is build-role only (the use-role capability denies it). Nothing infers it from the workspace's code. Workspaces stored before kinds existed read the default `app`. The Overseer sends the kind in `getMetadata()` and `subscribeToMetadata()` to both roles, because it decides how a use-role viewer is shown the workspace. `setKind` also mirrors the kind into the owner's workspace list (`User.updateKind`), so `listGadgets()` can group workspaces by kind without opening each one. Older list records have no `kind`, which also means `app`.

The kind decides what the workspace builds, through three pure functions in `workshop-shared/src/workspace-kind.ts` that the kernel, the agent and the UI share:

- `workspaceKindContract(kind)` is the kind's rules as a section of the builder agent's system prompt. It goes in the project-specific slot, so the cached static slot is unchanged. An app has no contract: it is what the agent builds by default.
- `workspaceKindStarter(kind)` is the files a new gadget starts from. The agent's `createGadget` copies them in when no blueprint is given, as one change that rides the chat's proposed changes like a blueprint copy, and reports them as `starterNotes`. A widget starts from `client.js` and `server.js`; a workflow from `server.js` with a `run(input)` method. An app starts empty, as before.
- `checkWorkspaceKind(kind, filenames)` returns how a gadget's files fail to fit the kind: an app or widget with no `client.js`, a widget or workflow with no `server.js`, a workflow with a `client.js`. Nothing in the kernel calls it yet; it is there for the UI.

The agent's `writeFile` and `editFile` refuse `client.js` in a workflow workspace's gadgets (`workspaceKindAllowsFile`), so a workflow cannot gain a UI through the agent. Worktrees are exempt. The agent reads the kind once per turn through the `getWorkspaceKind` hook.

`AuthenticatedApi.newGadget(kind?)` creates a workspace of a kind, storing it before the workspace is returned. `newGadgetFromBlueprint()` does not take or carry a kind, so a workspace installed from a blueprint is an app until switched.

Behind the `operate-mode` UI flag (on in local development; also requires composable views), the frontend acts on the kind. The Build home page shows a kind picker (App, Widget, Workflow) above the composer. It is a Kumo `Radio.Group` of cards, so the keyboard pattern comes from Kumo: one tab stop on the chosen kind, arrow keys move to and select a neighbour and wrap at the ends, and Home/End do nothing (Kumo's radio group disables them, as the WAI-ARIA radio pattern does not define them). The chosen kind is set on the new workspace in the same batch as its first chat, ahead of it, so that chat's agent builds that kind. The workspace editor header shows a kind switch, with a confirmation step, for the build role. Apps get a Chat ↔ App toggle. Workflows replace the app preview with a Triggers panel listing their bound hooks (scheduled tasks register as hooks) and the pending-approval count. The workspace list shows a kind chip. The Build sidebar gains a Build | Operate toggle whose mode is derived from the URL: the InferOps Canvas routes are Operate, where console navigation lives in a separate operator shell (see [Operate session page](#operate-session-page)). Creating a workspace with a kind and publishing to Operate are designed in [operate-mode](../design/operate-mode.md) but not implemented.

## Operate session page

With Operate available, `/inferops-canvas` renders `OperateSessionPage` (`features/operate`), one tab's view of the person's operate session (see [Operate mode](operate-mode.md)). `OperateSessionProvider`, mounted around the shell, holds the single subscription and a `dispatch` that retries once on a conflict. A `consoleChanged` refusal means this tab's copy of a console is out of date (a builder removed a view, say), so `dispatch` re-reads the saved consoles (`invalidateWorkspaceScreens`) before rejecting: the sidebar drops the removed view, a removed current view shows *This view is no longer part of the console.*, and the toast (`refusalMessage`, shared by the page and the sidebar) says the console changed and now shows as saved. `OperateSidebar.test.tsx` covers this with a view removed from another client.

- **Console shell.** On the Operate landing route, `AppShell` leaves navigation to `ConsoleWorkspaceShell`. It does not mount the configuration sidebar or command palette. `OperateSidebar` holds All consoles, optional Assistant, the console's pages, widgets beneath the active page, and Settings. Its desktop collapse state is independent of the configuration sidebar; mobile uses a Kumo dialog with focus management. Page changes close the drawer. Configuration is reached through Settings only when the viewer has build access.
- **Launcher.** `ConsoleMosaic` shows up to eight real consoles per page in four desktop columns, two on smaller screens and one on phones. It never fabricates placeholder consoles. The shared assistant composer sits below the grid. Saved consoles return to the launcher and are highlighted on their page. Screens and flows remains a secondary destination.
- **Console setup.** `ConsoleBuilder` offers workspace/name, reusable screens and ordered views, starting experience, and review. `ConsoleScreenEditor` uses the existing canvas controls and explicitly saves new screens through `createCanvas`; those screens remain after cancelling console setup. Console saves use `createConsole` or revision-checked `replaceConsole`. Missing references and failed saves retain the draft. Setup has human build authority; the Operate agent retains its restricted capability.
- **Settings.** `ConsoleSettings` stores independent opt-in `customization` flags for personal shareable screens, widgets, application tools, and skills. Older definitions default to disabled. Use-role viewers cannot change settings or reach configuration controls. These flags record policy only: personal artifact storage, sharing, and extension installation are not implemented by this change, and flags grant no capabilities. Screens remain workspace-owned references reusable in multiple consoles within that workspace.
- **Working set.** A focused standalone screen renders through `SessionScreen`; with nothing focused, the launcher shows the retained working-set links. `showHome` clears console/focus/flow while keeping the working set and conversation. Unavailable references never fall back to another screen.
- **Console content.** `ConsolePage` renders the selected page or rollup through the viewer's workspace capability, under a breadcrumb (`nav aria-label="Breadcrumb"`: console, view, screen, board). Its boards and Wiki resolve under the viewer's own authority (`CanvasView`'s `resourceScope`): through the console workspace's connections for a builder, and for a use-role operator through their own operate session workspace. There a board that is not connected shows `BoardConnectPrompt` instead of the generic *Not connected* note: it lists the operator's own connected accounts that can reach the reference (`subscribeConnectedAccounts` with `resourceUrl`), connects the board in the session workspace with the chosen one (`newGatekeeper`) and re-reads it, or, with none, links to connecting InferOps; a refusal (no grant for the project) is shown as InferOps gave it. The console owner's connection is never used for them. A board card's **Open** dispatches the session's `openBoard` naming that scope's workspace and the canonical reference, and `SessionBoard` then shows it full-page (`CanvasBoardFullView`) from the session state, keyed by workspace and reference so a switch starts from nothing and a late read of the previous board is never painted. Back and the browser's Back dispatch `closeBoard`. A board named through a workspace this viewer does not read boards from (for example the console's own, for the use role) is said to be unavailable, with Back. That alert is shown only once the workspace that could read the board is open: while it is still opening (the session state, and its board, comes back before the workspaces are reopened after a reconnect), the page shows *Opening the board…* as a status instead. Opening or closing a board moves focus to the page's `main`. `ConsoleWidgetActions` in the right assistant dock opens a referenced widget full-page or in a Kumo modal. Widget resolution rechecks the latest canvas through that capability, and reports removed or inaccessible widgets. These widget selections are local presentation state, cleared by sidebar navigation; agent page navigation continues through `operatePage`.
- **Issue continuity.** The issue shown over the session board is session state too: `SessionBoard` hands `CanvasBoardWidget` an `openIssue` control (`OpenIssueControl`), `KanbanBoard` gives each card's edit dialog a controlled open state (`IssueDialogControl`), and opening or closing it dispatches `openIssue` / `closeIssue`. A reload, reconnect or another tab therefore reopens the same issue's form, and an issue the board no longer has (deleted, moved, unreadable) is an alert with **Back to the board**, never another issue. `IssueForm` also holds a synchronous in-flight guard, so a second submit or Enter before the busy state renders cannot propose the same create or edit twice. An issue with a change awaiting approval has no edit form, so the session can name it but no form opens until the change is decided.
- **Browser history.** `useBoardHistory` mirrors the session's board and issue into the `/inferops-canvas` search params `board`, `boardWorkspace` and `issue`: a board or issue opened (from this tab, another tab or the agent) is pushed as a history entry, a close replaces the entry, and a browser Back or Forward is sent to the session as `closeIssue`, `closeBoard`, `openIssue` or the kernel-checked `openBoard`. The session stays the truth: a refused browser move puts the URL back to what the session shows. The params are references only and validated for length by the route.
- The agent can also open a board when no console is open; `OperateSessionPage` then shows `SessionBoard` over its session workspace, with Back to the consoles.
- **Subject bar (#64).** The shown board is the session's subject, so `SessionBoard` puts `SubjectBar` above it, keyed by workspace and reference so that switching subject drops the previous roster, audit and handover form. `useSubjectPresence` subscribes with `OperateSession.subscribeToSubjectPresence` while the board (and issue) is shown and disposes the subscription when either changes; the bar lists the other people on the board (never the viewer, and nobody until `whoami` resolves) and whether each is on the board, this issue or another one. **Hand over** opens a Kumo dialog for a recipient's user id and a note and calls `handOver`; refusals are shown by code (unknown recipient, board out of reach). **Audit** shows `SubjectAudit`: `listSubjectAudit` pages over the session's events and the workspace's action log entries for the board, merged newest first, with **Load older** while the cursor continues, and a refusal when the viewer can no longer reach the board.
- **Handover inbox.** `HandoverInbox` lists `state.handovers` under the page header. **Open** dispatches the person's own `openBoard` in their own session workspace, then `openIssue` when the handover names one, then `dismissHandover`; if that board is out of reach (`boardUnavailable`) it stays waiting and offers `BoardConnectPrompt` for the person's own accounts, retrying the open once connected. **Dismiss** sends `dismissHandover` only.
- **Shared chat.** One `OperateChatPanel` stays mounted across launcher, console, screen, and setup navigation. It restores the most recent conversation, preserving subscriptions and drafts while hidden during setup/settings. Assistant-first consoles show a centered greeting, composer, and navigation suggestions when the conversation is empty; selecting a suggestion shows the page with the same chat docked on the right. The dock is resizable by pointer or keyboard and has widget and close controls. On mobile the page and assistant alternate, with navigation always accessible. `operateOnly` hides chat-list and build-only controls.
- **Agent attribution.** `AgentActivityNote` identifies recent page changes made by the agent from the event log's actor; it never guesses from the resulting page.
- **Approvals.** `SessionApprovals`, above the main region, lists the pending actions (`useActions`) of the session workspace (what the operate chat proposed) and of the focused screen's workspace (what its board cards proposed), with each action's title, resource, attribution from `requestedBy` (*Requested by the agent*, and so on), time, and, while it is under review or the workspace is restricted, its full description and fields. It opens the focused screen's workspace with its own `openGadget` stub, one more besides `SessionScreen`'s, and leaves it out when the viewer's role is `use` or it does not open. Other workspaces in the working set are covered once focused, so at most two workspaces are watched. Opening an action dispatches `reviewApproval`. Approve and Deny call that workspace's `approveAction` / `rejectAction` through `decideApproval`, which then reads the action back with `listActions({beforeId: id + 1})` and reports only what the log shows: `approved` is `applied`, `rejected` is `rejected`, and an approval that threw with the action still pending is `failed`, shown with the thrown message (the gatekeeper's denied, expired or stale-revision refusal). A refused rejection, or a decision whose result cannot be read back or still shows pending, reports no outcome and shows why. The outcome goes to the session as `approvalResolved` and to a polite `role="status"` line. The page's `lastApprovalOutcome` is shown with the action's own title, read from its workspace's log (`readAction`): one reported after the tab opened (another tab, device or the agent) is announced in that line, while the one the page held when the tab opened is history, shown outside the live region with its age (*· 1m ago*) and only for two minutes after the decision (`RECENT_ACTIVITY_MS`); a restored `failed` outcome is not repeated, as its action is still listed pending. The panel renders nothing when no covered workspace has a pending action and there is no outcome to show.
- **Board refresh.** A decision in the focused screen's workspace reaches `SessionScreen`'s own subscription, so `useDecidedActionInvalidation` re-reads the board as for any approval. A decision in the session workspace touches a board shown through another workspace, so `SessionApprovals` calls `useDecidedActionInvalidationInEveryScope`, which invalidates that board in every open adapter scope. Each scope re-reads through its own capability. An approval whose apply failed leaves its action pending, so no log entry re-reads anything; `SessionApprovals` then re-reads the action's board in every scope itself (`invalidateBoardInEveryScope`), so a card no longer shows provisional values the stale apply did not write.
- **Flows and the full-canvas state.** `WorkspaceFlows` on the canvas home lists each workspace's flows and authors them with `FlowEditor` (title, and screens in an explicit order). Starting one dispatches `startFlow` with the flow's current steps. While the session has a running flow, `OperateSessionPage` renders `FlowPage` instead of the tabs: the current step drawn by `FlowScreen` with the chrome-free `CanvasView`, the step's position, Back, Next (Finish on the last step) and Exit. On that route `__root.tsx`'s `ShellFrame` also drops the app shell, so the step has the whole page. Flows are started from the Screens and flows destination. The console shell and its single conversation remain mounted through the flow.
- **Wiki read-only.** Neither `SessionScreen` nor `FlowScreen` passes `wikiEditable`, so a Wiki widget on a session screen or flow step shows pages and live embeds but offers no section edit: the Wiki is authored on the workspace's own canvas, not operated (see [InferMind Wiki widget](#infermind-wiki-widget)). Board embeds in it keep the board's own move and edit controls, as a board card on the same screen does.
- **No coding.** Neither `SessionScreen` nor `FlowScreen` passes `codingDispatch`, so boards in the session and in flows offer no coding control and never look up a coding-dispatch connection, whatever the screen's workspace holds (see [Coding control surface](#coding-control-surface)).
- `useWorkspaceScreens` loads each workspace's screens, flows and consoles in one batch and is invalidated when any changes. Besides the 24 most recently active build workspaces, it opens up to 24 workspaces shared with the viewer for use and lists each that holds consoles, with the screens those consoles show (all the use role can read, see [Operate mode](operate-mode.md)) and no flows. The console launcher shows those consoles without an edit action, and `canBuild` keeps them out of the canvas home and console setup. Only recently active use workspaces are inspected, so an operator's console in an older shared workspace is not listed. A workspace is in an operator's `listGadgets()` from the moment it is shared with them (`Overseer.addCollaborator` records it in their user DO), so its consoles are found before they first open it.
- **Gallery styling.** The console uses semantic Kumo surfaces with restrained headers and navigation. Widget cards use rounded corners and drop shadows; console launcher cards remain flat and compact.

## InferMind Wiki widget

`CanvasWikiWidget` renders an `inferops.wiki` widget ([#87](https://github.com/factory-level/inferos/issues/87)): one InferMind workspace's Wiki, read through the workspace's own Wiki connection (`inferops://<tenant>.<workspace>/knowledge/wiki`, the gatekeeper's `knowledge/wiki` resource; see [InferOps gatekeeper](inferops-gatekeeper.md)). `CanvasView` renders it for that kind; edit mode shows only its reference and first page (`CanvasWidgetCard`), and each section in edit mode offers **Add Wiki** (a reference and an optional first page slug) when the catalog enables the kind.

- **Store.** `WikiData` (`wikiData.ts`) mirrors `CodingDispatchData`: it resolves the canonical reference through `Overseer.getGatekeeperByResourceUrl` and `openSession()` (client disposed at once, session cached, forgotten after a failed read, and disposed with the instance), so the reference authorizes nothing. It holds the page list, the pages read (by slug) and the section edits proposed here, as one immutable snapshot for `useSyncExternalStore`. A per-read clock lands only the newest read of the list or a page. States: `unbound` (no connection; the cue to connect, never a connect action), `disabled` (`DISABLED`, connection kept), `error` with the gatekeeper's code (`FORBIDDEN` and `UNAUTHORIZED` read as *No access to this Wiki*), a missing page (`NOT_FOUND`), and a failed refresh that keeps the last read with its error. Lost access (`FORBIDDEN`, `UNAUTHORIZED`, the connection removed) and `DISABLED` drop every page read, so nothing read under a revoked grant stays on screen. `useWikiData` holds one instance per widget and re-reads the Wiki when an action whose resource is the Wiki leaves `pending` in the action log (`useActionEntries`), whoever decided it.
- **Tree and page.** `wikiTree` (`wikiPage.ts`) orders pages by `parentId`, then `siblingOrder` and title; a page whose parent is not listed, or that sits in a parent cycle, is shown at the top level rather than hidden. The widget opens the chosen page, else `params.page`, else the first top-level page; a slug the list does not hold is reported (*not in this Wiki, or you cannot open it*) and never read. Sections render as Markdown through `WikiMarkdown` (the frontend's existing `react-markdown` and `remark-gfm`): raw HTML is skipped, URLs pass react-markdown's own sanitizer (only `inferops://` is let through it, as a title), only http(s) links become anchors, and images are shown as their alt text and never fetched. A section's `[[target#tag]]` links stay as written.
- **Embeds.** `sectionBlocks` splits a body on blank lines and treats a paragraph as an embed by the gatekeeper's own rule (`embeddedReferences` from `gatekeeper-inferops/src/wiki.ts`, imported, not copied), so the page embeds exactly the references the gatekeeper reports as `WikiDocument.references`. `parseWikiReference` names each: `project/board/<KEY>` (optional `workflow`) renders `CanvasBoardWidget`, the live Kanban with its moves and edits; `project/issue-card/<KEY>-<n>` renders `WikiIssueEmbed`, which reads the issue's project board through `useBoardData`; `knowledge/document/<slug>` of the same Wiki opens that page, and of another Wiki shows its text; anything else shows as an unsupported reference with its text. Board and issue embeds go through the scope's shared board adapter, so they resolve only where the workspace holds a connection to that board's exact reference (another tenant or workspace has none and reads *Not connected*, showing nothing of the target), share the Kanban's reads and pending changes, and show the issue's identity, state, priority, revision and pending marker exactly as the Kanban card does. Each embed has its own state, so one that fails (an alert with **Try again**) or is missing (*not on the board; it may have been deleted or moved*) leaves the others rendered.
- **Section edits.** With `editable`, each section has an **Edit** button (*Edit section purpose*) opening an inline `InputArea` with its Markdown; **Propose edit** calls `updateSection(sectionId, body, version)` with the version the page was read at, the gatekeeper's approval path (`inferops.wiki-section-update`). The edit is `proposing` while the call runs and `awaiting` once queued (*Waiting for approval, not saved yet*); the page is re-read either way. Only a page read started after the edit was queued decides it (`reconcileEdit`): the gatekeeper's overlay (`pending: "update"` at the unchanged version) keeps it awaiting, a new version with the edit's body is `applied` (*Saved*), the unchanged version without the overlay `rejected` (*Rejected, not saved*), and a new version with another body or a vanished section `stale` (not saved). A refusal (`STALE_REVISION`, `CONFLICT`, `FORBIDDEN`, `NOT_FOUND`, `DISABLED`) is an alert that keeps the draft, and the page is re-read. A section with a pending edit, from here or elsewhere, offers no Edit. Outcomes are announced in a per-section polite `role="status"`. `editable` is passed only by `InferOpsCanvasPage` through `CanvasWorkspacePane`'s `wikiEditable`, as `codingDispatch` is.
- **Agent view.** The **Agent view** toggle shows `WikiAgentText`: the page as an agent reads it (`readDocumentText`, through the same connection, an observation in the action log), re-read whenever the page read changes, beside a badge saying whether it equals the text built from the sections shown (`pageText`, the gatekeeper's `documentText` over the shown bodies). Embedded references stay as the links they are written as, which is what the gatekeeper's text gives an agent today.

`wikiPage.test.ts` covers the tree (order, unlisted parent, cycle), embed splitting equal to the gatekeeper's references over the demo fixture, the agent text, reference parsing and edit reconciliation; `wikiData.test.ts` covers canonical resolution and unbound, missing pages, failed refresh, lost access, `DISABLED` and a removed connection, newest-read ordering, an edit through proposing, awaiting and applied, rejected and stale outcomes (and a read older than the edit never deciding it), a refused stale proposal, the agent text and disposal; `CanvasWikiWidget.test.tsx` renders it in `CanvasView` and covers the tree and Markdown (no raw HTML, no `javascript:`/`data:` href), the configured and an unknown first page, the live Kanban and issue embed from one board read, a wrong-tenant issue as not connected, the embed following the Kanban's state and revision and a deleted issue, a failing embed beside working ones, the Wiki not connected and refused, an edit through *Waiting for approval* to *Saved* after a decided action, rejected and stale edits, read-only rendering, agent text equal to the rendered sections, and disposal of the Wiki and board sessions. Live acceptance against a running InferOps/InferMind is not recorded here.
