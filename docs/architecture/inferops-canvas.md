# InferOps canvas and transactional widgets

## Overview

Current-state baseline inspected at InferOS `1045d2e1ceac7be29e1a6f056c936fb31aa00851`. Proposed work is recorded in the [design](../design/inferops-canvas.md), not asserted as implemented here.

## Data and Control Flow

InferOS hosts sandboxed Gadgets and human participant presence; these are not an implemented InferOps canvas or agent activity feed. InferOps has a versioned widget definition, visual/text registries, inferops:// target references and one project/board widget. Its text resolver coalesces repeated URIs, then resolves distinct URIs independently. ProjectKanban currently depends on InferOps authFetch and its own UI environment. The board DTO contains a full board and decimal-string revisions, not a cursor-page protocol. Personal canvas pins are scoped by tenant/workspace/principal and store x/y positions; they are not the guarded shared composition contract proposed here.

## Configuration

Current board widget freshness is 60 seconds. The InferOps board hook pauses polling when the document is hidden and merges revisions while protecting pending changes. Existing personal pins have their own RLS boundary. InferOS frontend changes must follow frontend-conventions and reuse Kumo/@gadgets/ui.

## Divergences from Design

A guarded composition schema and pure edit engine now exist; workspace-authorized definition storage now exists; the kernel resolves a board reference to the workspace's existing connection and the frontend's shared board data adapter loads it (see [Board data adapter](#board-data-adapter)); a Kumo Kanban renders it as a canvas card and a full view, with transitions through the approval path (see [Kanban board](#kanban-board)). The design's chat presentation is the canvas pane beside the workspace chat on the InferOps Canvas page: there is no board rendering inside chat messages. Board activity is derived on the client from the workspace action log rather than from emitted activity events (see [Board activity](#board-activity)): it carries no canvas, widget or run identity beyond the log's `requestedBy` label, has no *proposing* or *applying* phase for actions it did not propose itself (the log records a move once it is queued), and links an action to an issue card only through the `Issue` field the gatekeeper renders for the approver. Issue create and edit go through the same approval path as moves; whether a create or edit was applied or rejected is inferred from successive board reads (the gatekeeper also stops overlaying a change made stale by an outside change, which then reads as applied, as a stale move does), a created issue is matched to its provisional card by title, and the edit form cannot show or clear the current description, which the board DTO does not carry. Kanban performance is instrumented, has an adapter-side baseline and a local browser run against the mock gatekeeper (see [Kanban performance](#kanban-performance)); board widgets preload within 200px of their scroll pane and large columns window their issue cards, budgets are agreed only for the local mock measurement scope (2026-10-05), nothing is measured against a live InferOps or under a shaped WebSocket (so there is no production performance guarantee), and every board read still returns the full board (no paging). The adapter's freshness is event-driven (moves and decided actions); the design's visibility-aware polling and freshness policy are not implemented. Importing the existing React component alone would not resolve authentication, styling, iframe or sharing boundaries.

A Master's documentation coverage (inferops#2325, MVP-15) reaches the canvas only through the agent text in the **Agent view**: the page itself still renders its generated structure block from the structure read and draws no coverage block of its own.

Console board and issue continuity (#63) covers one board and one issue in the session; it has no multi-board history beyond the browser's, and a duplicate mutation is prevented only within one form (the in-flight guard) and, for an issue that already has a change awaiting approval, by the gatekeeper's `CONFLICT`: two tabs proposing the same new issue still queue two creates. Narrow and wide layouts reuse the existing console and full-view layout and are not separately browser-tested here; live real-provider browser evidence for #59 is not recorded by this change.

Durable views are released as a bounded slice (#34, MVP scope in #1): the one private Kanban/Operate view keeps its definition through reload and Worker restart, refuses stale expected revisions and inherits the workspace's build-access boundary (see the evidence under [Resolving a board reference](#resolving-a-board-reference)). The durable-view requirements in the [consumer configuration design](../design/consumer-configuration.md) for generalized export/import/rebind, independent view-sharing controls, deployment-update recovery, schema migrations and cross-customer upgrade matrices are post-release and not implemented; today a view is shared only by sharing its workspace, and import always creates a new definition.

Bound views ([Bound view](#bound-view)) diverge from the bound-view contract (r8) in these ways. The contract's merge-sort figure (at most 3,989 element comparisons at n = 500) is the top-down bound; a bottom-up merge sort can make 3,993. Both stay under the n⌈log₂ n⌉ = 4,500 per sort key that is pre-charged, so the 176,000 budget holds. The cohort's acceptance rule needs the selection's `changeSeq` at the time a read is sent, which the three hook changes of #203 did not expose, so `onRequest` gained a second argument and `useHostBoard` returns `changeSeq` (additive). A table column's `as: date` and `as: flag` render as text: the contract types them but gives them no other rendering. The Build preview reads the committed head, not a chat's unsaved changes. The connection-accept `GatekeeperModal` case is tested with a portaled iframe standing in for its configurator, not the modal itself. The two-user browser pass, its proof note and the COOP assertions (contract §7) are not done yet; Firefox and WebKit are deferred to MVP-35. The frontend's TypeScript `lib` adds `ES2024.String`, because the shared parser uses `String.prototype.isWellFormed`.

## Open Questions

- The Wiki widget shows a page reference (`knowledge/document/<slug>`) of another workspace's Wiki only as its text, and InferOps widget kinds other than `project/board` and `project/issue-card` (for example `project/board-summary`, `project/my-issues`) as an unsupported reference. Whether InferOS should render those, and how a page reference resolves across Wikis, is open ([#87](https://github.com/factory-level/inferos/issues/87)).
- `modeForPath` counts the workspace's own canvas (`/workspace/$id/inferops-canvas`) as Operate for the shell's Build | Operate toggle, yet it is the one surface that offers coding dispatch (its viewers hold the workspace's build role, and it is not the Operate session). Whether the coding control should move to a Build-only surface once role consoles land ([#106](https://github.com/factory-level/inferos/pull/106)) is open.
- Choose ownership and persistence for shared canvas configuration; current InferOps pins are personal and cannot simply be widened.
- Decide whether the canonical InferOps widget client package can be safely adapted to Kumo and capability RPC or needs a thin host-specific renderer.
- Kanban performance budgets are **agreed for the local mock measurement scope** (owner decision 2026-10-05, [#158](https://github.com/factory-level/inferos/issues/158); see [Kanban performance](#kanban-performance)). A production performance guarantee is open until live-provider and shaped-WebSocket runs are recorded ([#164](https://github.com/factory-level/inferos/issues/164)).
- Host-board freshness compares the server's `readAt` with the client's wall clock (`hostBoardState.ts`, `accept`). A client clock 60 s or more ahead of the server refuses every answer, so the board stays *unavailable* with no reason given; a smaller skew shortens the board's lifetime, and from 30 s on every focus clears it as overdue. Whether to estimate the offset (for example from the read's round trip) or tell the operator their clock is off is open.
- A same-account reconnect keeps the session page mounted. A leave and return to the same console revision made elsewhere entirely within the gap looks like no change (a run carries no marker of when it was opened): this tab's dialog stays open and reads afresh through the kernel's guards. Whether that needs handling is open. A CF Access deployment has no account key, so its reconnects still close an open board (fail closed); keeping it there would need a synchronous same-account signal for Access sessions.
- The board DTO has no paging: `readBoard()` returns every column and card of the project, and every refresh re-reads it whole. A proposal for InferOps (an upstream contract change, so a cross-repo decision under `BoardResponseSchema`): (1) a column page, `GET` board with `?limit=<n>&cursor=<opaque>` per state returning `columns[].{state, issues, nextCursor, total}`, so a card shows the first page of each column and its count; (2) a delta read, `?since=<board revision>` returning the changed and removed issue ids since an opaque board-level revision (a new `boardRevision` on the response, monotonic per project), falling back to a full read when the revision is too old. The gatekeeper would expose both as optional `readBoard({ limit, cursor, since })` arguments with the same capability scope, and the adapter would keep per-target pages and apply deltas under its existing `wanted`/`applied` clocks. Whether InferOps can provide a board-level revision cheaply is open. The provider contract request is tracked in [factory-level/inferops#2335](https://github.com/factory-level/inferops/issues/2335); it is not implemented by card windowing.

## Implemented guarded definition and edit engine

`@gadgets/workshop-shared/canvas` exports v1 definition, content, section, widget and operation types, `parseCanvasDefinition`, `applyCanvasOperations` and a revision-conflict error. The parser reconstructs detached objects, accepts only known fields and rejects unknown definition/widget versions. Three widgets are registered. `inferops.project-board` v1 has a canonical target reference, software/content workflow filter and explicit completed-card visibility; presentation filters do not authorize data. `inferos.gadget` v1 has a `gadget:<workpieceId>` reference to a gadget in the workspace that owns the definition and no parameters. That reference is resolved only through the owning workspace's already-authorized session, grants nothing, and is meaningless in another workspace. On a console's screens it must name a widget registered with the console; a published screen copy names that widget's frozen install instead, which the use role opens only through `getConsoleWidget` for that console revision (see [Console widget registry](operate-mode.md#console-widget-registry)). `inferops.wiki` v1 names one InferMind workspace's Wiki, `inferops://<tenant>.<workspace>/knowledge/wiki` (`CANVAS_WIKI_REF`), with one parameter, `page`: the slug of the page opened first (`CANVAS_WIKI_PAGE`, URL-unreserved characters) or null for the first page. Like a board reference it is resolved through a separately granted connection and is presentation only (see [InferMind Wiki widget](#infermind-wiki-widget)). No transaction DTO, credentials, ownership or sharing grants are embedded in portable content.

View, section and widget IDs occupy one unique namespace per definition. Titles are bounded plain text. Sections have one to three desktop columns; sizes are normal (one column), wide (up to two), or full (all available columns). The renderer must collapse layouts responsively. Structural limits are 12 sections, 48 total widgets and 32 operations per batch; these bound validation work and are not measured performance budgets.

Edits add/remove/move/configure sections or widgets, rename the view, or restore validated prior content. Move indices refer to the destination after removal. Every intermediate composition validates, and a failure returns no partially modified caller state. A successful batch advances one canonical decimal-string revision using BigInt; stale expected revisions return a conflict with the current revision. Restore keeps the view identity and advances revision; it never invokes or reverses InferOps transactions. An unchanged-content edit still consumes a revision.

This engine performs no storage, authorization or feature enforcement. Its result is suitable for preview. Before persisting, a server caller must check installation flags and workspace edit authority, resolve resource capabilities independently, and compare/write inside one storage transaction. A test of this pure engine is not evidence that concurrent durable writes are safe.

Bootstrap writes `views/operations.json` with the configured target reference. `views:check` runs the pinned validator, bounds file count/size, rejects links/executable files, duplicate view IDs and any widget other than a project board (gadget references are workspace-local, so a portable starter cannot carry one), and reports runtime readiness false. It does not load the InferOps fixture, connect a provider or publish a view. Supporting pins expose a builder Canvas page when composable views are enabled; importing the starter creates a new definition.

## Workspace-scoped definition storage

The existing Overseer durable object's typed storage now has a `canvases` collection. `WorkspaceCanvasStore` uses that collection and the object's synchronous transaction mechanism; it does not introduce a separate database or domain-data cache. Owner/build sessions expose list, get, create, edit and delete methods on the existing Overseer capability. The use-only surface denies create, edit and delete, covered by the exhaustive use-role suite; list and get return only the screens a console of the workspace shows (see [operate mode](operate-mode.md)), so a view no console shows lists as absent and reads as `null`. Unrelated users still fail the native workspace-open authorization, and IDs are resolved only inside the current workspace's collection.

Every storage operation requires deployment bindings `COMPOSABLE_VIEWS` and `DURABLE_VIEWS` to equal the string `true`. These are structural installation switches, separate from admin soft settings and rollout flags. Disabling either denies reads and mutations without deleting stored records. The consumer launcher maps the corresponding config flags to these bindings. Public server configuration exposes effective flags; the frontend hides the editor's Canvas button and the Canvas page explains that composition is disabled. The same `env.d.ts` declares `CONSOLE_TOOLS`, which only console publication reads (see [callable widget surfaces](operate-mode.md#callable-widget-surfaces)); it is not reported to the frontend.

Creation accepts content only, mints a new UUID and starts at revision zero. It enforces 64 active definitions per workspace. Imports/recreation never reuse the deleted view's identity, avoiding stale-edit confusion. Edit and delete compare expected revisions in the same synchronous transaction as the write. Invalid edit batches leave persisted content unchanged. Delete removes only the definition; underlying InferOps data is untouched. Unknown stored schema versions fail validation rather than being silently rewritten.

Definitions inherit the native workspace build-access boundary; they do not yet have independent sharing controls. The existing sharing manager's session/revocation behavior remains authoritative. Reading a definition is not reading a referenced board: no target is resolved and no resource grant is created by this API. The renderer/data adapter separately obtains an authorized capability before loading any referenced data (see [Resolving a board reference](#resolving-a-board-reference)). Existing InferOps personal pins remain untouched.

## Resolving a board reference

A board card's `targetRef` is resolved to a capability through `Overseer.getGatekeeperByResourceUrl(resourceUrl)`, which returns the workspace's existing connection (a `GatekeeperClient`) for that resource or null. It is a lookup over the workspace's gatekeeper records, matched on the canonical URL the gatekeeper reported in its own `describe()` (`GatekeeperRecord.resourceUrl`), never on what the creator typed; the oldest match wins, and vendorless connections (models, spawners) have no URL and never match. The returned client's `openSession()` goes through `openGatekeeperSession`, the same chokepoint as a gadget binding or the agent, so reads are recorded as observations and transitions are submitted as actions attributed to the calling user.

The lookup mints nothing. A connection exists only because `newGatekeeper(accountId, resourceUrl)` created it from the creator's own connected account through `User.getGatekeeperClassFor`, where the InferOps gatekeeper resolves the reference's `<workspace>` slug among the creator's own InferOps workspaces, checks the account can open the project there, and the admin's disabled gatekeeper/resource lists are enforced. Board references use InferOps' own grammar, `inferops://<tenant>.<workspace>/project/board/<KEY>` (lowercase slugs; `inferops://demo.local/project/board/DEMO` is the demo data), never a deployment host ([ADR 0005](../adr/0005-inferops-uri-authority.md)); `canonicalBoardRef` lowercases the authority for cache keys and the lookup, while the gatekeeper accepts only the lowercase form when a connection is created. A collaborator holding a build session was verified against every such connection with their own account at `open()` (`addObserver`, strategy B for InferOps), and a connection added later restarts live sessions so they re-verify. So a canvas reference identifies a target but authorizes nothing: an unconnected reference yields null, which is the cue to offer the normal connection flow, and the method is denied to use-role collaborators like `getGatekeeperById`. A use-role operator resolves a console's board in their own operate session's workspace instead, through a connection made from their own InferOps account (see [operate mode](operate-mode.md#data-and-control-flow)); they never read through the workspace owner's connection. `packages/workshop-backend/__tests__/gatekeeper-lookup.test.ts` covers the oldest-match, canonical-URL, vendorless, blocked-pending-restart and use-role cases.

Real Workers/RPC tests cover concurrent revision conflicts, rollback, scope isolation, build/use roles, quota and recreation identity. A harness configuration update reloads Workers with durable views disabled, proves access is denied, then reenables them and reads the original definition. This demonstrates Worker-reload retention, not a cloud rollout, OS crash recovery, schema migration or completed consumer view experience.

The release slice of #34 (one private Kanban/Operate view with a live reference) has its own end-to-end test in `packages/integration-tests/__tests__/workshop-canvas.test.ts`. A view whose board card targets `inferops://demo.local/project/board/DEMO` is created and edited; an edit or delete at the replaced revision is rejected with the `Canvas changed` conflict and the stored definition is unchanged; two connections of the same owner editing the same revision produce exactly one winner and one conflict. Another account cannot open the workspace, and its own workspace neither lists nor reads the view and reports `not found` on edit. A collaborator added with the `use` role opens the workspace, lists and reads no view while no console shows it, and gets `Unauthorized` on edit and delete. The owner's Operate session opens the view, then the Workshop Worker is restarted through a harness configuration update (a pre-restart connection is shown to drop). Afterwards the definition, its revision and its board reference read back unchanged, the Operate session's working set and focus still hold the view and resolve to it, the use-role denial and the stale-revision conflict still apply, and an edit at the current revision advances it. Like the reload test above, this is local Worker-restart evidence, not a cloud deployment or OS crash recovery claim, and it reads no board data.

## Canvas page and builder composition UI

`/workspace/$id/inferops-canvas` is a fullscreen page (the root already treats every `/workspace/` path as chrome-free). It opens the workspace through the same `useWorkspaceOpen` flow as the editor, so share keys, observer confirmation and open failures behave identically, and use-only collaborators are redirected to the editor route, which shows them only the deployed gadget UI. The workspace's chat runs in a resizable left column (`ChatInterface`, with the remembered width shared with the editor) and the canvas fills the rest; on narrow screens a Chat/Canvas toggle shows one at a time. Chat selection lives in the `chat` search parameter. Opening a gadget from chat navigates to the editor with that gadget selected. The editor's InferOps Canvas button navigates to this page. The selected view lives in the `view` search parameter, so a screen can be linked to directly.

Outside edit mode the active view renders read-only. Sections are size containers, so column counts follow the canvas pane's width rather than the viewport: two- and three-column sections collapse to one column below 48rem, and three-column sections show two columns until 64rem. Gadget widgets resolve their reference against the live workpiece list and open a `GadgetClient` through the workspace's `Overseer` (`getGadget`), disposing it when the widget goes away. They then render through the existing sandboxed `GadgetUI` host, keyed by the gadget's head commit so an accepted change reloads it. A widget does not load its bundle until it has been within 200px of the screen. Missing gadgets and drafts that are still pending in a conversation are never opened; each shows an explanatory state instead. Board widgets render the Kanban board the board data adapter holds for them, or its loading, not connected or error state (see [Kanban board](#kanban-board)). A board card's **Open** button opens its full view: the `widget` search parameter names the widget, the pane shows only that board with a **Back** button, and the widget is cleared from the URL when the view changes or no longer holds it. In edit mode a board card shows only its reference.

Edit mode uses Kumo controls and the shared guarded operation engine. Sections can be renamed. Each section adds a board by reference or an accepted gadget from a picker. A separate move form selects a widget and destination section, appends it there, and returns focus to the source selector. This avoids removing the focused control along with a moved card. Existing upward ordering and undo can refine or reverse the move. It supports temporary in-memory views or saved definitions through the existing Overseer capability. Temporary views are labelled unsaved and last only while the page stays open. Saved changes compare revisions; rejected writes retain the displayed snapshot and offer an explicit reload. Undo restores prior content with a new revision and retains up to 20 session-local snapshots per view. Import validates bounded JSON and sends only content, so stored identities and workspace authority are never imported.

Async responses from an earlier workspace are ignored. A slow file read cannot initiate a create against a workspace that has since been left. Layout controls do not load or mutate domain records or gadget code. Gadget console logs in chat, individual sharing and performance benchmarks remain follow-up work.

Export revalidates the active definition and uses the existing browser file-download helper. The JSON contains only the strict portable schema, including required resource references. It contains no ownership, grants, credentials or transactional rows. The filename uses the validated view ID rather than the display title. Import preserves section/widget identities within the new composition but creates a fresh view ID and revision zero; it never carries authority from the source workspace. Exporting a temporary view is allowed, and does not implicitly save it to the server. Exported views that contain gadget widgets are rejected by the consumer starter validator, because gadget references are workspace-local.

## Composition catalog

`CanvasCatalog` (in `@gadgets/workshop-shared/canvas`) is what an installation offers for composition: the widget kinds people and agents may add, blueprints offered as widgets (instantiated as gadgets, placed as `inferos.gadget`), and screen templates new canvases may start from. Templates hold layout and `inferops.project-board` and `inferops.wiki` references only, since gadget IDs are workspace-local; `parseCanvasCatalog` reuses the definition parser, so IDs, limits and widget rules match saved canvases exactly.

The deployer sets it through the `CANVAS_CATALOG` JSON binding. `readCanvasCatalog` (`canvas-catalog.ts`) treats an unset binding as every registered kind with no blueprints or templates, and a malformed one as an empty catalog, logged at `error`: a catalog only ever narrows composition, so failing closed loses nothing it could grant. `getServerConfig` publishes it as `canvasFeatures.catalog`.

`applyCanvasOperations` takes an optional `allowedKinds`. Every widget an add, configure, add-section or restore brings in must be of an allowed kind; widgets already on the canvas are left alone, so narrowing the catalog never strands a composition. `WorkspaceCanvasStore` passes the catalog's kinds to every edit and checks created content the same way, so the builder UI and the agent are held to one rule.

The catalog grants nothing. It does not resolve a board reference or bind a gadget to a resource, and enabling a kind is not permission to read the data it shows.

## Agent canvas tools

When durable views are enabled the chat agent has two tools, `listCanvases` and `editCanvas`, which reach the workspace's canvases through the `AgentHooks.getCanvasAccess` hook. That hook returns the same `WorkspaceCanvasStore` paths the builder UI uses, so the agent's edits obey the same revision checks, limits and catalog. With durable views off the tools are not offered at all, and spawned sub-agents never get them.

The `editCanvas` description lists every widget kind with its reference grammar and params, including `inferops.wiki` and that a page's embedded references show live only where the workspace holds their own connection. `listCanvases` returns each canvas's layout and revision plus the catalog (kinds, blueprint widgets, template titles). `editCanvas` creates a canvas (optionally from a template) or applies a batch of the engine's own operations against an expected revision; a stale revision returns the current one so the agent re-lists before retrying. Edits apply when the call runs rather than riding the chat's proposed changes: a canvas holds references and layout, not code or domain data, and the builder UI applies the same edits immediately. Replay returns the recorded output and never re-applies an edit.

A blueprint widget such as the InferOps Kanban board is placed in three steps the tool description spells out: `createGadget` from the blueprint, wire the binding its notes describe (requesting the connection first), then add it with `editCanvas` as an `inferos.gadget` widget. A gadget created in the chat renders on the canvas once the user accepts the chat's changes.

## Canvas configuration CLI

`scripts/consumer/canvas.ts` configures composition before any custom code is written, in this repository (`pnpm canvas <command>`) or in a consumer wrapper (`pnpm canvas <command>`, through the wrapper runtime). It reads and writes `inferos.canvas.json` at that root: enabled widget kinds, blueprint widgets, screen templates, and which `custom-gatekeepers/` packages run. `list` shows what the checkout builds beside what is enabled; `enable`/`disable`, `add-screen`/`remove-screen` and `gatekeeper enable|disable|all` edit the file, re-validating before every write so the CLI never writes a configuration the Workshop would reject. Names the checkout does not build are errors rather than being dropped, and a blueprint widget requires the gadget kind it is placed as. `customGatekeepers: "all"` (the default, also used with no file) selects every custom gatekeeper whose `connection.json`, if it has one, says `reference` or `production`: a `scaffold` or `conformant` package (`gatekeeper-tickets`) appears in `list` under `available.unreleasedGatekeepers` and runs only when named with `gatekeeper enable`, which also expands `"all"` to that released set before adding it.

`pnpm dev-server` (and `run-local`) reads the same file — from `--consumer-root`, or this checkout's root — and passes the resolved catalog as `CANVAS_CATALOG` and binds only the selected custom gatekeepers. In-repo there is no `inferos.config.json` to carry feature flags, so the presence of `inferos.canvas.json` turns composable and durable views on; a wrapper's own flags always take precedence.

## First-class InferOps Canvas page

When composable views are enabled the sidebar shows **InferOps Canvas**, linking to `/inferops-canvas`. That page lists saved screens across the user's most recently active build workspaces (at most 24): screens are stored per workspace, so it opens each workspace once with a pipelined `openGadget(id).listCanvases()` and disposes the stub right away. A workspace that needs observer setup before it can be opened is listed without its screens. The page also creates a screen in a chosen workspace, blank or from a catalog template, and opens it.

On a workspace's page the pane offers only the catalog's widget kinds. Catalog blueprint widgets appear as buttons that start a new chat (with the user's last-chosen model) asking the agent to build and place that widget, since doing so means creating a gadget and wiring a connection. Saved views are re-read every five seconds while the page is visible and no operation is in flight, and again as soon as a hidden page is shown, so the agent's edits show up without a reload. A board reference card shows the board through the board data adapter when the workspace has a connection for it, and says it is not connected otherwise; in edit mode it shows only the reference.

## Board data adapter

`features/canvas/boardData.ts` is the adapter every board-shaped card shares; `useBoardData.ts` serves it to React. One `BoardData` instance serves one scope, the user's capability on one workspace (its `Overseer` stub): the hook holds one per stub with a reference count and disposes it, sessions included, when the scope's last card unmounts, so a reopened session or another workspace starts empty and nothing read in one scope is shown in another. Within a scope, entries are keyed by the canonical widget request: kind, version, the canonical target (`inferops://` host lowercased, as the gatekeeper describes it) and the normalized params. Params are presentation only (`visibleColumns` filters the whole board by workflow and completed visibility at render), so every card of one board shares its reads whatever their params.

A target is resolved through `Overseer.getGatekeeperByResourceUrl` and the returned client's `openSession()`, pipelined and disposed; the session is cached per target and forgotten after any failed read so the next read resolves the connection again. A null lookup is the `unbound` state (the reference is not covered by any connection in this workspace); the card says so and offers nothing, since connecting is the normal connection flow. The adapter never mints a connection and never selects one from the URI. The session types are imported type-only from the gatekeeper's own `src/types.d.ts` (a workspace dev dependency), not copied.

Reads are independent `readBoard()` calls; there is no batching. A card that subscribes while another card of the same target shows it `ready` (the last read landed and nothing newer was asked for) takes that board and its pending moves and changes without a read, so a card deferred while offscreen costs nothing when it scrolls in; while that card is `stale` the newcomer joins the pending read, and after a failed or no read it reads. In-flight reads are coalesced per target, at most four run at once per scope, a queued read nobody subscribes to any more is dropped before it starts, and an in-flight result for a card that left is discarded. Two clocks per target order results: a demand for fresher data (a refresh, a submitted move, a decided action) stamps `wanted`, and a read started earlier cannot satisfy it; `applied` records the read on screen, and an older read never lands over it. A refresh keeps the last good board visible as `stale`; a failed refresh keeps it with the error, while a revoked connection (`UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, or the connection removed) drops it. A `DISABLED` failure (the deployment has InferOps turned off, `INFEROPS_ENABLED`; see [InferOps gatekeeper](inferops-gatekeeper.md#integration-switch)) is its own `disabled` state: the board is dropped, the connection is not treated as revoked, and the next successful read after InferOps is turned back on shows the board again.

`move(request, issueId, toStateId, expectedRevision)` proposes a transition through `openIssue(id).transition(...)`, the gatekeeper's approval path, with the decimal-string revision the card read. The move is listed as pending on every card of the board, `proposing` until the call returns and `awaiting` once it is queued; a second move of the same issue is refused locally as `CONFLICT`, as the gatekeeper would. The board is re-read whether the call succeeded or failed. A pending move stays while the authoritative board still shows it undecided, that is, the gatekeeper's simulation of the issue in the target state at the unchanged revision; it is dropped once the revision differs or the issue is back in its state. The adapter only says the board stopped showing it pending; how it ended is the action log's to say (see [Kanban board](#kanban-board)). The adapter never edits the board itself.

`create(request, issue)` proposes a new issue through the session's `createIssue` (the board UI always passes the column's `stateId`), and `update(request, issueId, changes, expectedRevision)` an edit through `openIssue(id).update(...)` with the revision the card read; both go through the same submit path as `move()` (session lookup, `NOT_CONNECTED` when no connection covers the board any more, the gatekeeper's code and message on refusal, a re-read either way) and return the same `ProposalResult`. Each is listed in the state's `changes` as a `PendingChange`, `proposing` until the call returns and `awaiting` once it is queued. Unlike a move, an awaiting create or edit is held only until the next read lands: only reads started after it was queued can land, and the gatekeeper's reads overlay it themselves (`Issue.pending` `create`, a provisional card with id `pending-<action id>`; `update`, the new title and priority at the unchanged revision), so from then on the board, not the adapter, says it is pending and how it was decided. `move()` and `update()` refuse locally, without calling the gatekeeper, an issue the board marks pending or that has a local pending move or edit (`CONFLICT`, as the gatekeeper would) and a provisional card (`PENDING_CREATE`, since `openIssue` does not accept its id). `CanvasView` listens to the workspace's action log through the existing `useActionEntries` store and invalidates a board when an action on its connection leaves `pending`, so an approval or rejection by anyone re-reads it.

`CanvasBoardWidget` renders a live board in one of two presentations (below); `CanvasBoardSummary` shows only the reference, for edit mode. Nothing polls on visibility. `boardData.test.ts` covers duplicate cards sharing one read, unbound and retried references, canonical keys, partial failure and revocation, InferOps turned off and back on, stale responses in both orders, concurrency and cancellation, scope isolation and disposal, pending moves through decision, refused moves, creates and edits through queueing and the overlaying read, local refusal of changes to pending and provisional issues, stale edits and presentation filtering, and (with the development read metrics) duplicate cards counted as one read, no read for a card that left, a superseded stale response, one re-read per invalidated target, coalesced invalidations under saturation, a late card served from the card showing the board (pending move included) without a read, and a late card joining a pending re-read or reading after a failure; `CanvasView.test.tsx` covers the live card, session release, action-log invalidation, offscreen board cards reading nothing until they come into view (duplicates still sharing one read) and a card that scrolled away staying subscribed. `useDecidedActionInvalidation` (in `useBoardData.ts`) is the action-log listener, called by every presentation that shows boards of a scope; the underlying `useActionEntries` store is reference-counted, so the view and the full view share one subscription.

## Kanban board

`CanvasBoardWidget` is one board reference shown live. Its props are a discriminated union on `presentation`: `card` (in a view's grid cell, with an optional `onOpen` for the full view) or `full` (the widget on its own, in `CanvasBoardFullView`). A card subscribes to its board, and looks up its coding-dispatch reference, only once it first comes near the screen (`useHasBeenOnScreen`, the same latch gadget cards use); until its board is loaded it holds an embedded board's height (32rem), so cards further down are not all near the screen as short loaders. The full view always reads. Both read through `useBoardData` with the widget's request, so the card and the full view of one reference are one adapter entry and one read, and a move proposed in either is pending in both. The frame shows the project name and key, the reference, a **Refreshing** or **Refresh failed** badge while the adapter holds a stale board, a count of moves pending approval, a refresh button, and the body for the adapter's state: a loader while loading, a *not connected* note for an unbound reference (the cue to connect through the normal flow, never a connect action), a `role="status"` note that InferOps is turned off for this deployment (and that the connection is kept) for the `disabled` state, an alert with **Try again** for an error, the last board with the refresh error for a failed refresh, and an empty note when the card's params leave no columns. `visibleColumns` applies the card's workflow and completed-visibility params to the whole board at render.

`KanbanBoard` renders the given columns, each a labelled section with a heading, a count and a list of `KanbanCard`s sorted by priority then identifier (`kanbanBoard.ts` holds the pure rules). A card shows the identifier, a priority badge, the title, the assignee id (truncated, full id as its title) when set, the target date with an overdue mark for open issues, and the blocked reason. Layout is a prop: `embedded` gives fixed-width columns that scroll sideways within the card's cell, capped in height with per-column scrolling, and `full` gives columns that share the pane's width and height. Kumo tokens and components only; no custom colors.

Moves go through the adapter's `move()` only, with the issue id, the target state and the revision the card read. Three inputs reach it: a card's **Move to** menu (`DropdownMenu`) listing the issue's targets, the keyboard (the card is focusable; left and right arrows choose a target, shown on the card, Enter proposes it, Escape cancels), and pointer drag and drop onto a column, which the board accepts only for an allowed target (same workflow, not the issue's own state, taken from the whole board so a target the card's params hide is still offered; the issue then leaves the card's columns). A card with a pending move offers none of the three until it is decided, matching the gatekeeper's one-move-at-a-time rule.

A card stays where the authoritative board places it and shows its pending move as a badge: *Proposing move to* while the transition call is in flight, *Awaiting approval* once queued; the re-read after the call shows the gatekeeper's simulation, which places the issue in its target column at its unchanged revision. When the board stops showing a move pending, its outcome is taken from the action log, never from the board (see the decisions paragraph below): a rejected move is marked *rejected* until the issue changes again, an applied one is marked for six seconds. Every outcome, including a refused proposal (a `STALE_REVISION` tells the user the board was re-read), is announced through a visually hidden `role="status"` live region, and the keyboard instructions are a hidden paragraph every card describes itself by. The board remembers which card has focus and restores it after the card re-mounts in another column; focus that left the board is left alone.

Each column header has a **New issue** button (`aria-label` *New issue in Todo*) and each card that can be edited an **Edit** button (*Edit ENG-12*); both open `KanbanIssueDialog`, a Kumo `Dialog` holding a form with a required title, a description and a priority (`Select`). Selects in these dialogs use Kumo's default portal, which Base UI nests inside the open dialog's own portal, the only subtree the modal dialog leaves visible to assistive tech; `styles.css` raises their positioner (`z-index: 1100`) above the dialog layers. The dialog's own trigger is the control, so Kumo returns focus to it when the dialog closes, and the form is mounted only while open, so every opening starts from the board's current values. A new issue is proposed in the column's state; columns are whatever states the board returns, and no workflow is assumed. The edit form starts from the card's title and priority and sends only the fields that changed (`changedFields`): the title when its trimmed value differs, the priority when it differs, and the description only when one was entered, because the board DTO does not carry the current description (the field says that leaving it empty keeps it). Submitting with nothing changed is disabled. While the proposal is sent the form is disabled and says *Proposing…*; a refusal keeps it open with the reason in an alert, the gatekeeper's message (a workflow-policy `FORBIDDEN`, `CONFLICT`, `INVALID_STATE`, `DISABLED` and so on) except `STALE_REVISION`, which reads *This issue changed; refresh and try again.* (the board is re-read either way, and reopening the form starts from the new values); a queued proposal closes it and is announced as waiting for approval.

A card shows one pending badge, most specific first: its own move (*Proposing move to* / *Awaiting approval*), its own edit while the call is in flight (*Proposing edit…*), a provisional card (*New issue, waiting for approval*, with a dashed border and *(not created yet)* in its accessible name), an awaiting action from the log (*Awaiting approval (Agent): …*), then the gatekeeper's markers (*Edit waiting for approval*, *Move waiting for approval*), which also cover changes requested elsewhere that the log does not tie to the card. Anything pending withholds the edit button, the move menu, keyboard moves and dragging (a drag that starts anyway is cancelled), so a provisional card can no longer be dragged into a move that fails `NOT_FOUND`. Provisional cards sort after the column's existing issues. **Decisions come from the action log.** `advanceDecisions` (`kanbanBoard.ts`) tracks what the board shows waiting for approval (`trackedChanges`: this board's own awaiting move or the gatekeeper's `transition` marker, an `update` marker, a provisional card; at most one per issue). When the board stops showing one, it is decided only once its action's record in the log is decided, and the outcome is that record's: `approved` is applied, `rejected` is rejected. `KanbanBoard` receives the board's decided actions as `decided` (`BoardActivity.decided`) and matches them on the issue identifier (the action's inline `Issue` field) or, for a new issue, on its title (the inline `Title` of an action that names no issue). The board's revision is never read as an outcome: an outside edit in InferOps moves it too, and the gatekeeper stops overlaying a change made stale while its action stays pending, as does an approval whose apply failed. A drop with no decision yet waits for one, a decision that lands before the drop is held for it, decisions the log held when the board mounted are history, and decisions for changes the board never showed pending are ignored. Edits are marked *Edit applied* (six seconds) or *Edit rejected* on the card. All outcomes are announced in the polite region, whoever proposed them.

`kanbanBoard.test.ts` covers `advanceDecisions` (a dropped edit at a new revision decided only by the log's rejection, early decisions, history and untracked issues, creates by title). `KanbanBoard.test.tsx` covers rendering, the three move paths, pending and decided display, announcements (including a denied edit announced as rejected though an outside edit moved the revision), focus retention, the two layouts, creating in a column's state, edits sending only changed fields, stale-revision and refusal messages, provisional and pending-edit cards withholding their controls, and announced create and edit decisions; `CanvasBoardWidget.test.tsx` covers the adapter states (including the turned-off note and recovery), the ids and revision a keyboard move sends, the card and full view sharing one read, a create and an edit end to end through the session, waiting for approval and applied after a decided action re-reads the board, a create through approval (#59) shown as a provisional card while its action is pending and announced from the action log as created, or as rejected for a denied one, an issue deleted in InferOps while its form is open (#63) closing the form with "no longer on this board" and the way back, and a pending edit across a reconnect (#63: a new `Overseer` stub whose log replays the pending action) still shown as awaiting approval with no outcome announced and nothing re-sent, then announced as rejected once the log says so; `CanvasWorkspacePane.test.tsx` covers opening and closing the full view. Chat shows no board of its own: on the InferOps Canvas page the chat sits beside the canvas pane, and a move's approval is decided in the chat's action list. Large boards are not paged and nothing polls on visibility; see [Kanban performance](#kanban-performance) for what is measured.

## Kanban performance

Implementation tracking issue [#28](https://github.com/factory-level/inferos/issues/28) is closed after windowing and re-measurement; the owner directed remaining human input into follow-up [#158](https://github.com/factory-level/inferos/issues/158). Instrumentation, an adapter-side baseline and a local browser run against the mock gatekeeper exist; nothing has been measured against a live InferOps. Budgets were agreed by the owner on 2026-10-05 for the local mock measurement scope only ([budget decision](#kanban-budget-decision) below).

**Read metrics.** `features/canvas/boardMetrics.ts` is an optional recorder `BoardData` takes as `metrics`. Per `readBoard()` it records the duration from read start (including the session lookup of a first read) to the result, the UTF-8 byte length of the result as JSON, and the outcome: `applied`, `unbound`, `superseded` (lost to a newer read, or no card left to show it) or `failed`. It also counts reads started and *shared demands* (a card served by an existing entry, or a demand joined to a queued or in-flight read). Snapshots give the counts, nearest-rank p50/p95 latency and last/max payload over the last 200 reads. Nothing about a board is kept: no target, content or identity. `useBoardData` creates one per scope only when `import.meta.env.DEV`, and exposes them as `window.__inferosBoardMetrics()` in development builds; production adapters have none and pay nothing. Sizing a payload serializes it, so metrics roughly double the adapter's per-read cost on large boards (below).

**What the tests prove** (`boardData.test.ts`, `CanvasView.test.tsx`): duplicate cards of one target, whatever their params, share one read; a queued read for a card that left is never started, and an invalidation does not re-read a target with no cards; an older response never lands over a newer one; an invalidation re-reads each target exactly once whatever its number of cards, reusing the cached session; repeated invalidations while reads are saturated (four per scope) coalesce into one queued read; a board card reads nothing until it first comes near the screen, and a card arriving after another card of the board loaded takes that board without a read.

**Offscreen cards.** Canvas hosts pass their actual scroll pane as the explicit `IntersectionObserver` root to `useHasBeenOnScreen`, so its 200px margin starts loading before a widget enters the clipped pane. This includes gadget widgets and board embeds in Wiki widgets. A board card subscribes only once the hook reports it near the pane, and then stays subscribed, also after it scrolls away; it is not unsubscribed when far away. Re-subscribing on each scroll back would cost a whole-board read every time (there is no paging or delta read), and a card that drops back to loading would unmount its Kanban, losing the decision tracking (`advanceDecisions`) and announcements of proposals still pending; a subscribed offscreen card costs nothing until its board is invalidated, and that re-read is shared with every other card of the target. Pending proposals are held per target in the adapter, so they reach a card whenever it subscribes. The full view always reads. Cards render nothing of the board until then; rendering, not reading, is the larger cost of a large board (below). The adapter does not poll, so there is no stale polling to clobber an edit; refreshes are event-driven and ordered by the `wanted`/`applied` clocks.

**Column windowing.** `KanbanColumn` owns each column’s vertical scroll list. Columns of 50 issues or fewer render in full; larger columns render the visible slice plus three cards of overscan on each side, using a 140px initial height estimate corrected by measured card heights. Titles, blocked reasons and badges keep their natural height. Inaccessible spacer list items preserve omitted ranges. First/last cards remain mounted for native Tab entry/exit; pending proposals (local moves/edits, external pending actions and provisional cards), focused/dragged cards and open edit/coding dialogs also remain mounted at their sorted positions rather than expanding the whole window. Column counts remain the full counts; each card has `aria-setsize` and its full sorted `aria-posinset`.

Tab/Shift+Tab preserves traversal through each card and its controls: crossing an unrendered gap mounts, scrolls to and focuses the next logical target. Up/Down and Home/End navigate cards; Left/Right, Enter and Escape retain move selection/proposal behavior. Focus follows a moved issue into its destination column. Decision tracking and live announcements remain in `KanbanBoard`, so scrolling does not forget pending actions. Windowing changes rendering only: the adapter still shares reads by target and keeps its existing proposal and invalidation behavior. `KanbanBoard.test.tsx` covers the 50-card boundary, positions/counts, keyboard traversal, off-window move focus, proposal retention and controlled/ordinary dialogs; `CanvasBoardCoding.test.tsx` protects an open coding form; `CanvasWorkspacePane.test.tsx` checks the explicit pane root and one-way preload latch. A Chromium run against the local 500-issue fixture additionally verified forward/reverse Tab across gaps, Home/End, an unsaved edit surviving scroll and returning focus after close, a pending move retained offscreen, and a board loading while still 150px outside the pane but not at 250px. It recorded no uncaught browser errors.

## Action attribution

Every workspace action log entry (`ActionLogEntry`, from `listActions` and `subscribeToActions`) carries an optional `requestedBy`: `agent`, `person`, `gadget` or `hook`, mapped in `actionRecordToLog` from the kind of the stored record's `caller` (`user` becomes `person`). It is the groundwork for agent activity and approval displays. It is a display label only: no decision reads it, and the caller's chat id, gadget id and identity stay on the server. Records persisted before callers were tracked have no `caller`, so their entries omit the field. `workshop-agent-actions.test.ts` checks that an agent's writes report `agent`, and `workshop-action-history.test.ts` that writes and reads through the owner's own connection session report `person`. The canvas board activity line (see [Board activity](#board-activity)) and the operate session's approvals show it, the latter as *Requested by the agent*, *a person*, *a gadget* or *a hook* (see [Operate session page](#operate-session-page)).

## Board activity

`boardActivity.ts` folds action log entries into one board's activity. Only entries whose `resourceUrl` is the board, after the same `canonicalBoardRef` the adapter keys on, count; entries for other resources, with no resource, or for hooks are ignored, and a later record with the same id replaces an earlier one. An observation is a *read*, a pending action is *awaiting approval*, and an approved or rejected action is *applied* or *rejected*. Awaiting actions are active until decided; the others are recent, dated by `actionChangeTime`, and fade two minutes later (`RECENT_ACTIVITY_MS`), at most five kept (`RECENT_ACTIVITY_LIMIT`). Each item carries the `requestedBy` label (`Agent`, `Person`, `Gadget`, `Automation`, or none for older records; a person is not necessarily the viewer) and only the one-line title the gatekeeper rendered for humans, never the description, fields or payload. An awaiting action's issue is the whole (untruncated) inline `Issue` field of its description, which the InferOps gatekeeper's `transition` and `update` write, and an action naming no issue carries the whole inline `Title` as `creates` (the gatekeeper's `createIssue`); both are used for matching only. Besides the capped `recent` list, `decided` holds every applied or rejected action the log holds for the board, oldest first and unfaded, for the board's decision announcements.

`useBoardActivity(overseer, targetRef, connected)` reads the scope's log through the shared, reference-counted action store: `useActionEntries` for live entries (replayed on mount) and `useActions` for actions already pending when the session opened, which the store pages rather than streams. Entries are held with the `Overseer` stub they arrived on and ignored for any other, so a card moved to another workspace or a reopened session never shows the previous scope's log. A timer re-renders when a recent item turns a minute old or fades.

`CanvasBoardWidget` passes `connected` as whether the adapter holds a board: once the connection is revoked or the board cannot be read (`error`, `unbound`, or loading), nothing shows as awaiting, so a pending action never looks active on a board that can no longer show its outcome. `BoardActivityLine`, below the header, shows a Kumo status badge, the label, the title and the age: the card shows the newest awaiting action (else the newest recent item) with a *+N more* count, the full view lists them all. A visually hidden, always-mounted polite live region announces the newest awaiting action only, so repeated reads stay silent. `KanbanBoard` takes the awaiting actions by issue identifier and marks the matching card *Awaiting approval (Agent): Move ENG-12 to Done*, offering no move on it, as the gatekeeper refuses a second; a move the board proposed itself keeps its own *Proposing* / *Awaiting approval* badge.

`boardActivity.test.ts` covers ordering, active to decided, fading and the cap, the disconnected fold, resource filtering, attribution labels, title-only output and issue linking; `useBoardActivity.test.tsx` covers scope isolation between two `Overseer` stubs, pending pages, the disconnected state and timed fading; `CanvasBoardWidget.test.tsx` covers the header line, the announcement, the card badge and clearing on a revoked connection.

## Coding control surface

A board's issues can be handed to the local coding runner from the Kanban ([#72](https://github.com/factory-level/inferos/issues/72)), through the project's **coding-dispatch** connection (`inferops://<tenant>.<workspace>/project/dispatch/<KEY>`, a separate grant from the board's; see [local coding workflows](local-coding-workflows.md)). Nothing about the board authorizes it.

- **Who offers it.** `codingDispatch` is an opt-in prop on `CanvasWorkspacePane`, `CanvasView`, `CanvasBoardFullView` and `CanvasBoardWidget`. Only `InferOpsCanvasPage` (the workspace's own canvas, which sends use-only collaborators away) passes it. The Operate session's `SessionScreen` and a flow's `FlowScreen` never do, so on those surfaces the dispatch reference is never looked up and no control is rendered: code is not edited from Operate.
- **Resolving it.** With the prop, `CanvasBoardWidget` derives the project's dispatch reference from the board reference (`dispatchRefOf` in `codingRuns.ts`) and `useCodingDispatch` reads it through `CodingDispatchData` (`codingDispatch.ts`), which resolves it exactly as the board adapter resolves a board: `Overseer.getGatekeeperByResourceUrl`, then `openSession()`. No connection means state `unavailable`, and the board then gets no `coding` prop: no button, no badge, nothing disabled. A connection removed later goes back to `unavailable`. `DISABLED` (the deployment's `CODING_WORKBENCH_ENABLED` off) is its own state, and so is a read error.
- **Reads and following.** One read lists the repositories and the runs; later automatic re-reads list only runs, since each read is an observation in the action log. While a run is queued or running, or a dispatch or cancel of one awaits approval, the runs are re-read after 10, 20 and 40 seconds and then every 60 seconds, for at most 60 re-reads (`FOLLOW_DELAYS_MS`, `FOLLOW_LIMIT`). Re-reads stop once nothing is in flight, after a failed read, or at the limit, which the dialog says (*Stopped checking for updates automatically*). A refresh restarts them, from the dialog's **Refresh runs**, the board's **Refresh board**, or any action on the dispatch reference leaving `pending` in the action log (`useActionEntries`). Requests made during a read coalesce into one more read. The instance is disposed, with its session, when the card unmounts.
- **Card.** `KanbanBoard` passes each card its issue's newest run (`latestRunOf`; the gatekeeper lists dispatches awaiting approval first). The card shows it as a Kumo badge (`CodingRunBadge`): *Dispatch awaiting approval*, *Coding queued*, *Coding running*, *Coding succeeded*, *Coding blocked* (a failed run with `reasonCode` `AUTH_BLOCKED` or `QUOTA_BLOCKED`), *Tests failed* (`TESTS_FAILED`), *Coding failed*, *Coding cancelled* or *Coding outcome unknown*, plus *Cancel awaiting approval* while one is pending. A software issue that exists (not a provisional create) gets a **Coding task** button (*Coding task for ENG-12*); a pending move or edit does not withhold it. When a run the board saw active finishes, the board announces it in its polite status region (`finishedRuns`, `describeRun`).
- **Dialog.** The button opens `KanbanIssueDialog` in `code` mode, which renders `KanbanCodingForm`. It shows the latest run (`CodingRunDetails`): repository and base ref, what a queued, unknown or blocked run means, the run's error, and once finished the patch path with files and `+`/`−` lines, the test pass and fail counts with the artifacts directory, each test command with its exit code, timeout, duration and its `stdout`, `stderr` and `record` paths, the test summary when there is no per-command detail, and the runner's own summary, labelled as not evidence. An active run can be cancelled (**Propose cancel**). With no active run and no dispatch awaiting approval, a **Repository** `Select` offers only repositories that are `allowed && enabled`; the others are listed with why (*disabled in InferOps*, *not on this deployment's coding allowlist*), and with none selectable the form is replaced by an explanation. Only software issues can be dispatched.
- **Honest states.** **Propose dispatch** sends `dispatch(issueKey, {repoId}, revision)` with the revision the card read. The dialog's polite status says *Proposing…* while the call is in flight, then *awaiting approval* (from the provisional run, the action log, or the queued call until either arrives), then *approved: InferOps queued the run* or *was rejected; nothing was queued* from the decided dispatch action in the log (`BoardActivityItem.tag` `inferops.code-dispatch`, only actions newer than the proposal). The run's own state, re-read from InferOps, says what happened after. A refusal is an alert and never shows as queued: `FORBIDDEN` (the repository is not allowlisted), `RUN_ACTIVE`, `STALE_REVISION` and `DISABLED` each get their own text (`codingErrorText`). An apply failure (for example a missing `issue:delegate`) leaves the action pending, so the dialog keeps saying it awaits approval, and the approval itself says why. The dialog stays open after a proposal, since it also follows the run.
- **Activity.** The board's activity line also shows the dispatch reference's actions (`combineActivity` with `actionsOnly`, which leaves out its reads, re-read automatically as they are), so a dispatch or cancel awaiting approval is announced like a move. Only the board's own awaiting actions lock a card's move and edit controls.

`codingRuns.test.ts` covers the run phases (blocked, tests failed, awaiting approval), following and cancelling rules, the newest run per issue, finished runs, the repository picker rules, the dispatch reference and a refused cancel; `codingDispatch.test.ts` covers no connection, the follow limit and refresh, coalescing, stopping after a failed read and disposal; `CanvasBoardCoding.test.tsx` covers no control without a connection or without the prop (the dispatch reference never looked up), dispatch through proposing, awaiting approval and applied, the `FORBIDDEN`, `RUN_ACTIVE`, stale-revision and `DISABLED` messages, the turned-off state, every run state on the card and in the dialog, a succeeded run's patch, tests and artifacts, a run that failed its tests, cancel through approval with its announcement, following on a backoff until the run finishes, content issues and the repository choice; `OperateCoding.test.tsx` renders a session screen and a flow step over a workspace that holds both connections and finds the board with no coding control and no lookup of the dispatch reference; `boardActivity.test.ts` covers the action kind tag and the combined line.

## Workspace kind

Each workspace stores an explicit kind, `WorkspaceKind` in `workshop-shared/src/api.ts`: `app`, `widget` or `workflow`. It records how the workspace is meant to run and where Operate mode (the InferOps Canvas) presents it. An app opens full-screen with a chat/app toggle. A widget is a tile on canvas screens. A workflow has no UI and runs on timed (scheduler) or event (hook) triggers.

The kind is deterministic. The Overseer's `kind` singleton changes only through `Overseer.setKind()`, which is build-role only (the use-role capability denies it). Nothing infers it from the workspace's code. Workspaces stored before kinds existed read the default `app`. The Overseer sends the kind in `getMetadata()` and `subscribeToMetadata()` to both roles, because it decides how a use-role viewer is shown the workspace. `setKind` also mirrors the kind into the owner's workspace list (`User.updateKind`), so `listGadgets()` can group workspaces by kind without opening each one. Older list records have no `kind`, which also means `app`.

The kind decides what the workspace builds, through pure functions in `workshop-shared/src/workspace-kind.ts` that the kernel, the agent and the UI share:

- `workspaceKindContract(kind)` is the kind's rules as a section of the builder agent's system prompt. It goes in the project-specific slot, so the cached static slot is unchanged. An app has no contract: it is what the agent builds by default.
- `workspaceKindStarter(kind)` is the files a new gadget starts from. The agent's `createGadget` copies them in when no blueprint is given, as one change that rides the chat's proposed changes like a blueprint copy, and reports them as `starterNotes`. A widget starts from `client.js` and `server.js`; a workflow from `server.js` with a `run(input)` method. An app starts empty, as before.
- `classifyGadgetFiles(kind, files)` classifies a gadget's files for the kind and reports every rule they fail. It implements the shared classification matrix of the bound-view and callable-widget contracts. Its codes are:
  - the existing ones: `missingUi` (an app, or a widget with no `view.json` or `tools.json`, has no `client.js`), `missingServer` (a workflow, or such a widget, has no `server.js`) and `unexpectedUi` (a workflow has `client.js`);
  - in a widget: `mixedView` (`view.json` with any JavaScript module, a path ending in `.js` as `isGadgetModule` decides for both the classifier and the gadget loader, or `tools.json`), `invalidView` and `invalidTools` (the file is present and does not parse, whatever else the gadget has), and `toolsWithoutServer` (in place of `missingServer`);
  - in an app or workflow: `unexpectedView` and `unexpectedTools`, on the file's presence alone, since nothing is parsed outside a widget.

  When nothing fails it also names the class: `app`, `workflow`, or a widget that is `visualWidget`, `callableTools`, `callableCombined` or `viewOnly`. The parsers are injected. The default for `view.json` is `parseBoundViewSpec` (`bound-view.ts`, see [Operate mode](operate-mode.md#bound-views)), so a valid `view.json` alone makes a `viewOnly` widget. `tools.json` is parsed by `parseWidgetTools` (`widget-tools.ts`, see [Operate mode](operate-mode.md#callable-widget-tools)), so a widget with `server.js` and a valid `tools.json` classifies as callable. A widget with `tools.json` is also `invalidTools` when it has a top-level `tool-main.js` or `tool-guard.js` (`RESERVED_TOOL_MODULES`), the module names the kernel's tool runner reserves.

  A widget's `view.json` or `tools.json` stands in for `client.js` once it is **present**, not only when it is valid: an invalid one is reported as `invalidView` (unless it is a valid bound view) or `invalidTools` alone, never also as `missingUi` or `missingServer`. The contracts' "Rules behind the matrix" say "a *valid* `view.json` … stands in", but their matrix rows for an invalid file require this reading.

  **Compatibility.** A widget that ships a root `view.json` or `tools.json` as a data file (or a `tools.json` that is not a valid tool list) is refused at blueprint publish, as `invalidView` (unless it is a valid bound view) or `invalidTools`, with a message telling the author to rename the file. Files with these names in subdirectories are not affected.
- `checkWorkspaceKind(kind, filenames)` is the classifier given filenames alone. It is unchanged for gadgets with no `view.json` or `tools.json`.
- `blueprintPublishRefusals(kind, violations)` is what blueprint publish enforces: every violation for a widget, and only `unexpectedView` and `unexpectedTools` for an app or workflow. Their other codes were never enforced at publish (see [Operate mode](operate-mode.md#console-widget-registry)).

`GitStore.readCommitBlob(commitId, path)` (`git-store.ts`) reads one file of a commit as raw bytes. With `"text"`, it decodes them as strict UTF-8 and throws `BlobTextError` on invalid UTF-8 or a leading byte order mark. It returns `null` only when nothing is there, the path names a directory, or it runs through a file. A symlink or submodule anywhere on the path throws `UnsupportedTreeEntryError`, which `readCommitFiles` now throws too, so it is never read as absent. It has no size cap, so callers must cap the bytes before parsing. `readCommitFiles` still decodes non-fatally. Blueprint publish reads a widget's `view.json` and `tools.json` through `readCommitBlob`, so a file that is not strict UTF-8 is classified as not parsing. `readCommitPaths(commitId)` lists exactly the paths `readCommitFiles` would key, through the same tree walk and the same refusal of symlinks and submodules, without reading any blob. Classification lists a commit's paths through it and reads no other blob.

The agent's `writeFile` and `editFile` refuse `client.js` in a workflow workspace's gadgets (`workspaceKindAllowsFile`), so a workflow cannot gain a UI through the agent. Worktrees are exempt. The agent reads the kind once per turn through the `getWorkspaceKind` hook.

`AuthenticatedApi.newGadget(kind?)` creates a workspace of a kind, storing it before the workspace is returned. `newGadgetFromBlueprint()` does not take or carry a kind, so a workspace installed from a blueprint is an app until switched.

Behind the `operate-mode` UI flag (on in local development; also requires composable views), the frontend acts on the kind. The Build home page shows a kind picker (App, Widget, Workflow) above the composer. It is a Kumo `Radio.Group` of cards, so the keyboard pattern comes from Kumo: one tab stop on the chosen kind, arrow keys move to and select a neighbour and wrap at the ends, and Home/End do nothing (Kumo's radio group disables them, as the WAI-ARIA radio pattern does not define them). The chosen kind is set on the new workspace in the same batch as its first chat, ahead of it, so that chat's agent builds that kind. The workspace editor header shows a kind switch, with a confirmation step, for the build role. Apps get a Chat ↔ App toggle. Workflows replace the app preview with a Triggers panel listing their bound hooks (scheduled tasks register as hooks) and the pending-approval count. The workspace list shows a kind chip. The Build sidebar gains a Build | Operate toggle whose mode is derived from the URL: the InferOps Canvas routes are Operate, where console navigation lives in a separate operator shell (see [Operate session page](#operate-session-page)). Creating a workspace with a kind and publishing to Operate are designed in [operate-mode](../design/operate-mode.md) but not implemented.

## Operate session page

With Operate available, `/inferops-canvas` renders `OperateSessionPage` (`features/operate`), one tab's view of the person's operate session (see [Operate mode](operate-mode.md)). `OperateSessionProvider`, mounted around the shell, holds the single subscription and a `dispatch` that retries once on a conflict. A `consoleChanged` refusal means this tab's copy of a console is out of date (a builder removed a view, say), so `dispatch` re-reads the saved consoles (`invalidateWorkspaceScreens`) before rejecting: the sidebar drops the removed view, a removed current view shows *This view is no longer part of the console.*, and the toast (`refusalMessage`, shared by the page and the sidebar) says the console changed and now shows as saved. `OperateSidebar.test.tsx` covers this with a view removed from another client.

- **Console shell.** On the Operate landing route, `AppShell` leaves navigation to `ConsoleWorkspaceShell`. It does not mount the configuration sidebar or command palette. `OperateSidebar` holds All consoles, optional Assistant, the console's pages, widgets beneath the active page, and Settings. Its desktop collapse state is independent of the configuration sidebar; mobile uses a Kumo dialog with focus management. Page changes close the drawer. Configuration is reached through Settings only when the viewer has build access.
- **Launcher.** `ConsoleMosaic` shows up to eight real consoles per page in four desktop columns, two on smaller screens and one on phones. It never fabricates placeholder consoles. The shared assistant composer sits below the grid. Saved consoles return to the launcher and are highlighted on their page. Opening a tile opens the console's published revision (`openConsoleEvent(entry, 'published')`), what operators use. For a builder, each tile also shows its publication status (`publicationStatus`): *Draft* (never published; the tile previews it), *Unpublished changes* (the console was saved, or a screen it published was edited, since the last publish) or *Published*, with **Preview** (`openConsoleEvent(entry, 'draft')`) and **Publish** where there is something to publish. Publish confirms in `ConsolePublishDialog`, which calls `publishConsole` at the listed draft revision through the builder's own workspace capability and reloads the lists; a stale revision or missing access is reported and nothing is published (see [Operate mode](operate-mode.md)). After setup saves, the launcher says the console was saved as a draft and offers Preview and Publish. Screens and flows remains a secondary destination.
- **Console setup.** `ConsoleBuilder` offers workspace/name, reusable screens and ordered views, starting experience, and review. `ConsoleScreenEditor` uses the existing canvas controls and explicitly saves new screens through `createCanvas`; those screens remain after cancelling console setup. Console saves (*Create draft*, *Save draft*) use `createConsole` or revision-checked `replaceConsole`, which change only the draft. Missing references and failed saves retain the draft. Setup has human build authority; the Operate agent retains its restricted capability.
- **Settings.** `ConsoleSettings` stores independent opt-in `customization` flags for personal shareable screens, widgets, application tools, and skills. Older definitions default to disabled. Use-role viewers cannot change settings or reach configuration controls. Settings save to the draft, like setup. These flags record policy only: personal artifact storage, sharing, and extension installation are not implemented by this change, and flags grant no capabilities. Screens remain workspace-owned references reusable in multiple consoles within that workspace.
- **Widgets.** `ConsoleSettings` also edits the console's widget registry through `ConsoleWidgetRegistry`: it lists the registered widgets with their version and whether operators have them yet (the published registry has a frozen install of that gadget, version and label), removes one from the draft, and registers a widget install of the workspace (`installedFrom.kind` widget, not a frozen install) under a label once the builder ticks that its state may start empty on each publication. The kernel checks every entry again on save and publish (see [Console widget registry](operate-mode.md#console-widget-registry)). `ConsoleBuilder` shows the same editor under its screens step whenever the workspace has widget installs, so a new console can register the widgets its screens show before its first save, and both it and `ConsoleSettings` keep the registry when they save. The gadget pickers (`CanvasWorkspacePane`, `ConsoleScreenEditor`) leave frozen installs out. On a published console's screens, `ConsolePage` and `ConsoleWidgetView` pass the open revision to `CanvasView` / `CanvasGadgetWidget` as `offeredBy`: a frozen install there opens with `getConsoleWidget(consoleId, revision, gadgetId)` rather than `getGadget`, while other gadgets, such as installed apps, open as before; a previewed draft opens its gadgets directly, under the builder's access. `ConsoleWidgetView` reads its screen again when the session's revision changes (as when another tab reopens the console), so it moves to the new revision's frozen install.
- **Working set.** A focused standalone screen renders through `SessionScreen`; with nothing focused, the launcher shows the retained working-set links. `showHome` clears console/focus/flow while keeping the working set and conversation. Unavailable references never fall back to another screen.
- **Console content.** `findConsole` resolves the open console as the revision the session opened (`consoleRevision`): a builder's draft over the workspace's current screens, or the published console over the screens as published, which `useWorkspaceScreens` reads per published console (`getConsoleScreen`) apart from the workspace's screens. `ConsolePage` renders the selected page or rollup through the viewer's workspace capability, under a breadcrumb (`nav aria-label="Breadcrumb"`: console, view, screen, board). Its boards and Wiki resolve under the viewer's own authority (`CanvasView`'s `resourceScope`): through the console workspace's connections for a builder, and for a use-role operator through their own operate session workspace. There a board that is not connected shows `BoardConnectPrompt` instead of the generic *Not connected* note: it lists the operator's own connected accounts that can reach the reference (`subscribeConnectedAccounts` with `resourceUrl`), connects the board in the session workspace with the chosen one (`newGatekeeper`) and re-reads it, or, with none, links to connecting InferOps; a refusal (no grant for the project) is shown as InferOps gave it. The console owner's connection is never used for them. A board card's **Open** dispatches the session's `openBoard` naming that scope's workspace and the canonical reference, and `SessionBoard` then shows it full-page (`CanvasBoardFullView`) from the session state, keyed by workspace and reference so a switch starts from nothing and a late read of the previous board is never painted. Back and the browser's Back dispatch `closeBoard`. A board named through a workspace this viewer does not read boards from (for example the console's own, for the use role) is said to be unavailable, with Back. That alert is shown only once the workspace that could read the board is open: while it is still opening (the session state, and its board, comes back before the workspaces are reopened after a reconnect), the page shows *Opening the board…* as a status instead. Opening or closing a board moves focus to the page's `main`. `ConsoleWidgetActions` in the right assistant dock opens a referenced widget full-page or in a Kumo modal. When the open revision is no longer the latest of its kind (a newer one was published, or the previewed draft was saved again), the page says so and **Reopen** opens the latest at the same view if it still exists; the kernel refuses the stale session's next move meanwhile, and the refusal toast says to reopen. These widget selections are local presentation state, cleared by sidebar navigation; agent page navigation continues through `operatePage`.
- **Issue continuity.** The issue shown over the session board is session state too: `SessionBoard` hands `CanvasBoardWidget` an `openIssue` control (`OpenIssueControl`), `KanbanBoard` gives each card's edit dialog a controlled open state (`IssueDialogControl`), and opening or closing it dispatches `openIssue` / `closeIssue`. - **Browser history.** `useBoardHistory` mirrors the session's board and issue into the `/inferops-canvas` search params `board`, `boardWorkspace` and `issue`: a board or issue opened (from this tab, another tab or the agent) is pushed as a history entry, a close replaces the entry, and a browser Back or Forward is sent to the session as `closeIssue`, `closeBoard`, `openIssue` or the kernel-checked `openBoard`. The session stays the truth: a refused browser move puts the URL back to what the session shows. The params are references only and validated for length by the route.
- The agent can also open a board when no console is open; `OperateSessionPage` then shows `SessionBoard` over its session workspace, with Back to the consoles.
- **Subject bar (#64).** The shown board is the session's subject, so `SessionBoard` puts `SubjectBar` above it, keyed by workspace and reference so that switching subject drops the previous roster, audit and handover form. `useSubjectPresence` subscribes with `OperateSession.subscribeToSubjectPresence` while the board (and issue) is shown and disposes the subscription when either changes; the bar lists the other people on the board (never the viewer, and nobody until `whoami` resolves) and whether each is on the board, this issue or another one. **Hand over** opens a Kumo dialog for a recipient's user id and a note and calls `handOver`; refusals are shown by code (unknown recipient, board out of reach). **Audit** shows `SubjectAudit`: `listSubjectAudit` pages over the session's events and the workspace's action log entries for the board, merged newest first, with **Load older** while the cursor continues, and a refusal when the viewer can no longer reach the board.
- **Handover inbox.** `HandoverInbox` lists `state.handovers` under the page header. **Open** dispatches the person's own `openBoard` in their own session workspace, then `openIssue` when the handover names one, then `dismissHandover`; if that board is out of reach (`boardUnavailable`) it stays waiting and offers `BoardConnectPrompt` for the person's own accounts, retrying the open once connected. **Dismiss** sends `dismissHandover` only.
- **Shared chat.** One `OperateChatPanel` stays mounted across launcher, console, screen, and setup navigation. It restores the most recent conversation, preserving subscriptions and drafts while hidden during setup/settings. Assistant-first consoles show a centered greeting, composer, and navigation suggestions when the conversation is empty; selecting a suggestion shows the page with the same chat docked on the right. The dock is resizable by pointer or keyboard and has widget and close controls. On mobile the page and assistant alternate, with navigation always accessible. `operateOnly` hides chat-list and build-only controls.
- **Agent attribution.** `AgentActivityNote` identifies recent page changes made by the agent from the event log's actor; it never guesses from the resulting page.
- **Approvals.** `SessionApprovals`, above the main region, lists the pending actions (`useActions`) of the session workspace (what the operate chat proposed) and of the focused screen's workspace (what its board cards proposed), with each action's title, resource, attribution from `requestedBy` (*Requested by the agent*, and so on), time, and, while it is under review or the workspace is restricted, its full description and fields. It opens the focused screen's workspace with its own `openGadget` stub, one more besides `SessionScreen`'s, and leaves it out when the viewer's role is `use` or it does not open. Other workspaces in the working set are covered once focused, so at most two workspaces are watched. Opening an action dispatches `reviewApproval`. Approve and Deny call that workspace's `approveAction` / `rejectAction` through `decideApproval`, which then reads the action back with `listActions({beforeId: id + 1})` and reports only what the log shows: `approved` is `applied`, `rejected` is `rejected`, an action the log shows `failed` is `failed` with its recorded reason, an approval that threw with the action still pending and a known not-applied attempt is `failed` with the thrown message, and one whose attempt's outcome is unknown reports no outcome, only the warning. A refused rejection, or a decision whose result cannot be read back or still shows pending, reports no outcome and shows why. The outcome goes to the session as `approvalResolved` and to a polite `role="status"` line. The page's `lastApprovalOutcome` is shown with the action's own title, read from its workspace's log (`readAction`): one reported after the tab opened (another tab, device or the agent) is announced in that line, while the one the page held when the tab opened is history, shown outside the live region with its age (*· 1m ago*) and only for two minutes after the decision (`RECENT_ACTIVITY_MS`); a restored `failed` outcome is shown with the reason its action's log kept, since a failed action is no longer pending. The panel renders nothing when no covered workspace has a pending action and there is no outcome to show.
- **Truthful outcomes in the Workshop.** Action outcomes (see [operate mode](operate-mode.md), *Approval outcomes*) show what the log recorded:
  - `decideApproval` reports a `failed` action as `failed` with the reason it kept, and an action pending with an unknown last attempt as no outcome at all, only a warning that it may already have been applied.
  - In `SessionApprovals`, a pending item shows its last attempt (`attemptNotice`), so a reload no longer hides it, and a restored or remote failed outcome carries the logged reason.
  - Activity shows `failed` as *Failed* and an unknown attempt as *Outcome unknown*, never *Approved*, with the reason in the expanded row.
  - The chat card labels it *Failed, not applied*, and the approval toast keeps the reason.
  - Board activity has a `failed` kind, *approved but not applied*, and Kanban decisions show it with error styling rather than as a success or a rejection.
- **Board refresh.** A decision in the focused screen's workspace reaches `SessionScreen`'s own subscription, so `useDecidedActionInvalidation` re-reads the board as for any approval. A decision in the session workspace touches a board shown through another workspace, so `SessionApprovals` calls `useDecidedActionInvalidationInEveryScope`, which invalidates that board in every open adapter scope. Each scope re-reads through its own capability. - **Flows and the full-canvas state.** `WorkspaceFlows` on the canvas home lists each workspace's flows and authors them with `FlowEditor` (title, and screens in an explicit order). - **No coding.** Neither `SessionScreen` nor `FlowScreen` passes `codingDispatch`, so boards in the session and in flows offer no coding control and never look up a coding-dispatch connection, whatever the screen's workspace holds (see [Coding control surface](#coding-control-surface)).
- `useWorkspaceScreens` loads each workspace's screens, flows and consoles in one batch and is invalidated when any changes. ## Host-rendered board

A console's host boards (MVP-26 slice 2, see [host boards](operate-mode.md#host-boards)) are trusted host code in `features/operate`, shown only while `ServerConfig.hostBoards` reports `INFEROPS_HOST_BOARDS` on. That report grants nothing; the kernel checks the switch on every call. While it is off, no menu entry, dialog or editor section appears, and the editors still keep the saved entries. Console bound views have their own kernel switch, `INFEROPS_BOUND_VIEWS` (declared in `env.d.ts`, and on only while host boards are; see [bound views](operate-mode.md#bound-views)). `ServerConfig.boundViews` (`deployment-config.ts`) reports it, read only, like `hostBoards`. The kernel delivers a bound view as plain data (`OperateSession.getConsoleBoundView`, returning `BoundViewDescription`: the spec text, its commit and each requirement's host-board entry id), and a draft is read through the build-only `Overseer.getConsoleBoundViewDraft`. The UI that shows them is described under [Bound view](#bound-view).

- **Opening.** The assistant dock's widget menu (`ConsoleWidgetActions`) lists the open revision's saved host boards under *Boards* when `OperateSessionPage` passes `onOpenHostBoard`, which it does only with the switch on. Choosing one opens `ConsoleHostBoard` in a dialog, keyed by the run's console, revision and entry. The dialog shows only while the session still has that console revision open (same console, source and revision) and that revision lists the entry. Once the console is left, opened from another source or revision, or covered by settings, setup or tools, the board is closed for good, so returning to the same revision neither reopens nor re-reads it. A reconnect is none of these: the page and the dialog stay mounted through it (see *Reconnect* below). It also closes at once when the open revision is superseded: `OperateSessionProvider` keeps, as `staleConsole`, the run that a kernel notice (`OperateSessionUpdate.consoleRevision`, sent when the console is republished or deleted from anywhere) found stale, and re-reads the saved consoles (`invalidateWorkspaceScreens`). A run naming exactly that revision offers no board, so the dialog cannot reopen on it, and the reloaded list opens the console at its new revision. A notice for another console, or naming a revision no later than the run's (compared as numbers, `""` as 0, so an earlier publish's late notice cannot close a current board), changes nothing; a deletion's (null) always counts. Without trusting a notice, a current read answered `stale` or `unavailable` (`onStaleOrUnavailable`; never a superseded read's answer) also asks for the saved consoles to be re-read, through `recheckWorkspaceScreens`, which coalesces those asks because a selection change alone can cause them and each reload opens up to 48 workspaces: no reload starts while one is in flight or within 5 s (`RECHECK_FLOOR_MS`) of the last one's start, and asks meanwhile get one trailing reload. Once the reloaded list no longer shows the run's revision (republished or deleted with the notice missed) the dialog closes for good. Opening one dispatches no session event, so nothing about the board enters the shared session state. A console that shows only Assistant (`fullChat: 'only'`) has no widget menu, so it offers no board, and the page never opens one for it.
- **Wiring.** `useHostBoard` acquires `OperateSession.getConsoleHostBoard({consoleId, source, revision}, entryId)` for the run's `ConsoleRef`. It subscribes with `subscribeSelection`, and runs the state machine's reads (`readRequirement(<the entry's requirement name>)`) and timers. A `visibilitychange`, `focus`, `pageshow` or `online` event feeds visibility and resume. While a board is shown, a 5 s tick (`HOST_BOARD_TICK_MS`) rechecks expiry on both clocks, so a device that slept with the tab visible cannot keep a board past its wall-clock expiry until a late timer fires; the tick never reads early. A broken transport is not observed directly (no `onRpcBroken` is wired): the session's recovery replaces the session stub, which acquires a new handle (see *Reconnect* below), and a failed read or subscription meanwhile clears the board. The machine is held in a ref, and each event is stamped with `performance.now()` and `Date.now()`. A delivery of `unknown`, or a subscription that fails to start, ends it as a failed subscription: the board is cleared and authority is unknown. The hook then resubscribes after a backoff (2 s, doubling to 30 s), or at once on a resume or on the tab being shown. A late delivery on an ended subscription is ignored. Only the new subscription's snapshot and a fenced read can show data again. A refusal naming a console that is not open, a requirement the handle lacks, or `OPERATE_SESSION_CONSOLE_CHANGED` (of a read or of the selection subscription) invalidates the handle and calls `options.onRefused` once, and `OperateSessionPage` then closes the dialog and re-reads the saved consoles rather than leave it cleared. A `stale` answer is not a guard refusal (see below). Any other failure, an unrecognized message or a non-`Error` included, clears the board and shows the generic *unavailable* state; the cause is never shown or logged, and only the 30 s cadence, Retry or the tab being shown again reads again. The guard refusals are matched by their English text (the kernel throws them uncoded, `server.ts:712/725/733/769`), so a reworded one fails closed as *unavailable*. A change of context, or unmount, first drops the handle and any read in flight from the machine, so nothing settling later can land and the new context never waits on it. Context tokens only rise. It then disposes the subscription and the handle. The board is held only in memory.
  - **Read requests.** An optional `options.onRequest(readToken, sent)` is called with each read's token where the read is issued, synchronously and before its answer can arrive, so a caller can tag the read and later match the `ok` view's `read.token` against it. `sent` (`HostBoardReadSent`) is what the read was sent under: its context token, its generation and the selection's `changeSeq` (null while none is known). The hook also returns the latest delivery's `changeSeq`, so a caller can refuse a read whose selection changed since it was sent even when that change did not invalidate the board (a newer delivery with the same state and epoch). It is given no board data. A throw from it is dropped and the read is still issued. The host-board dialog passes none; a bound view's requirements do. `isGuardRefusal`, the guard-refusal matcher below, is exported for the bound view's description, which the kernel refuses with the same text. `options.onRefused` and `options.onStaleOrUnavailable` (above) are contained the same way.
  - **Context tokens** are minted from a module-scope counter, so they rise across remounts as well as within one mount. A remounted board, whose read tokens and generations start over, still never repeats an earlier `read` identity.
  - **Containment.** Nothing in the host-board hooks reaches the global error reporter (`errorReporting.ts`):
    - An event the reducer throws on resets the machine to `faultHostBoard`'s fixed state, which is *unavailable*, the same as an ordinary failed read. The handle is kept, the generation rises, the read in flight is dropped outright (so later requests are not stuck joining it, and its late answer is ignored), and the 30 s cadence or Retry reads again.
    - Timer callbacks (the refresh and expiry timers, the 5 s tick, the resubscribe backoff) and the `visibilitychange`, `focus`, `pageshow` and `online` listeners drop any throw, so none reaches window `error`.
    - Every promise chain in `useHostBoard` (the read and the selection subscription) and `useHostBoardSelection` (the selection call) ends in a terminal `.catch(() => {})` that never rethrows, so a throw inside a handler, for example the dialog's `onConnected`, never reaches `unhandledrejection` with its raw reason. `useHostBoardAccounts` already ended its one chain in such a catch.
- **Reconnect.** `main.tsx` replaces the RPC stub as soon as the socket breaks, with one whose calls wait for the replacement connection, and `useAuth` re-authenticates on it, so every `authenticatedApi` consumer gets a new stub at the start of the gap. When the replacement is for the same account, `FeatureFlagsProvider` keeps the flags it last loaded until the new stub answers (with `loading` set meanwhile), so the `operate-mode` gate in `AuthenticatedShell` holds and `OperateSessionProvider`, the page and its open dialog stay mounted. The same account is known from `useAuth`'s `accountKey`, an opaque object exposed through `AuthProvider` that stays the same while the stub is re-authenticated with the same token. A `whoami` user id would only be known after a round trip on the new stub, about when its flags arrive, so it cannot keep the gate up. Any other replacement gets the default flags at once (fail closed): another account (`useAuth` retrying with a different stored token after `whoami` rejects the current one), a new token for the same account, or an unknown account (CF Access has no token here, so `accountKey` is null). The defaults turn `operate-mode` off, which unmounts the provider, the page and its dialog, so nothing of the previous account stays on screen; the new account's operate session then mounts from nothing. Under CF Access a reconnect therefore still closes an open board, as before this fix. Before, the flags fell back to their defaults during the reload, which unmounted the provider and the page: the page flashed *Opening your operate session…*, and the remounted page had lost the dialog, so the board never came back (MVP-26 host-board pass, case 8). `OperateSessionProvider` does not rely on the flags for that: it mounts its state, and everything under it (the page and its `hostBoardTarget`), afresh for each `accountKey` (for each stub when the key is null), so no account's session snapshot or open board outlives a switch to another even if `operate-mode` were on by default. Across a same-account reconnect it keeps its last snapshot and its `staleConsole` (the kernel sends a republish notice once, so one that landed just before the blip still keeps that revision from offering a board), clears any subscribe error of the previous connection, and hands out the replacement session stub. `useHostBoard` treats that as a new context: the board clears at once, the old handle and subscription are dropped and disposed (a late answer on them is ignored), and a new handle is acquired for the same `ConsoleRef` and entry, whose subscription and reads wait for the connection. Once it is restored, only the new subscription's snapshot and a fresh read through the operator's own selection show the board again. If the restored session no longer has that console revision open (it was left, or reopened from another source or revision) or the reloaded list no longer shows the revision, the rules under *Opening* close the dialog for good. A dialog the operator closes, or a console they leave, during the gap stays closed, as at any other time.
- **Picker.** `HostBoardPicker` lists only the operator's own accounts whose credentials are valid for the entry's frozen target (`subscribeConnectedAccounts` with `resourceUrl`). The target filters and grants nothing. Choosing an account selects through `OperateSession.selectHostBoardConnection(consoleRef, entryId, accountId, requestKey)`. That choice (`useHostBoardSelection`: the `hostBoardPicker` latch, the request key, the chosen account and the outcome) lives for the dialog's lifetime, not the picker's. The kernel publishes `pending` as soon as it reserves the intent, which shows loading and hides the picker. A reply lost after that (the call threw) still offers *Try that connection again* beside the board, which sends the same account with the same key, so a duplicate creates no second connection. This holds across a subscription that ends and comes back `pending` too. After a settled `superseded` or `failed` answer, which the kernel would repeat for that key, the next choice is a new request. The board is read only after the subscription delivers the committed selection, so a superseded selection is never shown. The accounts (`useHostBoardAccounts`) stay subscribed for as long as the dialog is open, not only while the picker shows. A failed listing is its own state (*Could not list your InferOps accounts*, with no cause), never *no account*. Any account for that target that is added, removed or invalidated after the first listing clears the board and re-reads through the current selection; it never selects an account, and an overlapping read is superseded.
- **Editors.** `ConsoleBuilder` (Screens and views step) and `ConsoleSettings` show `ConsoleHostBoardRegistry` with the switch on. It lists the entries (label, target, published or not), removes them, and adds one from a canonical `inferops://<tenant>.<workspace>/project/board/<KEY>` target and a label, with the next free `board-<n>` requirement name and no id (the kernel mints it). On a console that shows only Assistant, the section says boards can't be opened there, marks its saved boards *Unavailable on an Assistant-only console*, and offers none to add; the builder's starting-experience step repeats that when such a console holds boards. Both editors save through `consoleContentForSave` (`consoles.ts`), which runs `parseOperateConsoleContent` over the boards the console will hold, so the combined limit with `widgets` counts saved boards too. It sends `hostBoards` only once they are edited (an empty list included), so an unedited save leaves the saved entries to the kernel, which keeps them when the field is omitted. `ConsoleWidgetRegistry` counts host boards (and bound views) toward the same `MAX_CONSOLE_WIDGETS` limit, and `ConsoleHostBoardRegistry` counts widgets and bound views.
- `hostBoardTypes.ts` holds only `HostBoardTarget` (an entry id and a `ConsoleRef`) and the non-terminal selection delivery. The board, read and selection shapes are the kernel's (`HostBoardView`, `HostBoardViewSnapshot`, `HostBoardSelectionUpdate` in `operate-console.ts`).
- `HostBoardView` renders a snapshot as text only, with the read time:
  - columns with label, group and count;
  - cards with identifier, title, priority, target date and a blocked badge.

  It shows *loading*, *not connected* with the picker, and *unavailable* with Retry (focus stays in the board). For unknown authority or a cleared view it shows nothing itself, and `ConsoleHostBoard` adds a status line. It has no links, frames or markup from data, and logs and stores nothing.
- `hostBoardState.ts` is a pure reducer with injected monotonic and wall clocks. It returns its effects (`read`, `set-timer`, `clear-timer`) as commands.
  - **Invalidation.** Every invalidation starts a new generation and clears the board: a context change or unmount, a handle refusal, an account or picker change, a newer selection epoch, a change of selection state, or a subscription failure. A context change also drops the read in flight.
  - **Reads.** Answers for an older token, generation or context are dropped unread. At most one read is in flight; requests coalesce into it, or queue one follow-up behind a superseded one.
  - **Selection states.** Deliveries are ordered by `changeSeq` alone, which the kernel raises on every change of a target's selection and never resets (`host-boards.ts:258/330/361/389`; slots are never deleted); an older or repeated one is ignored. `selectionEpoch` is not an order: a removal (`connectionRemoved`) is `none` with a null epoch, and a re-pick's `pending` carries the previous epoch or null. Any change of state or epoch, to null included, clears the board; `none` shows *not connected* and `pending` shows loading and reads nothing.
  - **Stale and refused answers.** A `stale` answer gets one immediate recovery read per generation, then only the 30 s cadence (paused while hidden) or Retry. A guard refusal invalidates the handle until a new context arrives.
  - **Expiry.** The deadline is fixed once at accept on both clocks: `min(t0 + 60 s, readAt + 60 s)`, with a future `readAt` clamped to the send. The board's remaining lifetime is the smaller of the two clocks' (a sleep pauses the monotonic clock, while the wall clock runs on). The expiry timer is armed for that at accept, and rearmed for it on every recheck. An answer already expired on arrival is refused, and so is any replacement that is malformed, for another revision, or expired; a refused replacement also clears the board it would have replaced. Expiry is rechecked at render, on the timers, on the 5 s tick while a board is shown, and on visibility, focus, pageshow and online events. A wall time below the latest one seen means the clock moved back. Combined with a monotonic clock that may have paused, the board's age can then no longer be bounded, so it is treated as expired, cleared and read again. The latest wall time seen detects that rollback; it does not prove how much time passed. A resume more than 30 s after `readAt` clears the board before re-reading.
  - **Authority.** It is unknown until the selection subscription delivers a snapshot. Duplicate or older `changeSeq` deliveries, and those of a replaced subscription, are ignored.
  - **Read identity.** The accepted board records the context token, token and generation of the read it came from. The `ok` view exposes them, with the accepted deadlines, as `read: {contextToken, token, generation, deadlineMono, deadlineWall}`. Every read has a new token, so a 30 s refresh at the same generation still names a new read, and the context token tells apart a remounted board's reads.
  - **Fault.** `faultHostBoard` is the fixed safe state the hook falls back to when the reducer throws: the board cleared, the read in flight dropped, a new generation, *unavailable*, and the refresh cadence rearmed while visible. The deadlines are the ones the expiry timer is armed from, so a consumer can run its own expiry timer. Nothing here changes how the dialog renders.
- `hostBoardPicker.ts` holds the selection's synchronous in-flight latch, its `requestKey` and its intent. After a lost answer, `retry` or the same intent (console, source, revision, entry, account) reuses the key. A settled answer, or any other intent, gets a new one. A completion after a context change or unmount is ignored.

## Bound view

A console's bound views (MVP-26, see [bound views](operate-mode.md#bound-views)) are trusted host code in `features/operate`: `ConsoleBoundView.tsx`, `ConsoleBoundViewRegistry.tsx`, and the `boundView/` subsystem (`evaluate.ts`, `contain.ts`, `frameGate.ts`, `BoundViewRenderer.tsx`, `useBoundViewCohort.ts`, `fixture.ts`, `BoundViewBuildPreview.tsx`). They show only while `ServerConfig.hostBoards` and `ServerConfig.boundViews` both report on; the reports grant nothing, and the kernel checks its own switch on every call. While either is off, no *Views* menu section, dialog, editor section or Build preview appears, and the editors keep the saved entries. A view's spec, as JSON that a fixed evaluator interprets, never runs; a view's data is each operator's own host-board reads, and reaches only the renderer's text nodes.

- **Opening.** The assistant dock's widget menu (`ConsoleWidgetActions`) lists the open revision's saved bound views under *Views* when `OperateSessionPage` passes `onOpenBoundView`. Choosing one opens `ConsoleBoundView` in a dialog, keyed by the run's console, source, revision and entry, under the host board's rules: it shows only while the session has that revision open and lists the entry, and is closed for good once the console is left, opened from another source or revision, superseded (`staleConsole`), no longer listed at that revision, or covered by settings, setup or tools. A guard refusal of its description or of a read closes it and re-reads the saved consoles; a current `stale` or `unavailable` read asks for the coalesced recheck. Opening a view closes an open host board, and opening a board closes the view. Opening dispatches no session event. A console that shows only Assistant has no widget menu, so it offers no view, and the page never shows one for it.
- **Co-residence.** While a view is shown, the page's whole main content region gives way to a fixed placeholder (*A view is open*): `FlowPage`, `ConsoleWidgetView` as a page, `ConsolePage` and its screens, `SessionScreen`, `ConsoleMosaic`, and the settings, setup and tools pages are all unmounted, and the modal `ConsoleWidgetView` and the host-board dialog are not rendered. That unmounts every `GadgetUI` frame the page holds (they come only through `CanvasGadgetWidget` and `ConsoleWidgetView`). The assistant chat stays: its one transient frame (the connection-accept `GatekeeperModal`'s `SandboxedResourceConfigurator`) is the frame gate's to block.
- **Description.** `useBoundViewCohort` fetches `OperateSession.getConsoleBoundView(consoleRef, entryId)` once per context token and session (a request of a superseded session, after a same-account stub swap, is ignored whether it answers or is refused, so it can neither mark the description unavailable nor close the view; on a reconnect, though, the old session usually fails its pending request before the stub is swapped, which no superseded check can catch, so each new request first returns an `unavailable` description to `loading` (`retryDescription`) and the new session's answer is accepted, while a failure of the current session's request still sticks), re-parses `specText` with `parseBoundViewSpec`, and accepts it only when it names this console and entry, its requirements are exactly the spec's, and each is served by one of the console's host boards; anything else shows *its definition is not valid*. A description requested under an older context token is ignored. It is kept across every other signal (account, selection, expiry, the gate), so a draft preview never moves to a newer Build commit on its own; the preview names its commit. **Refresh preview** (drafts only) mints a new context token and, inside the click handler, clears the description, every accepted read, the caches and the dedicated root, then fetches again.
- **Requirements.** For each requirement, one child (keyed by the context token and the name) runs `useHostBoard`, `useHostBoardAccounts` and `useHostBoardSelection` for the host board that serves it, exactly as the host-board dialog does, with the picker for *not connected* and Retry for *unavailable*. A child renders that board's status only, never its data, and offers its current view to the cohort after every commit.
- **Cohort** (`BoundViewCohort`). An epoch, from 1, and a context token. Each read is tagged where it is sent (`onRequest`) with the current epoch and what it was sent under. An `ok` view is accepted only if the gate is clear, the description is ready, it was read for this console revision, its tag is the current epoch with the same hook context token and generation, the selection's `changeSeq` is unchanged since it was sent, and it is unexpired. A same-epoch 30 s refresh is a new read token, so it is accepted as a new snapshot set. An accepted read stays accepted when `changeSeq` later moves on its own; that is intended, since a change that matters invalidates through the selection signal. An `ok` view never accepted only because it was sent under an older epoch or `changeSeq` (a `changeSeq`-only bump does not invalidate the host board) makes that child alone read again, once per read, as soon as the gate is clear and the description ready, rather than waiting for its next scheduled read. While anything is missing the view says *Waiting for a fresh read of every board this view uses*. `invalidate(seenEpoch)` raises the epoch only when `seenEpoch` is current, so N children reporting one change raise it once and a stale signal raises nothing (a fresh read in flight is then still accepted). Raising clears every accepted read and the evaluation cache, tears the dedicated root down, and sends `invalidate` to every child, which re-reads under the new epoch. A child signals at the epoch it last rendered with; its unmount only unregisters, so a clear cannot loop. The signals are an account change or a connection choice in any child, a guard refusal, a child's accepted read replaced by anything the cohort cannot accept (its selection changed, or its own 5 s tick or render found it expired), the cohort's own deadline timer at the earliest accepted deadline, its own 5 s tick (`HOST_BOARD_TICK_MS`), `visibilitychange`, `pagehide` and `online`, the frame gate, a refresh, and the view's own unmount. The requirements are read independently: each read is fenced, but together they are not an atomic snapshot.
- **Snapshot sets.** A snapshot set is `(epoch, (contextToken, commitId), each requirement's read identity)`. Each is evaluated once, with a fresh `Budget`, and cached; re-renders within it run no query. A set with an expired read is never evaluated or rendered: expiry is rechecked when rendering, so even a suppressed timer cannot leave an expired read on screen.
- **Evaluator** (`evaluateBoundView(spec, snapshots, budget)`, pure and total). It first revalidates each snapshot against `HOST_BOARD_SNAPSHOT_LIMITS` and the field tables, reading own data properties through their descriptors (no getter runs) into host objects; a failure, or a missing requirement, is `invalid`, before anything is charged. Fields are read through a closed switch, never by an authored property name. Semantics: filter, then a stable bottom-up merge sort (`mergeSort`, never `Array.prototype.sort`), then limit (default 50), then group-by in first-appearance order with each group's count of limited rows; `count` counts before any limit; nulls sort last both ways; strings compare by UTF-16 code unit; ties keep column, then issue, order; enums sort in member order and show through constant tables (*Urgent* … *No priority*, *Backlog* … *Cancelled*), booleans as *Yes*/*No* (*Blocked*/*Not blocked* as a group), a null date as *No date*. A badge looks its value's canonical string up with `Object.hasOwn` in the spec's null-prototype map, else shows that text in the neutral tone. Every budget line of `BOUND_VIEW_BUDGETS` (8,000 row visits, 176,000 key comparisons, 500 groups, 11,077 elements, 2,000 cells, 1,479,104 code units of text; the contract's §2.3 values) is charged before the work it pays for, and the work is recorded against it (`charge`, then `spend`); either check failing is `too-large`, with nothing partial. Row visits are charged per query before the scan; comparisons as n × `where` clauses before filtering and n⌈log₂ n⌉ × sort keys before sorting, with the comparator counting every key comparison against that allowance; a row's cells, elements and text (measured from the snapshot's string lengths and the authored leaves) before its nodes are built; a group before its header. The elements limit is 1 wrapper + 16 queries × 24 + 48 other nodes × 4 + 500 rows × 1 + 2,000 cells × 4 + 500 list sections × 4 = 11,077, and the text limit 2,000 cells × 701 + 500 group headers × 112 + 8,192 + 64 nodes × 201 + 16 counts × 3 = 1,479,104. Elements are the DOM elements `BoundViewRenderer` emits, charged exactly from a constant table (`ELEMENTS`) of what each node, section, group header, row, leaf and cell renders; text is every code unit it emits, including the space between a label and its value, with only a group header's count and separator charged at their bound. A maximum legal spec over four maximum boards trips nothing (every query visits all 500 issues, exactly the row budget).
- **Renderer** (`BoundViewRenderer`, in its own React root). `mountBoundRoot(container, site)` appends a new element and creates a root on it whose `onCaughtError`, `onRecoverableError` and `onUncaughtError` (`boundRootOptions`) drop the error and send only the constant failure report; inside, an error boundary renders nothing on a render error. The main root's options are unchanged. It renders fixed Kumo and host elements: every label and value is the text child of a `<bdi>`, classes and badge variants come from constant tables keyed by evaluated enums, and React keys are positional. No value reaches an attribute (`href`, `src`, `style`, `class`, `id`, `aria-*`, `on*` or any other), nothing becomes a link, image or frame, and there is no `dangerouslySetInnerHTML`.
- **Teardown.** The cohort keeps the root and its container (a `<div data-bound-view>` with no class, attached through a ref callback because the dialog mounts its content after the view's first commit). From a timer, the observer, an event or a promise callback (the deadline timer, the tick, the listeners, a gate change, an account or selection signal, a guard refusal, **Refresh preview**), `boundRoot.unmount()` runs synchronously in that callback, so the container is empty when it returns. Where the change is seen in render or commit (a child's view leaving `ok` on the host board's own tick, an expiry found while rendering, the view's own unmount), the container is hidden with an inline `display: none` (which no stylesheet rule overrides) in the layout phase, and the root is unmounted in a microtask, since React defers, with a warning, an unmount requested while it renders. A new root is created only for the next renderable snapshot set.
- **Frame gate** (`watchFrames`, `findFrames`). Before the first search, and while it finds any `iframe`, `frame`, `object`, `embed` or `fencedframe` in the document or, recursively, in any open shadow root found through `element.shadowRoot`, no read is accepted and nothing is evaluated; the view says *Close the other window or widget to see this view*. A `MutationObserver` on the document element, and one on each open shadow root found (which a document observer cannot see into), triggers a full search on every callback, ignoring the records; each search attaches observers to new roots and detaches them from gone ones, and the cohort's tick searches too. A frame appearing invalidates the cohort and unmounts the root at once; its going away invalidates again, so only fresh reads are accepted and the view is never stuck. Closed shadow roots cannot be searched; no frontend, shared UI or Kumo code creates any.
- **Containment.** Bound-view code sends no telemetry. Every promise, event handler, effect body, subscription callback and evaluator call goes through `contain(site, fn)`, which catches a throw or rejection and sends only the constant `{type: 'BoundViewFailure'}` to a local site: the view's fixed *could not be shown* state, which clears everything until it is reopened. The reused host-board hooks were brought inside the claim by #203 (see [Host-rendered board](#host-rendered-board)).
- **Editors.** `ConsoleBuilder` and `ConsoleSettings` show `ConsoleBoundViewRegistry` with both switches on: it lists the entries (label, the boards they read, published or not), removes them, and registers a widget install with a label and the host boards it reads (which must be exactly its `view.json` requirements; the kernel checks that, and that the install is view-only). An Assistant-only console marks its views unavailable and offers none to add. `consoleContentForSave` takes the bound views as saved or edited, like the host boards, so an unedited save omits them and the kernel keeps them, and the combined limit and their requirement names are checked against what the console will hold.
- **Build preview.** In a widget workspace whose selected gadget's committed head has a `view.json` (`useBoundViewSource`, through `readFilesAtCommit`), `GadgetEditor` shows `BoundViewBuildPreview` in place of the gadget's UI. It parses and evaluates the text live inside `contain` (a throw is its fixed *could not be shown* state), lists problem codes and spec paths (never values), and renders a valid spec with the real renderer, in its own dedicated root, over `BOUND_VIEW_FIXTURE`, a made-up board labelled as sample data, for every requirement. Real board data appears only in a console's draft preview in Operate, read with the builder's own connection.

## InferMind Wiki widget

`CanvasWikiWidget` renders an `inferops.wiki` widget ([#87](https://github.com/factory-level/inferos/issues/87)): one InferMind workspace's Wiki, read through the workspace's own Wiki connection (`inferops://<tenant>.<workspace>/knowledge/wiki`, the gatekeeper's `knowledge/wiki` resource; see [InferOps gatekeeper](inferops-gatekeeper.md)). `CanvasView` renders it for that kind; edit mode shows only its reference and first page (`CanvasWidgetCard`), and each section in edit mode offers **Add Wiki** (a reference and an optional first page slug) when the catalog enables the kind.

- **Store.** `WikiData` (`wikiData.ts`) mirrors `CodingDispatchData`: it resolves the canonical reference through `Overseer.getGatekeeperByResourceUrl` and `openSession()` (client disposed at once, session cached, forgotten after a failed read, and disposed with the instance), so the reference authorizes nothing. It holds the page list, the Wiki structure (`readStructure`, read beside the list and re-read with it), the pages read (by slug), the section edits and the page body edits proposed here, as one immutable snapshot for `useSyncExternalStore`. A per-read clock lands only the newest read of the list, the structure or a page. A structure read that fails without losing access is its own `error` state (or, after a successful read, the last structure with its error), so the page list and pages stay readable. States: `unbound` (no connection; the cue to connect, never a connect action), `disabled` (`DISABLED`, connection kept), `error` with the gatekeeper's code (`FORBIDDEN` and `UNAUTHORIZED` read as *No access to this Wiki*), a missing page (`NOT_FOUND`), and a failed refresh that keeps the last read with its error. Lost access (`FORBIDDEN`, `UNAUTHORIZED`, the connection removed) and `DISABLED`, from any of these reads, drop every page read and the structure, and invalidate the list and structure reads still in flight, so nothing read under a revoked grant stays on screen or lands later. `useWikiData` holds one instance per widget and re-reads the Wiki when an action whose resource is the Wiki leaves `pending` in the action log (`useActionEntries`), whoever decided it.
- **Navigation.** `wikiNavigation` (`wikiPage.ts`) and `WikiNavigation` show an organized Wiki by its structure: the company root, then each pillar's Master in `position` order with the pages it files beneath it, then *Unfiled pages*. A page filed in several pillars is listed under each, marked *Shared* (accessible name *…, filed in several pillars*); every entry selects the page by slug, so either opens the same page, read once, and both entries are `aria-current`. A pillar whose Master cannot be opened is a plain label over its pages. The list decides what can be opened: a structure page the list does not hold is left out, and a listed page the structure does not place joins the unfiled pages rather than being hidden. A Wiki with no root and no pillars, or whose structure is not read, is navigated by the page tree as before: `wikiTree` orders pages by `parentId`, then `siblingOrder` and title; a page whose parent is not listed, or that sits in a parent cycle, is shown at the top level rather than hidden. A failed structure read is an alert (*Could not read how this Wiki is organized, so its pages are shown as a tree*) above the tree. The widget opens the chosen page, else `params.page`, else the root (or the first Master or filed page, or the first unfiled page; the first top-level page of a tree). The default waits for the structure read to settle, so it never jumps from the tree's first page to the root. A slug the list does not hold is reported (*not in this Wiki, or you cannot open it*) and never read.
- **Page contract.** The page renders as the gatekeeper's page contract composes it (`authoredContent`, `masterStructureText`, `composeDocumentText` from `gatekeeper-inferops/src/wiki.ts`, imported, not copied), which is also what `readDocumentText` gives an agent and what the InferMind reader shows. A page with a body renders the body (`WikiPageBody`, without a leading heading repeating the title; any other heading is kept) and never its sections, which are separate, lens-gated index text. A page without one renders its sections (`WikiSection`). A Master then shows its generated block in a region labelled *Generated from the Wiki structure, not editable*: the pillar list for the root, the filed pages for a pillar's Master. While the structure is unread it says so, and a failed read is an alert. Links in Markdown that are Wiki routes (`/wiki/<encoded slug>`, `wikiPagePath`, as the generated block writes them; `wikiPageSlug` reads them back) are buttons styled as Kumo links that select that page in the widget, never a browser navigation. Bodies, sections and generated blocks render as Markdown through `WikiMarkdown` (the frontend's existing `react-markdown` and `remark-gfm`): raw HTML is skipped, URLs pass react-markdown's own sanitizer (only `inferops://` is let through it, as a title), only http(s) links become anchors, and images are shown as their alt text and never fetched. `[[target#tag]]` links stay as written.
- **Embeds.** `sectionBlocks` splits a body or section on blank lines and treats a paragraph as an embed by the gatekeeper's own rule (`embeddedReferences` from `gatekeeper-inferops/src/wiki.ts`, imported, not copied), so the page embeds exactly the references the gatekeeper reports as `WikiDocument.references`. `parseWikiReference` names each: `project/board/<KEY>` (optional `workflow`) renders `CanvasBoardWidget`, the live Kanban with its moves and edits; `project/issue-card/<KEY>-<n>` renders `WikiIssueEmbed`, which reads the issue's project board through `useBoardData`; `knowledge/document/<slug>` of the same Wiki (a slash slug encoded as one segment, `%2F`, parsed by the gatekeeper's `parseWikiDocumentUrl`) opens that page, and of another Wiki shows its text; anything else shows as an unsupported reference with its text. Board and issue embeds go through the scope's shared board adapter, so they resolve only where the workspace holds a connection to that board's exact reference (another tenant or workspace has none and reads *Not connected*, showing nothing of the target), share the Kanban's reads and pending changes, and show the issue's identity, state, priority, revision and pending marker exactly as the Kanban card does. Each embed has its own state, so one that fails (an alert with **Try again**) or is missing (*not on the board; it may have been deleted or moved*) leaves the others rendered.
- **Section edits.** With `editable`, each section of a page without a body has an **Edit** button (*Edit section purpose*) opening an inline `InputArea` with its Markdown; **Propose edit** calls `updateSection(sectionId, body, version)` with the version the page was read at, the gatekeeper's approval path (`inferops.wiki-section-update`). The edit is `proposing` while the call runs and `awaiting` once queued (*Waiting for approval, not saved yet*); the page is re-read either way. Only a page read started after the edit was queued decides it (`reconcileEdit`): the gatekeeper's overlay (`pending: "update"` at the unchanged version) keeps it awaiting, a new version with the edit's body is `applied` (*Saved*), the unchanged version without the overlay `rejected` (*Rejected, not saved*), and a new version with another body or a vanished section `stale` (not saved). A refusal (`STALE_REVISION`, `CONFLICT`, `FORBIDDEN`, `NOT_FOUND`, `DISABLED`) is an alert that keeps the draft, and the page is re-read. A section with a pending edit, from here or elsewhere, offers no Edit. Outcomes are announced in a per-section polite `role="status"`. `editable` is passed only by `InferOpsCanvasPage` through `CanvasWorkspacePane`'s `wikiEditable`, as `codingDispatch` is.
- **Body edits.** With `editable`, a page's body can be edited when the page is not a Master, or is a Master with a body (a Master without one reads only as its generated block). **Edit page body** (or **Add page body** on a page without one, whose editor says that once it has a body the page reads as its body and its sections are no longer shown) opens `WikiEditForm`, the inline editor `WikiSection` also uses, on the raw body. **Propose edit** calls `updateDocumentBody(page.id, body, page.version)` (`inferops.wiki-page-update`). It is decided as a section edit is (`reconcileBodyEdit`): `proposing`, then `awaiting` while a later read shows the gatekeeper's `pendingBody` overlay at the unchanged version, then `applied`, `matched`, `rejected` (the same version without the overlay) or `stale` (a new version with another body). A new version with the edit's body is `applied` (*Saved*) only when this session also saw the edit's own approval approved: `WikiData.noteAction` binds the first pending action log record for this Wiki titled `bodyEditActionTitle(page.title)` (the gatekeeper's *Edit Wiki page <title>*, since the proposal returns no action id) while the edit is open, and only that record's approval counts. Otherwise it is `matched` (*The page now has this text*): another writer may have set the same text, which fails this approval's compare-and-swap, and the page read cannot tell the two apart. A pending body edit whose proposed body is empty says that approving it removes the page's body, from a reload and read-only too. Refusals (`STALE_REVISION`, `CONFLICT`, `FORBIDDEN`, `NOT_FOUND`, `DISABLED`) are alerts worded for the page (`editErrorText(edit, 'page')`) that keep the draft, and the page is re-read. A page with a pending body edit, from here, another session or before a reload, offers no edit and shows *Body edit waiting for approval*. Outcomes are announced in a polite `role="status"` (*Page body: Saved*).
- **Agent view.** The **Agent view** toggle shows `WikiAgentText`: the page as an agent reads it (`readDocumentText`, through the same connection, an observation in the action log), re-read whenever the page read changes, beside a badge saying whether it equals the text composed from what is shown (`pageText`, the gatekeeper's `composeDocumentText` over the shown body or sections and, for a Master, its generated block). The agent text is InferOps' own (`document.text`), so for a Master it ends with the documentation coverage block computed with the person's own access; the panel shows it, and the comparison leaves it out (`agentTextShown`).
