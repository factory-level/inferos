# Persistent stage deploys

## Overview

`scripts/stage/` deploys this checkout as a long-lived instance on the account named by `CLOUDFLARE_ACCOUNT_ID`, with the pinned Wrangler and its login. Stages are defined in `scripts/stage/stages.ts`:

| Stage | Hostname | InferLab API / central auth |
| --- | --- | --- |
| `dev` | `dev-os.factorylevel.dev` (sign-in proxy `auth.dev-os.factorylevel.dev`) | `https://api.dev.inferlab.io` / `https://auth.dev.inferlab.io` |
| `prod` | `os.factorylevel.dev` | `https://api.inferlab.io` / `https://auth.inferlab.io` |

- **Real deploys, not Worker Previews.** Each package is deployed with `wrangler deploy` as `<workerPrefix><package>` (`inferos-dev-…`, `inferos-prod-…`), with every service binding renamed to match and binding names unchanged, so the router and backend discover gatekeepers exactly as they do elsewhere. The prefix is part of a stage's identity: Durable Objects belong to the worker name, so changing it starts an empty instance. `stage-config.ts` builds every config from the committed `wrangler.jsonc` files, reusing `backendGatekeeperServices`/`routerGatekeeperServices` from `scripts/preview/staging-config.ts` with a worker-name mapper; it writes a gitignored `wrangler.stage-<stage>.jsonc` beside each.
- **Topology.** Tiers deploy gatekeepers concurrently, then the backend, then the router. Only the router is reachable, at the stage hostname as a custom domain, plus, on a stage with `inferops.authorizeOrigin`, the InferOps gatekeeper at that origin's hostname (`stageWorkerHost`); every worker sets `workers_dev: false` and `preview_urls: false`, and the deploy fails when Wrangler reports any other target (`WRANGLER_OUTPUT_FILE_PATH`). Gatekeepers are `BASE_URL=https://<host>/gatekeeper/<short>`, and the context gatekeeper's `sharingDomain` is the stage origin.
- **Gatekeepers.** A stage deploys only the gatekeepers it lists: `gatekeeper-inferops`, `gatekeeper-context`, `gatekeeper-scheduler` and `gatekeeper-mcp`, the ones that need no third-party OAuth app. Others are neither deployed nor bound.
- **InferOps resource kinds.** The InferOps gatekeeper always offers boards and the Wiki. Its optional kinds (custom tables, members, workflow policy) are on only where the stage lists them in `inferops.resources` (`INFEROPS_OPTIONAL_RESOURCES` in `stages.ts`), and every switch is written as `true` or `false`. `dev` lists `tables` and `workflowPolicy`: dev InferOps serves custom tables since its `objects.enabled` went on ([inferops#2535](https://github.com/factory-level/inferops/pull/2535)), and its grokbot tenant has a fictional `equipment` table to bind. `prod` lists none. A kind that isn't offered is left out of the gatekeeper's supported resources, so Configure refuses a blueprint binding to it: "The required resource type for this binding isn't offered by InferOps." Before FAC-149 every stage had all three off, which is why the Records and workflow-policy blueprints were refused on dev-os. Turning a kind on grants nothing: every call is still the person's own InferOps authority.
- **Sign-in.** Cloudflare Access protects the hostname at the edge only. The backend gets no `CF_ACCESS_*`, because with `CF_ACCESS_AUD` set it takes the Access identity and refuses every other login; instead it gets `AUTH_GATEKEEPERS=inferops` and `DISABLE_PASSWORD_AUTH=true`, checked with `inferLabLoginStartupError` before deploying, and the frontend is built with `VITE_CF_ACCESS_MODE=false`. Both stages also get `SHARED_CONFIGURATION_GATEKEEPER=inferops`, so only a person whose InferOps grant holds `configuration:build` / `configuration:publish` (an Admin) edits or publishes a shared workspace (see [Operate mode](operate-mode.md#shared-configuration)). The InferOps gatekeeper gets `INFEROPS_BASE_URL`, `INFERLAB_AUTH_ORIGIN`, `INFERLAB_AUTHORIZE_ORIGIN` when the stage has an `authorizeOrigin`, `INFEROPS_ENABLED=true`, and every optional switch stated: coding dispatch, custom tables and members `false` on both stages, workflow policy `true` on `dev` only (see the resource kinds above), and every optional switch `false` on `prod`. The local-development stopgap (`INFEROPS_API_TOKEN`, workspace id/slug, mock seed) is refused.
- **Company (FAC-160).** Each stage names the one company it belongs to in `inferops.company`, written to the gatekeeper as `INFEROPS_COMPANY`: an InferOps tenant id, or `internal` (InferLab's own, reserved tenants only). `stageDefinitionProblems` refuses anything else. `dev` and `prod` are both `internal`. A wrapper stage takes it from `inferops.tenantId` in the wrapper's `inferos.deploy.json`, which is required, must be a tenant id and is never `internal` (`parseWrapperDeployment`). InferOps enforces it from its own `auth.sso.inferosCompanies` entry for the stage's origin, so the two must agree; InferOps refuses everyone for an origin it has no company for (see [InferOps gatekeeper](inferops-gatekeeper.md)).
- **Sign-in proxy (dev).** Dev InferLab's Cloud Armor admits only allowlisted addresses and the edge header, so a browser elsewhere (an external test agent) cannot open central-auth. `dev` therefore sets `inferops.authorizeOrigin: https://auth.dev-os.factorylevel.dev`: the gatekeeper sends the sign-in popup there and forwards central-auth's browser legs (the sign-in page, the persona form, `/logout`, and the Google edge's sign-in start and callback) to InferLab with the edge header (see [InferOps gatekeeper](inferops-gatekeeper.md#sign-in-proxy)). `stageDefinitionProblems` requires it to be a bare https origin on a hostname of its own. Each sign-in there asks InferLab to show the sign-in page again (`prompt=select_account`), so the persona picker is shown every time and a person can switch persona by reconnecting, without ending the session behind accounts already connected through that hostname. This needs an InferLab with factory-level/inferops#2528, and Google sign-in also needs the hostname in InferLab's `auth.sso.proxyOrigins` and its callback on the Google client. The page exposes the persona picker, so the hostname must be in the stage's Access application.
- **Backend.** `PUBLIC_BASE_URL` is the stage origin, `COMPOSABLE_VIEWS` and `DURABLE_VIEWS` are on, `CANVAS_CATALOG` comes from `inferos.canvas.json` when the checkout has one, and the `WORKERS_AI` binding is injected as in the manifest and previews.
- **Resources.** KV namespaces are titled `<resourcePrefix><package>-<binding>`, found by title with `wrangler kv namespace list`, created when missing and bound by id; the R2 bucket is `<resourcePrefix>blueprint-content`, which Wrangler creates on first deploy. Committed Durable Object migrations pass through unchanged; a step that deletes, renames or transfers a class is refused unless `--allow-destructive-migrations` is passed.
- **Secrets.** `ADMINS` (from `STAGE_ADMINS`, required) and the optional AI Gateway settings (`resolveAiGateway`) are uploaded with the backend's version through a temporary `--secrets-file`; no value is written to a config, argv or the plan. The InferOps gatekeeper's optional `INFEROPS_EDGE_SECRET` (`stageInferOpsGatekeeperSecrets`, validated as `[A-Za-z0-9_-]{32,}` without printing it) is uploaded the same way with that gatekeeper's version, and the plan names it on that worker's line. Unset, no secrets file is passed to the gatekeeper, so the deploy keeps any value an earlier version held. Inputs come from the shell, then a gitignored `.stage-<stage>.vars`.
- **Checks.** `--dry-run` prints the plan with no network. `prod` deploys only from a clean tree; `dev` needs `--allow-dirty` for one. After the router deploys, an unauthenticated request to every stage hostname (`stageHostnames`: the stage's, and the sign-in proxy's) must be an Access login redirect, or the run fails saying the stage is exposed; on a first deploy the probe retries name-resolution failures (`ENOTFOUND`/`EAI_AGAIN`) for up to five minutes while the new custom-domain record appears (`retryWhileDnsPending`, `scripts/stage/stage-resources.ts`); with `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` set it then runs `runSmoke` against the stage's gatekeepers. `pnpm stage:delete <stage> --confirm <hostname>` deletes the workers, router first, and prints the exact KV namespaces and R2 buckets retained. Worker deletion also destroys that stage's Durable Object storage. No export or KV/R2 deletion is performed; for a real stage, a person must export and delete only the printed KV/R2 names in the matching Cloudflare account.
- **A company's own InferOS (FAC-161).** A wrapper repository commits `inferos.deploy.json` (`schemaVersion: 1`, `company`, `hostname`, `inferops: {baseUrl, authOrigin, authorizeOrigin?, resources?}`), and `pnpm inferos:deploy [config|deploy|delete] [--dry-run]` in the wrapper runs the pinned checkout's `stage.ts <command> --wrapper <root>`. `wrapper-stage.ts` turns the file into a `StageDefinition` with the persistent stages' own rules (`stageDefinitionProblems`) and gatekeepers, a clean tree always, and names derived rather than chosen: worker and resource prefix `inferos-<company>-`, stage name `company-<company>` (so `wrangler.stage-company-<company>.jsonc`), inputs from the wrapper's gitignored `.inferos-deploy.vars`. The company slug is 2 to 31 lowercase letters and digits with no hyphen, so no company's prefix starts another's, and `dev`, `prod`, `staging`, `preview`, `test`, `local` and `disposable` (the deploy recipe's ephemeral names) are reserved. Every hostname the stage serves (`stageHostnames`: the router's and a sign-in proxy's custom domain) is compared with every persistent stage's, and an overlapping prefix is refused. For a wrapper, an input set in both the shell and `.inferos-deploy.vars` to different values is refused by name (`conflictingInputs`), so another stage's exported value can't deploy into a company.
  - **Company storage (FAC-162).** `pnpm stage:company-storage plan --manifest <local-manifest>` reports the selected company's KV/R2 resources, export allow-list, name-only withheld resources, workspace export surface, gadget DO inventory, and the fact that remote deletion is not performed. `export-local` reads only keys and objects under the manifest's delimiter-terminated company prefix and exports only resources named in `resources.exportKv` and `resources.exportR2`; missing lists export nothing. It invokes the kernel's allow-listed workspace export. **Gadget storage** (`gadget-state.ts`): a gadget is a Durable Object facet of its workspace's Overseer, and a parent can't read a facet's storage without running the gadget's code, so `export-local` reads what local Miniflare persisted once the runtime has stopped: each Overseer's `<id>.facets` index (an 8-byte header, then per facet a little-endian u16 parent and u16 name length and the name, facet n stored as `<id>.<n>.sqlite`) and the `_cf_KV` table of each facet the kernel lists as a gadget (`exportWorkspaceRecords().gadgets`). It reads copies, never the company's own files, and refuses a workspace with no state in this company's directory. Only keys `resources.exportGadgetState` names for the gadget's blueprint (`[{ blueprintId, keys: { <key>: <rule> }, clearNames?: [<name>] }]`), matched exactly, are exported, and only when the value meets its rule: `number`, `boolean`, `timestamp`, `uuid`, `issueKey`, `revision` (the same strict formats as the kernel's), `actorId` (written only as a per-export salted SHA-256, as the kernel hashes actor ids) or `text` (in clear, for text no person writes). Every other key is withheld with the reason, and **its name is a per-export salted hash** (`hashed: true`) unless the manifest lists it: a key with a rule, or a name in `clearNames`, which a person has checked isn't personal. Gadget code chooses its names, so no pattern of name is trusted; a gadget built from scratch has no blueprint, so all its names are hashed. A gadget's SQL tables are listed by row count and named the same way; gatekeeper facets (`gatekeeper<n>`) and nested facets are named, never read, and any other facet name is hashed. The document carries a `structureDigest`: the export without its creation time, with every salted hash replaced by its order of first appearance, so a rerun over the same data gives the same digest though each export salts afresh. **Paths are contained by real path.** `stateDirectory` and `workerConfig` must exist, be absolute, hold no `..`, resolve inside the real wrapper root, and pass through no symbolic link between the root and themselves, even one that stays inside (`containedRealPath`). Each is **pinned** as it is checked: the `lstat` identity (`dev`, `ino`) of the root and of every component down to the path (`pinContainedPath`). Right before each use (the Wrangler bundle, Wrangler's config read, Miniflare's start, the gadget storage read after the runtime stops, and `purge-local`'s delete) the path is checked again and every identity compared (`verifyPinnedPath`); a path that no longer resolves to itself, or any part that is now another file or a symbolic link, is refused with its name, and nothing is started. Only the resolved paths are used after the check. Below the state directory, every file the gadget read opens (the object database, the facet index, each facet's database and its WAL and shared memory) and the `do` directories are `lstat`ed, and a symbolic link is refused. **What this doesn't cover:** Node can't hold a directory open across a child's own open (no `openat` or `O_NOFOLLOW` directory pinning), so a writer that swaps a path in the moments between the last re-check and Wrangler's or workerd's own open isn't caught. A writer with that access to the wrapper root could change the wrapper itself anyway, so the export assumes the wrapper isn't being written while it runs. **It's bounded.** `export-local` runs the export in its own process group and kills the whole group, Wrangler, esbuild and workerd included, after `--timeout-ms` (default 300000); the child ends its own group if its parent is killed outright (`stopWithParent`), and after a normal exit the group kill is skipped when the group is already empty; the Wrangler dry-run bundle is bounded at 120 s, Miniflare's start and stop at 30 s each. The deadline starts once the CLI has loaded, a few seconds after the command. **Fixed from #351:** the backend declares the Overseer unbound (reached through `ctx.exports`), so the export now gives it a binding of its own (`__INFEROS_STORAGE_EXPORT_OVERSEER`) to open it by; namespaces are opened by binding name, not class name; Miniflare's listing of facet databases (`<id>.<n>`) as object ids is filtered out; and the kernel's records are copied out as plain data before the runtime stops. The other Durable Object ids listed are platform and gatekeeper objects, inventory only, not gadget state. `scripts/stage/company-storage-cli.test.ts` drives the real bundle and runtime on throwaway wrappers; it hasn't run against the full InferOS backend bundle. Each InferOS wrapper must contain data for exactly one company; never point purge at a shared state directory, because `purge-local --apply` removes the wrapper's entire `.wrangler/state` directory after checking the tenant's live InferOps offboarding status and purge deadline. Do not use `--apply` for a stage: stage manifests are plan-only and Cloudflare deletion is a separate, person-run operation. Keep the status token in `INFEROPS_OFFBOARDING_TOKEN`, never in the manifest.
  - **Pinned.** Before anything else, dry run included, `stage.ts` requires its own HEAD to be the wrapper's committed `inferos` gitlink (`git ls-tree HEAD inferos`), and the wrapper's runtime (`deployArgs`) has already checked that the submodule HEAD, the staged gitlink and `upstream.revision` agree (`checkConsumer`). A real deploy also needs both trees clean, and refuses a modified pinned checkout.
  - **Not colliding on the account.** A deployment claims its prefix and hostnames with one KV namespace per hostname it serves, `<prefix>owner.<hostname>` (`ownershipMarkers`). Read-only, before anything is created, `ownershipProblem` reads the account: KV titles and R2 bucket names by listing, and each worker name this deploy would use by probing it (`wrangler deployments list --name`; Wrangler can't list workers account-wide, and Durable Objects live in those workers). A rival claim, meaning a marker under this prefix for another hostname or a marker under another prefix for one of these hostnames, refuses even beside this deployment's own. With no claim of its own, any Worker, KV namespace or R2 bucket under the prefix refuses as unowned rather than adopted. An answer it can't read (an R2 listing it doesn't recognize, a worker probe that is neither listed nor Cloudflare's not-found code 10007) refuses too. On a first deploy, `claimMarkers` then creates the missing markers one by one, keeping the id each create returned, and lists again. The id is never read from what the create printed: after the create, the deployment lists the account's namespaces and takes the one titled exactly that (`createdNamespaceId`). No match, two namespaces with that title, or a list it can't read stops it, saying the title may have been created and how to remove it by hand. If a rival appeared meanwhile (`claimProblem`), or one of its own titles was taken between the listing and the create (another run's, so never treated as this run's), it stops with nothing else created and removes only the ids its own creates returned, never a namespace found by title. The log names where each input came from (`inputSources`: shell or file, never the value). A worker probe counts as not found only on Cloudflare's code 10007 in a JSON error or Wrangler's `[code: 10007]` line. So two first deploys racing for one slug or hostname both stop rather than both deploying. **The window left:** the guard assumes a KV namespace list reflects a namespace created just before it, which hasn't been verified against Cloudflare's API; if listing lags, two runs racing within that lag could both pass. Resources made by something other than this deploy after its check, and workers under the prefix that aren't among this deploy's names, aren't seen. `config` reports the same check, and `delete` makes it first.
  - **The wrapper's composition.** `CANVAS_CATALOG` comes from the wrapper's `inferos.canvas.json`, and the wrapper's `blueprints/` directory, when present, replaces the bundled ones (`BUNDLED_BLUEPRINTS_DIR`, as `pnpm dev` does). A wrapper with `features.customCloudflareCode` on is refused: its own gatekeepers and Workers aren't deployed yet. Capabilities the pin doesn't support are refused as at `pnpm dev`.
  - **Proven by dry run only.** `wrapper-stage.test.ts` covers the derivation, strict parsing, reserved slugs, prefix and hostname overlap, the ownership check and the gitlink parse; `stage-config.test.ts` the `--wrapper` arguments. No wrapper deployment has been made.
- `scripts/stage/stage-config.test.ts` and `stage-resources.test.ts` cover the configs built from the real packages, the stage definitions (including the authorize origin's rules and which workers get a custom domain), secret redaction in the plan (the backend's and the edge secret), edge-secret validation and the Wrangler output parsers. The runbook is [deploy a persistent stage](../wiki/stage-deploy.md); the decision is [ADR 0009](../adr/0009-persistent-stage-deploys.md) (proposed).

## Divergences from Design

- There is no design document for stages; the owner's stated intent (two Zero-Trust instances wired to InferLab dev and prod, deployed from a workstation) is recorded in [ADR 0009](../adr/0009-persistent-stage-deploys.md), which is proposed. The cloud-parity requirements in [local development](https://github.com/factory-level/inferops/blob/develop/docs/human/architecture/inferos/local-development.md) remain the nearest design.
- No CI job deploys a stage. Access applications are created by hand in Zero Trust; a deploy can only probe that one is in front of the hostname.
- Stages deploy this checkout's packages only, not wrapper gatekeepers.
- Both stages were first deployed on 2026-10-28 (`inferos-dev-*` at dev-os.factorylevel.dev, `inferos-prod-*` at os.factorylevel.dev); each answered an unauthenticated `/`, `/api/` and `/gatekeeper/inferops/oauth` with an Access login redirect. InferLab sign-in and the deployed InferOps bindings remain unproven in the cloud.
