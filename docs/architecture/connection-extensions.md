# Connection packages and reviewed fork updates

## Overview

The package pattern has a **shared conformance suite** any gatekeeper can run through a small
adapter, a **package contract** (`connection.json`) checked against a schema and against the
package's own source, a **scaffolder** that generates a working package from the reference shape,
and **manifest loading** that decides which wrapper gatekeepers may run. The InferOps gatekeeper
(`custom-gatekeepers/gatekeeper-inferops`) is the reference package (status `reference`). The
second connector, `custom-gatekeepers/gatekeeper-tickets`, was generated by the scaffolder and
filled in; it passes every shared case against its fake provider and is `conformant`. The kit's
synthetic gatekeeper passes the same suite.

A contract's `status` is a ladder only a person climbs: `scaffold` (generated, not reviewed) →
`conformant` (contract reviewed, shared suite passing against the fake provider) → `reference`
(reviewed against a real provider contract) → `production` (accepted live). Scaffolding writes
`scaffold` and nothing else, and only `reference` and `production` packages are released or bound
by default.

Not implemented from the [design](../design/connection-extensions.md): file classification, the
upgrade and reconciliation CLI, and cloud packaging of wrapper gatekeepers. Parts of
[#73](https://github.com/factory-level/inferos/issues/73) and
[#74](https://github.com/factory-level/inferos/issues/74), under
[#51](https://github.com/factory-level/inferos/issues/51).

## Components

| Path | Responsibility |
| --- | --- |
| `packages/gatekeeper-kit/src/conformance.ts` | `defineConformanceSuite(adapter, { describe, it, beforeEach })`, exported as `@gadgets/gatekeeper-kit/conformance`. Registers the shared cases through the calling test file's own vitest functions, so it runs in that package's pool (workerd for every gatekeeper today). Imports neither vitest nor `cloudflare:*`. `ConformanceAdapter<F>` maps the suite's steps onto one gatekeeper. |
| `packages/gatekeeper-kit/__tests__/workerd/conformance/adapter.ts` | The adapter for the kit's synthetic gatekeeper (`ConformanceAccount`/`ConformanceResource` over `FakeProvider`). `conformance.test.ts` registers the shared suite through it and keeps the kit-only cases (connect races, stages, cursors, journals, fences) local. |
| `custom-gatekeepers/gatekeeper-inferops/__tests__/conformance-adapter.ts`, `conformance.test.ts` | The adapter for a demo account's `DEMO` board binding over `MockInferOps`, driven through `TestHooks` as the overseer drives it. Provider faults come from the test worker's `MockInferOps` subclass (`failNextWrite("unavailable" | "lost")`), exported under the production name so every binding's client opens it. |
| `custom-gatekeepers/gatekeeper-inferops/connection.json` | The package contract: entrypoints and Durable Objects; per resource kind (`project/board`, `project/dispatch`, `knowledge/wiki`) its URL pattern, gatekeeper class, session type, scope, enabling switches, observer strategy, read calls and write calls (each with its concurrency check, idempotency mechanism and revert rule); approval behaviour; every provider error code with its meaning and whether a retry can succeed; simulation limits; configuration names (never values); the InferOps revision the board DTO schema is pinned to; and which conformance cases run where. |
| `scripts/connection-package.schema.json` | JSON Schema (draft 2020-12) for `connection.json`, format `schemaVersion: 1`. Closed objects throughout, so a credential cannot carry a value. Status is `scaffold`, `conformant`, `reference` or `production`. `compatibility.provider.revision` may be `null` when there is no real provider to pin (a scaffold or a synthetic connector). Optional `compatibility.inferos.gatekeeperApi` lists the gatekeeper API levels the package was built against; a wrapper gatekeeper must declare it. |
| `scripts/connection-package.ts` | The one reader: `readConnection(dir)` (missing, invalid with a value-free reason naming the failing path, or valid; a symbolic link or bad JSON is invalid) and `validateConnection`, over the schema with zod's `fromJSONSchema`. Defines `GATEKEEPER_API_LEVEL` (1), the level this checkout implements. |
| `scripts/connection-status.ts` | `CONNECTION_STATUSES`, `RELEASED_STATUSES` (`reference`, `production`) and `isUnreleasedConnection(dir)`, read without the schema so the release manifest and canvas selection need no validator. A contract with no known status counts as unreleased. |
| `scripts/scaffold-gatekeeper.ts`, `scripts/connection-template/` | `pnpm gatekeepers:scaffold <slug> [--consumer-root <wrapper>]` (and `pnpm gatekeepers:scaffold` in a wrapper, through its runtime). Copies the `.tmpl` files with the slug's names filled in, links `src/types.txt`, and in this checkout generates the package's `wrangler.jsonc`. Slugs are 2 to 32 lowercase letters and digits (the release slug rule has no separators). It refuses an existing directory, even an empty one, and a name the checkout or wrapper already uses, and stages beside the target so a failure leaves nothing. |
| `custom-gatekeepers/gatekeeper-tickets` | The second connector: a synthetic support-ticket service. One binding is one queue (`tickets://<workspace>/queue/<id>`); `listTickets` and `readTicket` are observed reads, and `setStatus(id, status, expectedRevision)` is the one approved write, refused at proposal and at apply for a closed ticket or a no-op. `tickets.test.ts` covers those rules; the shared suite runs all 11 cases. |
| `scripts/connection-package.test.ts` | `node --test` (part of `@gadgets/scripts`' `test` task): finds every `connection.json` one level under `packages/` and `custom-gatekeepers/`, validates it with the schema (zod's `fromJSONSchema`), and checks it against source: each `urlPattern` is declared in `src/` and names its `kind`; every entrypoint, Durable Object and resource gatekeeper is a class in `src/`; every session is an interface and every listed read and write method exists; every configuration name is read in `src/`; each pinned contract file's `source.revision` equals the recorded provider revision; each conformance test file imports and registers the suite; conformance names only listed kinds. |

## The scaffold

Generated in `custom-gatekeepers/gatekeeper-<slug>/` (or a wrapper's `gatekeepers/`), it is a
working package against a fake provider, not a template to finish before it compiles:

| File | What it holds |
| --- | --- |
| `src/<slug>.ts` | An auto-provisioned `GatekeeperVendor` (no connect flow), the account, a strategy-B verifier and one `<Name>CollectionGatekeeper` facet whose session has two observed reads and one write. The write goes through `gatekeeper-kit/actions` (`defineActions` + `ActionJournal`, fence `none`, `await-decision`), sends `<binding id>:<action id>` as the idempotency key, and classifies provider errors: known-no-effect codes are terminal (`ActionApplyError`), others stay pending. `applyAction` returns through `applyActionOutcome`, so a terminal failure reaches the overseer as a structured result (known not applied, or possibly applied for `ActionOutcomeUnknownError`) and is replayed with that classification. |
| `src/client.ts` | The typed client, headed `SCAFFOLD ... not a trusted proxy`: one named method per provider call, classified read or write, and an error-code mapper. It opens the fake provider. |
| `src/fake-provider.ts` | A Durable Object per account with seed data, revisions, idempotency-key replay and a revocation tombstone. |
| `src/types.d.ts` | The agent-facing contract, the first thing to review. |
| `__tests__/` | A test worker whose `TestHooks` plays the overseer and whose provider subclass injects faults, the adapter implementing every optional hook, and the test file registering the shared suite. |
| `connection.json` | `status: "scaffold"`, no credentials, provider revision `null`, `compatibility.inferos.gatekeeperApi: [1]`, all nine cases claimed for the one kind. |
| `README.md` | The status ladder, the steps from scaffold to connector, and Setup/Operate/Recover/Troubleshooting SOP stubs. |

In this checkout it then needs `pnpm install` and `pnpm types:generate`; a freshly generated
package passed `tsc` and all 11 conformance cases before `gatekeeper-tickets` was edited from it.

## Where packages live

| Root | What goes there | Discovered as | Runs |
| --- | --- | --- | --- |
| `custom-gatekeepers/gatekeeper-<slug>` | This fork's connection packages, with full workspace tooling (tests, types, capnweb-validate build) | A gatekeeper, by `scripts/worker-dirs.ts` | Released and bound by default only at `reference`/`production`; otherwise local, when named in `inferos.canvas.json` |
| Wrapper `gatekeepers/gatekeeper-<slug>` | A customer's private connection packages | A candidate only; loaded by `scripts/consumer/gatekeepers.ts` when listed, enabled, valid and compatible | Local development only, at any status; never packaged |
| Wrapper `workers/<id>` | Ordinary trusted custom Workers with public `/extensions/<id>` routes | Never a gatekeeper; listed in `inferos.extensions.json`, bound router-only as `CONSUMER_<ID>` | Local development only |

A `workers/` directory holding a `connection.json` is refused by `extensions.ts`, and no gatekeeper
discovery reads `workers/`, so a custom Worker route can never become an agent capability.

## Data and Control Flow

A package's test file calls `defineConformanceSuite(adapter, { describe, it, beforeEach })`. For
each case the suite calls `adapter.setup()` for a fresh connected binding, drives it through the
adapter, and fails with a `ConformanceError` naming the broken property. Operations an overseer can
be refused return the refusal message (or `null`) instead of rejecting, so no RPC rejection goes
unhandled.

| Case | Hook | What must hold |
| --- | --- | --- |
| Resource scope | `scope` | An out-of-scope target is refused with exactly the refusal an unknown one gets. |
| Observation | — | A read is authorized as an observation before it returns. |
| Sharing (two cases) | — | A collaborator who cannot see the target is refused at admission or excluded from the observation; one who can is admitted and not excluded. |
| Approval | — | A write is submitted to the approval queue and has no effect until applied; applied, it lands once. |
| Apply once | — | An approval delivered twice applies once and answers the repeat as success. |
| Stale revision | `staleRevision` | A write whose target moved on after proposal is refused at apply and never lands. |
| Server error retry | `faults` | A provider 5xx before commit leaves the write retryable; a retry lands it once. |
| Lost response retry | `faults` | A committed write whose response was lost is reported failed, and a retry (replayed or refused) never adds a second effect. |
| Revocation (two cases) | — | After revocation reads fail, and a write approved before it does not land. |

An adapter that omits an optional hook gets that case registered as skipped, with its
`notExpressed` reason in the name.

| Gatekeeper | Runs | Skipped |
| --- | --- | --- |
| Kit synthetic | all but stale revision (10) | stale revision: the fake provider has no revisions |
| InferOps `project/board` | all (11) | — |
| Tickets `queue` | all (11) | — |
| A fresh scaffold's `collection` | all (11) | — |

The InferOps contract records the cases its other kinds cover in their own suites
(`dispatch.test.ts`, `wiki.test.ts`) and the ones not tested for them (revocation and server-error
retry for `project/dispatch` and `knowledge/wiki`, which share the board's data source and
credentials), and that a connected person's revocation is covered by `account.test.ts` rather than
the suite.

The suite found that revoking a demo account did not stop its bindings: `MockInferOps.forget()`
deleted the account's data, and the next call re-seeded fresh demo data, so a held session kept
reading and an action approved before revocation applied into the new copy. `forget()` now leaves a
tombstone, and every later call is refused `UNAUTHORIZED`.

## Configuration

`connection.json` lists the package's configuration names; the schema test fails when one is not
read in `src/`. A wrapper allows its own gatekeepers with `gatekeepers: [{ slug, enabled }]` in
`inferos.config.json` ([consumer configuration](consumer-configuration.md#consumer-workers)).

`scripts/connection-package.test.ts` additionally checks, per package, that a status past
`scaffold` covers at least one kind in the shared suite, that `reference` and `production` pin a
provider revision, and that a declared `gatekeeperApi` includes this checkout's level; and that
`gatekeeper-tickets` exists at `conformant`.

## Divergences from Design

- The design's manifest question is answered as: `connection.json` with `schemaVersion` (a breaking
  format change raises it, and the schema refuses versions it does not know), a provider
  compatibility pin, and a host compatibility level (`compatibility.inferos.gatekeeperApi` against
  `GATEKEEPER_API_LEVEL`). Manifest loading fails closed on disabled, unlisted, invalid or
  incompatible entries for wrapper gatekeepers. This fork's own `custom-gatekeepers/` are not
  gated that way: they are built with the checkout, so their compatibility is the checkout's, and
  their status gates releases and the default selection instead.
- The gatekeeper API level is a hand-maintained integer. Nothing yet detects an incompatible
  change to `workshop-shared`'s gatekeeper interfaces or `gatekeeper-kit` and raises it.
- The scaffold generates a strategy-B, auto-provisioned connector with one resource kind and no
  configurator UI, connect flow, simulation or revert. Those are left to the person filling it in.
- A wrapper-scaffolded package cannot be built or tested in the wrapper yet: the wrapper has no
  workspace to install the package's dependencies, and its `cloudflare.config.ts` keeps the
  capnweb-validate build step. Its README says to develop it in a fork's `custom-gatekeepers/`
  first. The loader, `gatekeepers:check` and config generation do work on it.
- Upgrade-failure cases ("upgrade failures pass a shared real-contract fixture suite") are not in
  the suite; there is no upgrade mechanism to test.
- The second connector is synthetic (Tickets over a fake provider), not a customer one, so it
  stops at `conformant`.
- Skills, SOPs and setup or troubleshooting material are not part of the package contract yet.

## Open Questions

- The InferOps HTTP API is unversioned (`apiVersion: null`); only the board DTO has a generated,
  pinned contract. Issue, run, repository and knowledge endpoints are not pinned.
- How file classification and three-way reconciliation are recorded (design open questions) is
  untouched.
- Whether `project/dispatch` and `knowledge/wiki` should get their own adapters, or the suite a way
  to run one adapter per kind.
- Whether the release manifest should ever package wrapper gatekeepers, and with what status gate
  (cloud parity, [#11](https://github.com/factory-level/inferos/issues/11)).
- Who may advance a package's status, and whether that review should be recorded beside the
  status (today it is a reviewed edit to `connection.json`).
