# Software factory sandboxes and local CI

## Overview

The factory is the skills agents consume plus the sandbox environments they run in ([design](../design/factory.md), tracking [#285](https://github.com/factory-level/inferos/issues/285)). This checkout is the vessel: `pnpm local factory` brings the sandboxes up and down, and `scripts/ci/pipeline.ts --target=local` runs the InferOS side of release-graph nodes 1-5, 7 and 8 against them, writing evidence under `.factory/runs/<run-id>/`. GitHub Actions is a consumer of the same scripts through a reusable workflow and thin composite actions. Nothing here deploys: there is no Cloudflare account in any step.

## Components

| Path | Responsibility |
| --- | --- |

## Data and Control Flow

**Sandboxes.** `up` first checks the environment by name: model-provider keys through `runner.ts`'s `providerVariables`, cloud/deploy keys (`AWS_*` keys, `GOOGLE_APPLICATION_CREDENTIALS`, `CLOUDFLARE_API_TOKEN`, `PULUMI_ACCESS_TOKEN`, ...) and, outside `stage-probe`, the smoke credentials (`CF_ACCESS_CLIENT_ID/SECRET`, `GROKBOT_PERSONA_USER/PASSWORD`, `GROKBOT_OPERATE_USER`). Any hit refuses `up` and FAILs `doctor`; values never enter a report. It then starts, per sandbox:

- `inferos`: adopts this checkout's recorded dev server (`stackOwnership` from `stack.ts`), refuses a foreign listener, else launches `scripts/run-local.ts` detached (own process group, log `.factory/logs/inferos.log`). Health: every configured Worker through the router (`probeWorkers`) and `/` answering 200 (a router whose asset manifest went stale answers 404).
- `inferops`: adopted when `/health/ready` already answers 200 with a ready body (the route answers 200 even while Postgres is down, so a body `status` other than `ok`/`up`/`ready` is a FAIL); else one of two modes, each in `FACTORY_INFEROPS_DIR` with pnpm's script variables (`npm_*`, `PNPM_*`, `INIT_CWD`, `NODE_OPTIONS`) removed. URL `FACTORY_INFEROPS_URL`, else `8080 + FACTORY_INFEROPS_OFFSET x 100`.
  - **Checkout mode** (default): `bun run dev up --docker --seed` detached. Needs a bootstrapped checkout, which decrypts that checkout's development secrets.
  - **Image mode** (`--inferops-image REF` or `FACTORY_INFEROPS_IMAGE`; a digest reference from the InferOps CI's local registry is best): the way the InferOps CI's `local-deploy` node runs the image, so nothing is KMS-decrypted. Through `deps.runIn` in the checkout (which must be at the image's commit, since the image carries no migrations): `DROP`/`CREATE DATABASE <FACTORY_INFEROPS_DB>` (default `inferos_factory`) over `FACTORY_PG_ADMIN_URL` (default the InferOps compose Postgres, `postgres://postgres:postgres@localhost:5432/postgres`), `psql -f db/init-db.sql`, `bunx turbo run migrate`, `seed` and `seed:reserved` (throwaway probe keys). Then `docker run -d --name inferos-factory-inferops --add-host host.docker.internal:host-gateway -p 127.0.0.1:<port>:8080` with `NODE_CONFIG_ENV=factory` (no secret layer exists for it, so the API boots on `default.js` in stub auth), `NODE_ENV=production` and the database URL; no volume, no Docker socket. Every step's output goes to `.factory/logs/inferops.log`, and so does the container's log tail when it is not ready in time. A refused image reference is a usage error. `down` removes the container; the database stays until the next `up` recreates it.
- **Connect** (`--inferops-connect`, `up` only): InferOS's `run-local` is launched with `INFERLAB_AUTH_ORIGIN` and `INFEROPS_BASE_URL` both set to the sandbox's InferOps origin and `inferops` added to `AUTH_GATEKEEPERS` (`inferopsConnectEnv`), so the login page offers "Continue with InferOps" and every person connects with their own InferLab session; no stopgap token is set. Refused (usage error) unless that InferOps is `http` on loopback. In image mode the container also gets `NODE_CONFIG={"auth":{"sso":{"inferosOrigins":["<InferOS origin>"]}}}` (`inferopsSsoLayer`), registering this InferOS as the `inferos` client's redirect origin (InferOps' default allows only `http://localhost:8787`); against the image's stub auth the `/authorize` page offers the reserved test personas (`grokbot-owner` and others). An InferOS that is already running is adopted unchanged and the flag is reported as not applied (stop it first). The state records `inferos.inferops: "mock" | "connected"`. A second `up` keeps the ownership of an InferOps container an earlier `up` started, so InferOS can be restarted with new settings (say `CODING_WORKBENCH_ENABLED`/`CODING_WORKBENCH_REPOS` from the shell) without recreating the database, and `down` still removes it. Checkout mode does not set `inferosOrigins`: that checkout's own config decides.
- **Access emulator** (`--access-emulator`, `up` only, not `stage-probe`): before InferOS starts, `up` generates a service token for this run (`<hex>.access` and a 256-bit hex secret), writes it to `.factory/access-emulator.env` (mode 0600, as `CF_ACCESS_CLIENT_ID=`/`CF_ACCESS_CLIENT_SECRET=` lines, for the smoke shell to load) and launches `access-emulator.ts --port <FACTORY_ACCESS_EMULATOR_PORT, 8789> --upstream <InferOS url>` with only `PATH`, `HOME` and the token as `ACCESS_EMULATOR_CLIENT_ID/SECRET` (by name, never on its command line), logging to `.factory/logs/access-emulator.log`. A port someone else holds is reported, not taken. InferOS is launched with `PUBLIC_BASE_URL` and `DEV_PUBLIC_HOST` naming the emulator's origin (`accessFrontEnv`; `run-dev-server.ts` builds every gatekeeper's `BASE_URL` from `DEV_PUBLIC_HOST`), so OAuth callbacks and connect hand-offs come back through Access as they do on a stage hostname, and in image mode `inferopsSsoLayer` registers both origins. The emulator listens on 127.0.0.1 only and decides each request and WebSocket upgrade: matching `CF-Access-Client-Id` + `CF-Access-Client-Secret` (compared in constant time) is proxied with the token headers stripped, a `Cf-Access-Jwt-Assertion` header (any client-sent one replaced) and a `CF_Authorization` cookie (`HttpOnly; SameSite=Lax`, 24 h) on the response; a valid `CF_Authorization` cookie it issued is proxied the same way; any service-token header that does not match is 403; anything else is a 302 to `https://<team, factory-local>.cloudflareaccess.com/cdn-cgi/access/login/<host>?kid=<aud>&redirect_url=<path>`, which `isAccessRedirect` (`scripts/preview/smoke.ts`) recognises. Upgrades are piped raw once authorised. The assertion is an HS256 JWT (`aud`, `iss`, `type: app`, `common_name` = client id, 24 h) under a per-process random key. Health `service:access`: an unauthenticated `GET /` is an Access redirect. `down` stops it like any launched process and deletes the token file.
- `floci`: adopted when `127.0.0.1:<FACTORY_FLOCI_PORT>/health` answers 200 (the existing `floci-spike` container); else `docker run -d --name inferos-factory-floci -p 127.0.0.1:<port>:4588`.

`up` polls until every started service is healthy, a launched process dies (its log is named), or `--timeout` passes. `doctor` adds tool checks (`wrangler`; `docker`; for `verify` the six images; for `stage-probe` docker and `artilleryio/artillery:latest`, the smoke's browser). The state records InferOS's `url` so a stage probe can tell whether a loopback stage is this sandbox.

**Stage probe.** `stage-probe` starts nothing; it targets the stage `FACTORY_STAGE_URL` (or `--stage-url`) names, classified by `stageTarget`: an http(s) origin on `127.0.0.1`/`localhost`/`[::1]` is a **loopback** stage (the `dev` sandbox up with `--inferops-connect`, standing in for a stage), any other host must be https and is a **remote** stage (dev-os/os behind Cloudflare Access). With `FACTORY_STAGE_ACCESS=emulated` a loopback origin is an **emulated** stage (the Access emulator in front of the `dev` sandbox); the variable is refused with a remote host and with any other value, so a real stage stays https and remote. `requiredSmokeCredentials` is, by name: remote `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET`, `GROKBOT_PERSONA_USER`, `GROKBOT_OPERATE_USER`, plus `GROKBOT_PERSONA_PASSWORD` unless the stage's InferLab is in stub auth (dev is; prod's oauth, or a mode doctor could not read, keeps it required); loopback only `GROKBOT_PERSONA_USER` and `GROKBOT_OPERATE_USER` (persona ids: no Access in front, and InferOps' stub auth signs personas in without a password); emulated `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET` and the two persona names (no password: the InferOps behind it is the stub-auth sandbox one). Checks: `stage` (named and valid), `smoke-credentials` (naming, for a remote stage, the InferLab auth mode that decided the set), `stage:reachable` (`GET /` answers); remote and emulated `stage:access` (unauthenticated `GET /` is an Access login redirect, `isAccessRedirect`), `stage:access-token` (`GET /` with the service token answers 200) and `stage:access-refused` (the right client id with a wrong secret is refused: 403 from the emulator; on a remote stage a 403 or, as real Cloudflare Access answers a token matching no Service Auth policy, a 302 to `*.cloudflareaccess.com`; redirect targets are reported by host only); remote `stage:inferops` (the InferLab API `remoteStageInferopsUrl` names: `FACTORY_INFEROPS_URL`, else the `inferops.baseUrl` of the `scripts/stage/stages.ts` stage with that hostname, `api.dev.inferlab.io` for dev-os; `/health/ready` ready and `/auth/public-config` naming a mode, read without credentials since InferLab is not behind the stage's Access); emulated also its `stage:inferos`/`stage:inferops` as below with every probe through the emulator carrying the token (the InferOps is found through the recorded emulator whose upstream is the connected InferOS); loopback `stage:inferos` (every Worker and the shell, without the ownership rule, since a stage need not be this checkout's) and `stage:inferops` (the InferOps it is connected to, `FACTORY_INFEROPS_URL` or else the recorded sandbox's `inferopsUrl` when its InferOS `url` is the stage: `/health/ready` ready and `/auth/public-config` mode `stub`). The smoke itself is not a doctor check (it signs in and writes); `stage-smoke` runs this doctor and only when it is READY `node scripts/ci/stage-smoke.ts` with `FACTORY_STAGE_URL` set, relaying only its `[stage-smoke]`/`[factory]` verdict lines (and `FACTORY_STAGE_ACCESS` when set).

**Stage smoke (node 10).** `stage-smoke.ts` resolves the stage's InferOps API and auth mode as doctor does (`stageInferlab`), passes the API to the flow as `FACTORY_INFEROPS_URL` (the oracles read it rather than the sign-in popup's origin) and records both in `result.json`; it refuses on a missing stage, a forbidden credential or a missing required name (for that mode), then runs two parts, each as `docker run --rm -u <uid> -e HOME=/tmp` with the smoke variables passed by name (`-e NAME`, never a value on a command line), this checkout mounted read-only at its own path and the evidence directory writable; `--network host` only for a loopback or emulated stage. With `CF_ACCESS_CLIENT_ID/SECRET` set (remote or emulated) the browser adds the token headers through a Playwright route on the stage origin only (InferOps, another origin, never receives it), so the browser's own `/api` WebSocket rides the `CF_Authorization` cookie Access set; the Node RPC socket sends the headers; the probe routes the same way. `flow` runs `stage-smoke-flow.ts` with the image's node and its bundled Playwright/Chromium (`capnweb` resolves from the mounted checkout). Per persona it signs in through the stage's own login page ("Continue with InferOps" opens the InferOps persona page in a popup; the person's InferOS session is the page's `authToken`), completes onboarding over RPC, and connects (or reconnects) the person's InferOps account the way the connect buttons do (`connectAccount`/`reconnectAccount`, a disowned popup carrying the flow nonce, `/connect/handoff`). Over the same Workshop RPC the browser uses it ensures a workspace bound to `FACTORY_STAGE_BOARD` (default `inferops://grokbot.operations/project/board/GROK`) with a saved canvas holding the board widget, and rejects any request an interrupted run left pending. Oracles: `owner.signIn`; `owner.wikiReads` and `operate.wikiReads` (each persona's own connection to `FACTORY_STAGE_WIKI`, default `inferops://grokbot.knowledge/knowledge/wiki`, lists the Wiki's pages; the first root page read through the gatekeeper must equal, slug, title, body and section bodies, what InferOps' knowledge API answers the same persona over stub persona login; a saved canvas holding the `inferops.wiki` widget opened on that page must show its title and first prose lines, Markdown markup stripped; a read, which the operate persona's knowledge viewer role allows; run right after sign-in so a board failure does not hide it); `owner.boardRenders` (every card the gatekeeper reads appears on the canvas page); `owner.simulated` (a move proposed through the gatekeeper's issue session shows on the board while InferOps' own API, read as the owner through stub persona login, is unchanged and a request is pending); `owner.applied` (Approve clicked in the workspace's Activity panel; InferOps' API then shows the new state and a higher revision); `owner.restored` (the same move back, so the stage's board is left as found); `operate.signIn` (its own session and connected account); `operate.knowledgeWriteRefused` (a versioned `updateDocumentBody` through the operate persona's Wiki connection must fail with explicit `FORBIDDEN` at proposal or structured `lastAttempt.code=FORBIDDEN`, `outcome=notApplied` in a pending/failed action after browser approval; independent owner reads must show the same document identity, content and version before approval and after the attempt; pending requests are rejected even on failure). Generic failures, expired authentication, conflicts, missing pages, unavailable providers, accepted writes and version-only changes fail the gate. `probe` runs `load/stage-probe.yml`: 2 VUs signing in as the owner, gated by `ensure` (`vusers.failed == 0`, proposed step ceilings). Evidence `<run>/stage-smoke/`: `smoke.json` (oracles by role, no values), screenshots per step, `probe.json`, logs, `result.json`; exit 1 on any failed oracle. `down` signals each launched process group that is still alive (SIGTERM, then SIGKILL after 30 s; a recorded pid that already exited is reported, never signalled, since its group id may have been reused), removes a container only if it created it, and reports what it left running.

**Pipeline.** `pipeline.ts` refuses on any forbidden credential, then runs `verify → security → build → local-deploy → bindings → dast → perf` as `node scripts/ci/<node>.ts --run-id <id> --target=<t>`. Each command's output is teed to its log; a command is judged by its exit code, with a 5 s drain after exit, because an orphaned grandchild (a vitest worker) can hold the pipes open indefinitely. Each node writes `<node>/result.json` (gate text, commands with exit codes, durations and logs, details) and exits 0 only on a passed gate; the orchestrator records `state.json` (`nodes`, `passes`, `skipped`, `ok`). `local-deploy` precedes `bindings`, `dast` and `perf` because they need the stack. Tool containers: `--rm`, this uid, `HOME=/tmp`, checkout mounted read-only, evidence directory mounted as `/out`, no published ports, no Docker socket; `--network host` only for ZAP and Artillery, which must reach 127.0.0.1 where `wrangler dev` listens.

**Security gate.** Fingerprints ignore line numbers: `semgrep:<rule>:<file>`, `gitleaks:<rule>:<file>`, `osv:<advisory>:<package>`, `trivy:<id>:<package or file>`. Severities: Semgrep `ERROR` high; gitleaks always critical; OSV `max_severity` CVSS (≥9 critical, ≥7 high, empty unknown); Trivy's own. Only high/critical findings absent from the baseline fail. `--update-baseline` rewrites the accepted set; the committed file is reviewed in its diff.

**GitHub Actions.** `ci.yml` → `_verify.yml` jobs `lint` (setup without cache → `verify --part lint`) and `test` (setup with cache and Bun → `--part build` → `--part test`), 25-minute cap as before. Called jobs surface as `verify / Lint` and `verify / Build and test`. `factory.yml` runs the full graph on a fresh hosted VM: a full-history checkout (gitleaks' `origin/main..HEAD` range), the setup action with cache and Bun, then `pnpm factory:ci --run-id gha-<run>-<attempt> --keep-going`. A node table goes to the job summary, the evidence is uploaded, and `pnpm local factory down` runs in an `always()` step. Docker is preinstalled on the hosted image, and the nodes pull their tool images, including Artillery's, which carries Chromium for the Playwright engine. The hosted runner's user is uid 1001, which the ZAP and Artillery images do not name (they know uid 1000), and both tools fail without a passwd entry. `userEntryMount` (`scripts/ci/lib.ts`) therefore binds a read-only copy of the image's `/etc/passwd` with one added line for that uid. The container still runs as the invoking user.

## Configuration

`FACTORY_INFEROPS_DIR`, `FACTORY_INFEROPS_OFFSET`, `FACTORY_INFEROPS_URL`, `FACTORY_INFEROPS_IMAGE` (image mode), `FACTORY_INFEROPS_DB` (`inferos_factory`), `FACTORY_PG_ADMIN_URL` (the local compose Postgres), `FACTORY_FLOCI_PORT` (4588), `FACTORY_FLOCI_IMAGE` (`floci/floci-gcp:latest`); `FACTORY_ACCESS_EMULATOR_PORT` (8789), `FACTORY_STAGE_URL`, `FACTORY_STAGE_ACCESS` (`emulated`); `FACTORY_RUN_ID`, `FACTORY_BASE_REF` (`origin/main`); `FACTORY_LOCAL_USER`/`FACTORY_LOCAL_PASSWORD` for the browser flow (default the local seed's `dev`/`devpassword`). Images are pulled ahead (`doctor verify` lists them); scanners use `:latest` tags. `.factory/` is gitignored.

## Divergences from Design

- Nodes 0 (intake), 6 (e2e), 9 and 11-12 (release, Grok Bot, prod) and rollback are not in the InferOS local graph; node 10 (stage smoke) is scripted but run from `stage-probe`, not by `pipeline.ts`. The InferOps halves of nodes 4-5 live in that repo.
- The Wiki read oracles run for both smoke personas; the operate persona also attempts a body edit that must be refused. A loopback stage's `grokbot.knowledge` has no page until one is created through InferOps' knowledge API after each `up` (the reserved seed gives the workspace none; the factory-sandboxes skill has the requests). The move is proposed through the gatekeeper's issue session over the Workshop RPC (the API the board widget calls), not by dragging a card; the approval is a click. Against a non-stub InferOps (prod) the InferOps API oracles have no persona token and FAIL naming that, never pass: proving them there needs an InferOps-side read credential for the smoke. Dev's InferLab is in stub auth, so on dev-os they read `api.dev.inferlab.io` through persona login.
- A loopback stage needs saved canvases (`inferos.canvas.json`, `pnpm canvas init`, before `up`); without it `owner.boardRenders` FAILs naming that.
- `dev` does not start `grokbot` seeding or the coding runner; `verify` does not run a local `registry:2` or build images (InferOS ships Workers).
- Sandboxes are processes on the host, not one rootless container per agent run with egress limits.
- The bindings proof uses `getPlatformProxy` rather than `@cloudflare/vitest-pool-workers`.
- Perf compares against fixed `ensure` ceilings, not the last green run; the DAST scan is unauthenticated and `/api` is not API-scanned.
- `GROKBOT_PERSONA_USER=grokbot-owner` and `GROKBOT_OPERATE_USER=grokbot-operate` are required by doctor and smoke preconditions. Old ids, swapped roles, the power seat and the obsolete `GROKBOT_VIEWER_USER` variable fail closed (the legacy variable remains guarded outside stage-probe too). `GROKBOT_PERSONA_PASSWORD` is read by nothing yet: an oauth stage's sign-in flow is not scripted.

- The Access emulator proves the smoke's Access path (the service token reaching InferOS through Access, the redirect and refusal doctor checks, the session cookie on the WebSocket, OAuth and hand-offs returning through the front origin) and nothing about Cloudflare: not Access's signing (RS256 keys at `/cdn-cgi/access/certs`; its assertion is locally HS256-signed and InferOS does not verify it, since stages run Access at the edge only), identity providers or the One-time PIN, policy evaluation beyond one service token (whether a wrong token is 403 or a login redirect on the real application depends on its policies), TLS, edge timeouts, or that the stage's application is configured at all. It is http on loopback; a remote stage stays https.

## Open Questions

- Whether required status checks on `main` need renaming to `verify / Lint` and `verify / Build and test`.
- Who reviews and owns `security-baseline.json`; it was generated from the 2026-10-28 scan and needs a person's acceptance (it includes OSV and Trivy high/critical dependency advisories and one Trivy false positive on a demo principal).
- Whether checkout mode can be bootstrapped without decrypting the InferOps development secrets. Image mode avoids the question but serves the API only: no web clients and no pg-boss worker.
- Without `--inferops-connect`, InferOS in the factory talks to the InferOps gatekeeper's mock (`inferops://demo.local/...`). With it, only stub-mode persona sign-in has been exercised; a Google sign-in against a non-stub InferOps is not.
