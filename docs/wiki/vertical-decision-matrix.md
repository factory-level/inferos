# Vertical customization decision matrix

Choose native primitives, custom code and external services by concrete workflow.

## Steps

1. Select the concrete workflow and identify its real provider/data owner.
2. Start with the suggested extension surfaces, then resolve the named gap.
3. Run the row’s proof against synthetic fixtures before choosing production scope.
4. Record the chosen provider/version and update confidence with measured evidence.

There are **36 workflows across 12 areas**. All rows are proposed engineering mappings. Mechanism confidence is based on inspected native code; provider compatibility remains provisional until the exact provider/API is tested. A source may establish a boundary or representative capability without establishing every proposed workflow in that row. No row below claims clinical, industrial or financial deployment approval.

Legend: **C** configuration; **S** skill; **G** native Gadget; **B** Blueprint; **K** custom/existing gatekeeper; **E** external service or specialist infrastructure. A kernel change is intentionally not the default for any row; use the escalation rule in the capability guide when a proof identifies a missing general primitive.

## Interpretation

Configuration and skills can specialize terminology, defaults and authoring behavior. They cannot implement an absent external API or grant authority. A Gadget/Blueprint is appropriate for user-facing workflows when existing bindings suffice; a custom gatekeeper supplies missing typed actions. External systems remain authoritative for orders, tickets, patient records and devices. Shared canvas widgets can visualize these domains later, but initial delivery only implements the InferOps project/board slice.

See [priority vertical analysis](priority-verticals.md) for the first five areas and the [source ledger](research-sources.md) for evidence limitations. Additional source-provider investigations belong in the research issues rather than being silently treated as complete.
