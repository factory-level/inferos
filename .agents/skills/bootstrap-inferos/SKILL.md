# Bootstrap InferOS

In a source InferOS checkout, use `scripts/consumer/bootstrap.ts`; read `docs/wiki/consumer-bootstrap.md` for commands and `docs/design/consumer-configuration.md` for design decisions. In a generated wrapper (identified by `inferos.config.json`), use its `.inferos/runtime.ts` check/setup/doctor/blueprints/dev/intake/config/verify/recover/upgrade commands and README. A pinned older submodule may not contain the new bootstrap source or design documents; the copied wrapper helpers are the runnable entrypoints. Inspect `.inferos/config.ts` for the exact current schema.

Obtain the destination, source repository and reviewed full Git commit SHA from the task or checkout. Bootstrap into a new directory; an existing managed wrapper can be validated without replacing its edits. Do not point bootstrap at an arbitrary populated repository or silently select a moving revision.

Run the deterministic command with those three arguments, then run `pnpm inferos:check` inside the wrapper. For a Kanban customer shell, add `--capability INFEROPS_ENABLED --capability INFEROPS_AUTH` only when the task asks for them: profiles never switch a capability on. That writes a schema version 2 file and an `inferos.canvas.json` selecting the InferOps gatekeeper and the `operations` board screen; confirm both report `enabled` in `inferos:check`. Options apply only to a new wrapper; a rerun never rewrites its configuration. Check both `ok` and `pending`: configuration validation does not prove operational readiness. `pnpm run setup` installs the frozen dependency set. Run `pnpm run doctor` before startup: it checks local prerequisites and returns nonzero for blocking errors. Its `ok` reports preflight success only; `runtimeReady` remains false while InferOps adapters are pending. On pins containing `scripts/consumer/settings.ts`, its `settings` check validates the customer's required settings (sign-in origin, InferOps target, coding adapter and the rest listed in `docs/wiki/configuration-reference.md`) against the configuration and shell; fix every error it names, and never paste a secret value into a report: it prints only whether a secret is set. An occupied port must be resolved by configuration, never by stopping an unrelated process. `pnpm dev` starts the current native Workshop baseline and reports missing consumer adapters. On pins containing `scripts/local/lifecycle.ts`, `pnpm local status|start|stop|seed|verify|reset|logs` drives the same stack with JSON reports; `reset` deletes local state and needs explicit task authorization. Keep the chosen package manager version.

The wrapper owns configuration, profiles, gatekeepers and blueprints; the submodule stays pinned. Credentials belong in uncommitted local settings. Feature flags never grant authority. Durable views require composable views; do not silently enable dependent features or hide an unsupported-mode error.

To configure a customer, apply its reviewed intake (format: the pin's `scripts/consumer/intake.schema.json`; synthetic sample: `scripts/consumer/fixtures/intake/acme-field-ops.json`) with `pnpm inferos intake apply <file>`, keeping the file in the wrapper, for example `intake/<customer>.json`. Only apply an intake whose `review.status` is `reviewed`; never mark one reviewed yourself. Mark invented data `synthetic: true`. The command migrates a version 1 file, switches on only the capabilities the pin implements (Kanban → `INFEROPS_ENABLED` and `INFEROPS_AUTH`), sets the `inferops-operations` profile, writes the `customer-operations` screen template and `views/customer-operations.json`, runs `inferos:check` (rolling back on failure), and writes `intake-report.json` and `intake-report.md`. Report every requirement's disposition from the report as written: `supported` means configurable in this pin, not live-accepted, and `configured: false` means a kept customer edit leaves it off. Wiki pillars stay pending #87. Read `configuration.conflicts`: a conflict is a customer value the command kept, so ask before changing it by hand, then rerun. Commit `.inferos/intake-managed.json`. File the drafted gap issues only when the task names the repository, with `--file-issues OWNER/REPO`; a rerun never files the same requirement twice. The command never deploys. `pnpm inferos config migrate` migrates a version 1 file on its own. Wrappers older than the `inferos` script need newer copied helpers first. Do not hand-edit them into place without saying so.

For an upgrade request, follow the `upgrade-inferos` skill: `pnpm inferos upgrade <sha>` plans the pin change and `--apply` performs it without overwriting customer edits. Bootstrap itself never changes an existing wrapper's pin. Use `verify-inferos` for evidence and `recover-inferos` for port, config, fixture or state repairs. Never claim that profile/style, fixture data, durable views or custom Workers run just because their settings validate.

After setup, report the created path, actual pin, validation evidence and remaining runtime gaps. Launch/deploy/provider authorization remains governed by the user's task; bootstrap alone does not authorize a production deployment.

New wrappers include editable copies of the pinned standard sources in `blueprints/`. This is the complete format set used by `pnpm dev`, through the native `BUNDLED_BLUEPRINTS_DIR` mechanism; it is not an additive overlay. An empty legacy blueprint directory retains upstream defaults. Run `pnpm blueprints:check` after edits to compile and validate packaging, then restart development. Existing gadget instances retain their code; changing a template does not migrate them. Source/content changes trigger native template installation, while administrator curation remains authoritative. Bootstrap reruns preserve all copied files. These sandboxed Gadget blueprints do not enable custom Cloudflare Workers or implement the pending InferOps canvas.

On pins containing the profile operator, `pnpm profile:init` initializes the site name, selected profile instructions and fallback theme after local administrator login. It requires `INFEROS_ADMIN_SESSION`, supplied privately by the operator, and only connects to the configured localhost port. Do not read or print a user's token without task authorization. Initialization preserves pre-existing branding/instructions and is consumed once on the server; use ordinary admin settings for later changes. An explicit browser theme preference wins over the deployment fallback. Pins containing the density extension also initialize curated workspace/Explore listing spacing. Other profile adapters remain pending. An older pin fails explicitly; do not patch the pin silently to bypass that check.

On pins containing `scripts/consumer/extensions.ts`, `customCloudflareCode` enables manifest-listed local Workers. New wrappers include a disabled public `workers/hello` example. Review executable canonical configs, then run `pnpm extensions:check` before `pnpm dev`. The manifest's IDs map to `/extensions/<id>` public routes; each Worker must authenticate private operations itself. These HTTP bindings grant no agent/gadget capability. Disabled manifests are not loaded. Do not claim cloud extension deployment is implemented: release packaging and required-input wiring remain pending. See the consumer wiki for path/name rules and local-only restrictions.

On pins containing `scripts/consumer/gatekeepers.ts`, the same flag also runs the wrapper's own gatekeepers from `gatekeepers/gatekeeper-<slug>/`. Put new vertical gatekeepers there, never in the submodule. Author `cloudflare.config.ts` (Worker name = directory name), run `pnpm gatekeepers:generate`, commit the generated `wrangler.jsonc`, and run `pnpm gatekeepers:check` to catch drift. A name the pin already uses is rejected. They are local-only: do not claim the release manifest packages them.

New wrappers also contain `views/operations.json`, a guarded project-board composition referencing the initial InferOps target. On supporting pins, run `pnpm views:check` after edits. This checks source/schema only: it does not load a board, persist a view or authorize resources. On supporting pins, enable composableViews to open the builder Canvas dialog and import a definition; add durableViews to save compositions under the workspace build capability. Temporary views disappear on reload or leaving the workspace. Board data and agent canvas tools remain pending. Preserve view edits on rerun; a later target setting change requires deliberately updating relevant view references. Portable definitions never contain ownership, sharing grants, credentials or transactional rows.

New wrappers materialize the operations profile with composable/durable views enabled, custom code disabled and compact density. Use a pin containing the canvas runtime; an older pin must fail its feature preflight rather than silently disable requested behavior. Existing explicit wrapper settings are preserved. Supporting parsers accept partial features/styling objects and resolve base defaults → profile → explicit override; inspect `inferos:check` provenance before making changes. Explicit false overrides inherited true. Disabling composition in the operations profile requires disabling durable views too. Changing only the profile name does not replace materialized fields or reinitialize existing administrator customization.

On pins containing fixtures.ts, run `pnpm fixtures:check` after editing the synthetic board. Doctor and dev enforce canonical schema and relationship validation before startup. Keep the selected fixture project identifier aligned with inferops.targetRef; preserve customized fixture files on reruns. Do not report data loading or authorization from successful schema validation. Missing validator/dependencies requires a supporting pin/setup, never bypassing validation. Schema refresh is a maintainer operation against a clean reviewed InferOps checkout, described in the consumer wiki.

New wrappers also ship runtime skill packs (`skills/operate`, `skills/build`, `skills/shared`, mapped by `inferos.skills.json`) and the `skill-upload` skill. For installing skills.sh skills such as skill-creator, authoring runtime skills or publishing packs with `pnpm skills:check` / `skills:upload`, follow `.agents/skills/skill-upload/SKILL.md`. Preloading packs is a separate administrator step after `profile:init`; a passing `skills:check` does not mean they are uploaded.
