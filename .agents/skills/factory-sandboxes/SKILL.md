# Factory sandboxes

The factory is the skills agents consume plus the sandboxes they run in; InferOS is the vessel that hosts the sandboxes. A sandbox is a credential-free set of local services. Architecture: `docs/architecture/factory.md`. Code: `scripts/local/factory.ts` (routed through `scripts/local/lifecycle.ts`).

| Sandbox | Runs | Extra checks |
| --- | --- | --- |
| `dev` | InferOS `pnpm run-local` (this checkout, :8787) + InferOps `bun run dev up --docker --seed` in **its own checkout**, or with `--inferops-image` the built InferOps API image (no KMS); with `--access-emulator` the local Cloudflare Access emulator in front of InferOS (127.0.0.1:8789) | `service:access` (with the emulator) |
| `infra` | `dev` + floci-gcp (reuses whatever answers `127.0.0.1:<port>/health`, else starts `floci/floci-gcp:latest` published on 127.0.0.1 only) | wrangler, docker |
| `verify` | `dev` | wrangler, docker, the six tool images (Semgrep, gitleaks, OSV-Scanner, Trivy, ZAP, Artillery) |
| `stage-probe` | nothing; targets the stage `FACTORY_STAGE_URL` (or `--stage-url`) names | the stage's smoke credentials are present **by name only**; the stage answers; remote: unauthenticated `/` redirects to Cloudflare Access, the service token reaches InferOS, a wrong one is refused (302 to the Access login, or 403), and its InferLab (from `scripts/stage/stages.ts`) is healthy and says its auth mode (stub: no persona password); emulated: that, the service token reaches InferOS, a wrong one is 403, then as loopback through the emulator; loopback: InferOS and its connected InferOps healthy, InferOps in stub auth; docker + the Artillery image |

## Commands

```bash
pnpm local factory up <sandbox> [--inferops-dir DIR] [--inferops-image REF] [--inferops-connect] [--access-emulator] [--timeout SECONDS]   # start, then wait for health
pnpm local factory doctor [sandbox]     # one READY/FAIL line per check + health JSON per service
pnpm local factory status               # the recorded sandbox's services only
pnpm local factory down                 # stop exactly what `up` started
pnpm local factory stage-smoke [--stage-url URL]   # doctor stage-probe, then (only if READY) node 10's smoke
```

Add `--json` for one JSON object on stdout. Exit 0 means every check is READY, 1 a FAIL, 2 a usage error.

Configuration (environment): `FACTORY_INFEROPS_DIR` (the InferOps checkout; or `--inferops-dir`), `FACTORY_INFEROPS_OFFSET` (that checkout's worktree offset; API at 8080 + offset x 100) or `FACTORY_INFEROPS_URL`, `FACTORY_INFEROPS_IMAGE` (or `--inferops-image`), `FACTORY_INFEROPS_DB` (`inferos_factory`), `FACTORY_PG_ADMIN_URL` (the local compose Postgres), `FACTORY_FLOCI_PORT` (4588), `FACTORY_FLOCI_IMAGE`, `FACTORY_ACCESS_EMULATOR_PORT` (8789); for `stage-probe` `FACTORY_STAGE_URL` and `FACTORY_STAGE_ACCESS` (`emulated`). InferOS's own port follows `--port`/`VITE_BACKEND_HOST` like the rest of `pnpm local`.

## Procedure

1. Unset every cloud, model-provider and prod credential in the shell first. `up` refuses and `doctor` FAILs while one is present (`credentials` names them; values are never printed). Do not rename a variable to dodge the check; start a clean shell.
2. Use a separate InferOps worktree with its own offset (the `new-worktree` skill in that repo). Never point `--inferops-dir` at a checkout whose `config/local.json` holds cloud keys, and never run InferOps commands from this directory: the factory runs `bun` in that checkout with pnpm's script variables stripped.
3. `pnpm local factory up dev`, then `pnpm local factory doctor`. Fix each FAIL line at its cause. A `service:inferops` FAIL saying the checkout "is not bootstrapped" means InferOps needs `bun run bootstrap`, which decrypts its development secrets; that is a person's step, not an agent's. Use image mode instead.
   - **Image mode** (no KMS): build the image with the InferOps CI (`bun ci/pipeline.ts --target=local` in that checkout; its `build` node records the digest in `.factory/runs/<id>/state.json` `ctx.digest`, the registry is `127.0.0.1:<5000 + offset x 100>`), then `pnpm local factory up dev --inferops-dir <that checkout> --inferops-image 127.0.0.1:<port>/services/inferlab@sha256:<digest>`. The checkout must be at the image's commit: migrate and seed run there, into the factory's own database (`FACTORY_INFEROPS_DB`, recreated on every `up`). The API runs in stub auth (`inferops login --persona owner` works against it); it serves no web clients and no worker. Read `.factory/logs/inferops.log` when it FAILs.
4. Run the work (for example the `factory-ci` skill), then `pnpm local factory down`.
5. **Stage smoke (release graph node 10).** In a shell holding only `PATH`/`HOME`/`USER`/`LANG`/`TERM`, `FACTORY_STAGE_URL` and the stage's smoke variables:
   - Remote stage (`https://dev-os.factorylevel.dev`, behind real Cloudflare Access): `CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET` (the stage's Access service token, e.g. `inferos-dev-smoke`, loaded from a 0600 vars file into that shell only with `set -a; . <file>; set +a`; never printed), `GROKBOT_PERSONA_USER=grokbot-operator`, `GROKBOT_VIEWER_USER=grokbot-viewer`, plus `GROKBOT_PERSONA_PASSWORD` only when the stage's InferLab is not in stub auth. Doctor finds the InferLab from `scripts/stage/stages.ts` by hostname (`dev` -> `api.dev.inferlab.io`; or `FACTORY_INFEROPS_URL`), reads its `/auth/public-config` mode and reports it in `stage:inferops` and `smoke-credentials`: dev is `stub` (persona sign-in, no password), prod's `oauth` keeps the password required, and an unknown mode is treated as not stub. Remote checks: `stage:access` (unauthenticated 302 to `<team>.cloudflareaccess.com`), `stage:access-token` (200 with the token), `stage:access-refused` (a wrong secret is a 302 to the Access login on real Access, or a 403; both are a refusal), `stage:inferops` (`/health/ready` and the mode). The smoke's InferOps API oracles read that same API (passed as `FACTORY_INFEROPS_URL`) through stub persona login; against a non-stub InferLab they FAIL with the reason, never pass. Never run anything against `os.factorylevel.dev` (prod) without the owner's explicit say-so.
   - Loopback stage (the `dev` sandbox standing in): `pnpm canvas init` (saved canvases) and `pnpm local factory up dev --inferops-image <digest> --inferops-connect` from the clean shell first; then `FACTORY_STAGE_URL=<that InferOS origin>`, `GROKBOT_PERSONA_USER=grokbot-operator`, `GROKBOT_VIEWER_USER=grokbot-viewer` (no Access, stub personas, no password). The connected InferOps is found from `.factory/sandbox.json` (or `FACTORY_INFEROPS_URL`).
   - Emulated stage (a remote stage's Access mode, locally; Cloudflare is not involved): add `--access-emulator` to that `up dev` (check port 8789, or `FACTORY_ACCESS_EMULATOR_PORT`, is free). `up` generates a service token for the run and writes it to `.factory/access-emulator.env` (0600). In the smoke shell use `FACTORY_STAGE_URL=http://127.0.0.1:8789`, `FACTORY_STAGE_ACCESS=emulated`, the two persona ids and the file's `CF_ACCESS_CLIENT_ID`/`CF_ACCESS_CLIENT_SECRET` lines (for example `env -i ... $(cat .factory/access-emulator.env) pnpm local factory doctor stage-probe`; never print them). No persona password: the InferOps behind it is still the stub-auth sandbox. Doctor adds `stage:access` (unauthenticated `/` is a 302 to `factory-local.cloudflareaccess.com/cdn-cgi/access/login/...`), `stage:access-token` (200 with the token) and `stage:access-refused` (403 for a wrong secret). The emulator signs its `Cf-Access-Jwt-Assertion` locally (HS256), so a pass proves the smoke's Access path, not Cloudflare's signing, identity providers or the stage's real Access policy; say so when reporting. `down` deletes the token file.
   - Remote dev stage data: the grokbot tenant on dev InferLab is persistent (seeded by `seed-reserved.yml` in InferOps; dispatching it needs the owner's OK). Before the smoke, check read-only as each persona (`POST /auth/inferlab-login` on `api.dev.inferlab.io`, then `GET /project/board-snapshot?ref=inferops://grokbot.operations/project/board/GROK` and `GET /knowledge/documents` with the persona's workspaces); if the GROK project or the personas are missing, stop and report. The smoke's only writes there are the GROK move and its restore; an empty `grokbot.knowledge` may get one Wiki page as `grokbot-operator` (the requests below, against `api.dev.inferlab.io`) only when the owner has authorized dev writes.
   - Loopback Wiki page: the reserved seed gives `grokbot.knowledge` (InferMind workspace `00000000-0000-4000-8000-000000000c12`) no pages, and `up` recreates the factory database, so after every `up` create one as the operator through the sandbox InferOps' knowledge API (a remote stage only as above): `POST /auth/inferlab-login` `{"personaId":"grokbot-operator","product":"inferops","transport":"bearer"}` for a token, then with `authorization: Bearer <token>` and `x-workspace-id: <that workspace>` `POST /knowledge/documents` `{"slug":"grokbot-qa-handbook","title":"Grokbot QA Handbook"}` and `PATCH /knowledge/wiki/pages/<its id>` (`x-idempotency-key`) `{"expectedVersion":1,"body":"<markdown>"}`. Without a page `operator.wikiReads`/`viewer.wikiReads` FAIL saying the Wiki lists no page.
   - `pnpm local factory doctor stage-probe` must be all READY, then `pnpm local factory stage-smoke` (or `node scripts/ci/stage-smoke.ts --part flow|probe`). Evidence is `.factory/runs/<id>/stage-smoke/` (`smoke.json` oracles, screenshots, `probe.json`, `result.json`). The oracles are `operator.signIn`, `operator.wikiReads`, `operator.boardRenders`, `operator.simulated`, `operator.applied`, `operator.restored`, `viewer.wikiReads` and `viewer.refused` (`FACTORY_STAGE_WIKI` overrides the Wiki, default `inferops://grokbot.knowledge/knowledge/wiki`). Report each oracle as it reads there; a FAIL there is the gate failing, not a flake to retry away. The smoke moves one issue and moves it back, and rejects requests an interrupted run left pending. `down` leaves running anything the factory reused (another process's floci, an InferOps already answering), and says so.

## Guardrails

- Evidence, not belief: report the doctor lines you saw. A service that the doctor shows FAIL is not "up", and a sandbox whose InferOps check FAILs has not proven InferOps.
- A port held by a process this checkout did not start is reported, never probed as the stack and never signalled.
- `stage-probe` is the only sandbox that may hold the smoke credentials (`CF_ACCESS_CLIENT_ID`, `CF_ACCESS_CLIENT_SECRET`, `GROKBOT_PERSONA_USER`, `GROKBOT_PERSONA_PASSWORD`, `GROKBOT_VIEWER_USER`); in any other sandbox they are a credentials FAIL, so keep the smoke shell separate from the one that runs `up dev`. Never echo, log or paste their values; the smoke passes them to its container by name.
- Do not weaken a loopback stage into a remote one or the reverse to make doctor green (for example plain `http://` to a remote host): the credential set follows the stage's kind. `FACTORY_STAGE_ACCESS=emulated` is for the local emulator only and is refused with a remote host; never use it to dodge a real stage's credentials.
- Docker: ports on 127.0.0.1 only, never mount `/var/run/docker.sock`. Image mode mounts nothing and passes no credential; never add a secret layer or `GOOGLE_APPLICATION_CREDENTIALS` to make an image boot.
- InferOS in `dev` reads boards from the InferOps gatekeeper's mock unless `up` is given `--inferops-connect` (or `INFEROPS_BASE_URL` and a sign-in are set in the shell that starts it); `factory status --json` records `inferos.inferops` as `mock` or `connected`. With `--inferops-connect` people sign in through the sandbox's InferOps ("Continue with InferOps"; in image mode a stub persona such as `grokbot-operator`), each with their own session. Do not report the mock as InferOps.
- State lives in `.factory/sandbox.json` and logs in `.factory/logs/` (gitignored). Do not edit the state file by hand; `down` reads it.
